Queues: FIFO, Deques, and PriorityQueue
1

ليه الدرس ده مهم؟

عندك BackgroundService في ASP.NET Core بيشيل jobs من طابور: توليد PDF، إرسال نشرة بريدية، إعادة تعيين كلمة سر. متوسط الـ job ١.٢ ثانية. ساعة الذروة الطابور فيه ٤٠٠٠ job نشرة بريدية. جه عميل طلب «reset password» — دخل آخر الطابور.

بحساب بسيط: 4000 × 1.2 ثانية ≈ ٨٠ دقيقة قبل ما إيميل الـ reset يخرج أصلاً. نفس الكود بالظبط، بس بـ PriorityQueue<Job,int> بدل Queue<Job>، الـ job ده يخرج في الدور اللي بعده = ١.٢ ثانية. مغيّرتش حرف في منطق الشغل — غيّرت سياسة الترتيب بس.
لو مش فاهم الدرس ده: هتستخدم List<T> كطابور وتنده RemoveAt(0) فتحوّل O(1) لـ O(n) من غير ما تحس، وهتفترض إن PriorityQueue بتحافظ على ترتيب الدخول للعناصر المتساوية (مش بتحافظ)، وهتكتب Dijkstra بـ Queue عادي فيطلع لك مسار غلط.
2

الفكرة في صورة: جوّه Queue<T> حلقة، مش قايمة

السؤال اللي بيحير الناس: إزاي الحذف من أول الطابور بيكون O(1) والعناصر في array متصل؟ الجواب إن مفيش حد بيتحرك — المؤشرين بس هما اللي بيلفّوا.

head — مكان العنصر اللي هيخرج tail — مكان العنصر اللي هيدخل

المؤشرين بيزيدوا بـ (i + 1) % capacity، فلما يوصلوا آخر الـ array بيلفّوا على صفر ويستخدموا الخانات اللي الـ head سابها. ده اسمه circular buffer، وهو سبب إن Enqueue وDequeue وPeek كلهم O(1). لما الـ tail يلحق الـ head (يعني Count == Capacity) بس — ساعتها الـ array بيتضاعف.

اضغط Enqueue لحد ما الخانات تخلص وشوف الـ Capacity بتتضاعف — نسخة واحدة O(n) كل n عملية، وعشان كده بنقول إن الـ Enqueue amortized O(1).

4

مثال واقعي: العيلة التلاتة ومين يستحق الأول

أ. الطابور الغلط: List<T> بـ RemoveAt(0)

❌ O(n) لكل حذف
var jobs = new List<Job>(source);
while (jobs.Count > 0) {
    var j = jobs[0];
    jobs.RemoveAt(0);     // بيزحزح كل اللي بعده
    Handle(j);
}
// 100,000 job ≈ 1,800 ms في الإزاحة لوحدها
✅ O(1) لكل حذف
var jobs = new Queue<Job>(source);
while (jobs.TryDequeue(out var j))
    Handle(j);

// نفس الـ 100,000 job ≈ 1 ms
// TryDequeue بترجع false بدل استثناء

نفس عدد الـ jobs ونفس الشغل الحقيقي — الفرق كله إن RemoveAt(0) بتنسخ ٥٠ ألف عنصر في المتوسط كل مرة، والـ Queue بتزوّد رقم.

ب. الـ Deque: داخل وخارج من الناحيتين

// .NET مفيهاش Deque<T> جاهزة — LinkedList<T> هي الأقرب، وكلها O(1)
var window = new LinkedList<int>();
window.AddLast(5);          // push back
window.AddFirst(3);         // push front
window.RemoveFirst();       // pop front
window.RemoveLast();        // pop back

// بتحتاجها في sliding window maximum، وفي undo/redo بسقف محدود

ج. PriorityQueue<TElement,TPriority> — من .NET 6

var pq = new PriorityQueue<Job, int>();
pq.Enqueue(newsletterJob, 5);
pq.Enqueue(passwordResetJob, 1);
pq.Enqueue(reportJob, 3);

pq.Dequeue();               // passwordResetJob — أصغر أولوية الأول (min-heap)
pq.Peek();                  // reportJob — بص من غير ما تشيل
pq.Count;                   // 2

// عايز الأكبر الأول؟ مش بتقلب الأرقام بإيدك — بتبعت comparer
var maxFirst = new PriorityQueue<Job, int>(
    Comparer<int>.Create((a, b) => b.CompareTo(a)));

// Channel<T>: طابور بين producer وconsumer جوّه البروسيس، بـ async
var ch = Channel.CreateBounded<Job>(new BoundedChannelOptions(1000) {

});

نفس الموديل الذهني على كل المستويات: Queue<T> جوّه الميثود، ConcurrentQueue<T> بين threads، Channel<T> بين producer وconsumer، و RabbitMQ / Azure Service Bus بين خدمات. الفرق في الضمانات والدوام، مش في الفكرة.
وفي الخوارزميات: BFS = Queue حرفياً (مستوى بمستوى)، وDijkstra = PriorityQueue حرفياً (أقرب عقدة الأول). على جراف فيه ٥٠ ألف عقدة، لو بدّلت الـ PriorityQueue بـ «دوّر على الأصغر في list» تحوّل O(E log V) لـ O(V²).
5

غلطات بتحصل كتير

  • List<T> + RemoveAt(0) كطابور — أشهر غلطة. كل حذف بيزحزح كل العناصر اللي بعده. استخدم Queue<T>.
  • Dequeue() على طابور فاضي — بترمي InvalidOperationException مش بترجع null. في أي loop استخدم TryDequeue(out var item).
  • افتراض إن PriorityQueue stable — العناصر المتساوية في الأولوية ترتيبها مش مضمون. لو محتاج العدل، خلي الأولوية مركّبة: PriorityQueue<Job,(int Prio, long Seq)> بعدّاد متزايد.
  • محاولة تعديل أولوية عنصر داخل الطابور — مفيش decrease-key. الحل المعتاد في Dijkstra: اعمل Enqueue بالقيمة الجديدة، ولما تطلع نسخة قديمة تجاهلها (lazy deletion).
  • استخدام Queue<T> من أكتر من thread — مش thread-safe، والـ corruption بيظهر كـ bug عشوائي بعد شهر. ConcurrentQueue<T> أو Channel<T> لو عايز انتظار async.
6

اختبر نفسك

1. ليه Queue<T>.Dequeue() بتكون O(1) بينما List<T>.RemoveAt(0) بتكون O(n)؟
جواها array متصل + مؤشرين. الحذف = head = (head + 1) % capacity وبس. الـ List مضطرة تخلي العنصر الأول في الخانة صفر، فبتنسخ كل اللي بعده.
2. دخّلت تلات jobs بنفس الأولوية 5 بالترتيب A ثم B ثم C في PriorityQueue<Job,int>. أول Dequeue هترجع إيه؟
الـ binary heap بيضمن إن الجذر هو الأصغر، مش إنه يحافظ على ترتيب الدخول. لو عايز العدل بين المتساويين استخدم أولوية مركّبة (Prio, Seq) والـ Seq عدّاد متزايد.
7

الخلاصة في ٣ نقاط

  1. Queue<T> جواها circular buffer، فـ Enqueue/Dequeue/Peek كلهم O(1) — وأي حل بـ List.RemoveAt(0) هو O(n) متخفّي.
  2. PriorityQueue<TElement,TPriority> binary heap بيطلّع أصغر أولوية الأول في O(log n)، ومش stable للمتساويين — ضيف رقم تسلسلي لو العدل مهم.
  3. اختار على حسب سياسة الخروج: FIFO عادي → Queue، من الناحيتين → LinkedList، «الأهم الأول» → PriorityQueue، وعبر threads → ConcurrentQueue أو Channel.
