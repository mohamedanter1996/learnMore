الـ Array مش مجرد قايمة — دي حتة ذاكرة ورا بعضها

Arrays: Memory Layout and Why Cache Matters
1

ليه الدرس ده مهم؟

تخيل عندك تقرير بيلف على مليون Order ويجمع المبيعات. كتبته بـ List<T> فخلص في ٨ ملي ثانية. زميلك كتب نفس الكود بالظبط بـ LinkedList<T> فخلص في ١٢٠ ملي ثانية. نفس عدد العمليات، نفس الـ Big-O يعني O(n)، والفرق ١٥ ضعف.

الفرق مش في عدد الخطوات — الفرق في مكان الداتا في الذاكرة. الـ CPU بيقرا الرام على دفعات، مش بايت بايت. لو داتاك ورا بعضها بتاخد الدفعة كلها شغل مفيد، ولو مبعترة بترمي ٩٠٪ من كل دفعة.
لو مش فاهم الدرس ده: هتفضل تحسّن الـ Big-O وتستغرب ليه الكود لسه بطيء، وهتختار LinkedList أو List<object> في مكان غلط، وهتقع في مصيدة الـ O(n²) المخفية من غير ما تعرف السبب الحقيقي.
2

الفكرة في صورة: الـ CPU مش بيكلّم الرام مباشرة

يعني لما تطلب arr[0] الجهاز مبيجبش ٤ بايت، بيجيب ٦٤ بايت ورا بعضها ويحطهم في الكاش. لو الـ ٦٠ بايت اللي جم معاهم هما اللي هتحتاجهم بعد كده — إنت كسبان مجاناً. ده اسمه locality of reference.

4

مثال واقعي من شغلك

أ. لفّة على مصفوفة ثنائية: صف بصف مقابل عمود بعمود

✅ صف بصف — بيمشي مع اتجاه الذاكرة
for (int r = 0; r < 4096; r++)
  for (int c = 0; c < 4096; c++)
      sum += m[r, c];   // ~45 ms
❌ عمود بعمود — كل قفزة سطر كاش جديد
for (int c = 0; c < 4096; c++)
  for (int r = 0; r < 4096; r++)
      sum += m[r, c];   // ~430 ms

نفس الـ 16 مليون عملية جمع. الفرق كله إن التاني بيرمي 15 من كل 16 int بيجيبهم.

ب. List<T> مقابل LinkedList<T>

// List<int>: العناصر ورا بعضها في array واحد جوّه
long sum = 0;
foreach (var x in list) sum += x;        // 10M عنصر ≈ 8 ms

// LinkedList<int>: كل node في مكان لوحده + pointer للي بعده
foreach (var x in linked) sum += x;      // نفس العدد ≈ 120 ms
القاعدة العملية: LinkedList بتكسب بس لو بتضيف/تحذف من النص وإنت ماسك الـ node بالفعل. غير كده List<T> بتكسب حتى في الإدخال، لأن نسخ بلوك متصل في الذاكرة أرخص من ملاحقة pointers مبعترة.

ج. حتة مهمة جداً في .NET: class مقابل struct

// Point class → الـ array بيخزن مراجع، والأجسام نفسها مبعترة في الـ heap
class PointC { public double X, Y; }
PointC[] a = ...;   // كل a[i].X = قفزة لمكان تاني في الذاكرة

// Point struct → القيم نفسها متخزنة جوّه الـ array ورا بعضها
struct PointS { public double X, Y; }
PointS[] b = ...;   // مرور متتابع حقيقي، أسرع بمراحل في اللفّات الكبيرة
5

غلطات بتحصل كتير

  • «الـ LinkedList أسرع في الإضافة» — الإضافة نفسها O(1) بس الوصول للمكان O(n)، وكل node قفزة في الذاكرة. في ٩٠٪ من الحالات List<T> أسرع فعلياً.
  • لفّ على الأعمدة بدل الصفوف في المصفوفات والصور والمصفوفات الرياضية — أبطأ ١٠ أضعاف من غير سبب.
  • array من classes صغيرة (زي نقطة أو لون) بدل struct — بتحوّل مرور متتابع لمرور مبعتر.
  • الحكم بالـ Big-O بس. O(n) على داتا متصلة ممكن تكسب O(log n) على شجرة مبعترة لما n صغيرة أو متوسطة.
6

اختبر نفسك

1. عندك int[1000] وقريت arr[0] بس. كام عنصر بقى في الكاش تقريباً؟
سطر الكاش ٦٤ بايت، والـ int ٤ بايت → 64 ÷ 4 = ١٦ عنصر بيجوا في رحلة واحدة.
2. إمتى فعلاً تختار LinkedList<T>؟
ده الموقف الوحيد اللي بتكسب فيه: عندك مرجع للـ node، فالحذف/الإضافة O(1) من غير أي إزاحة.
7

الخلاصة في ٣ نقاط

  1. الـ array = بلوك ذاكرة متصل، فـ arr[i] حساب عنوان بسيط = O(1) حقيقي.
  2. الجهاز بيقرا ٦٤ بايت في المرة. امشي مع اتجاه الذاكرة تاخد الدفعة كلها شغل مفيد.
  3. Big-O بيقولك شكل النمو، والـ memory layout بيقولك الثابت المخفي — والاتنين بيفرقوا في الإنتاج.
