الـ Linked List مش «List أسرع» — دي مقايضة: قفزة في الذاكرة مقابل حذف بـ O(1)

Linked Lists: Trade-offs vs Arrays
1

ليه الدرس ده مهم؟

عندك في الـ API كاش صغير للـ Product بيشيل ١٠ آلاف عنصر، ولما يمتلي بيرمي أقدم عنصر. كتبته بـ List<Product> وبتستخدم list.RemoveAt(0) عشان تشيل الأقدم — كل حذف بينسخ الـ ٩٩٩٩ عنصر اللي بعده مكان واحد لورا. تحت ضغط ٥٠٠ request/sec ده بيطلع ملايين النسخ في الثانية على الفاضي، والـ p99 بيقفز من ٣ ملي لـ ٤٠ ملي.

بنفس المنطق بالظبط: list.Insert(0, x) مية ألف مرة ≈ ٢١٠٠ ملي ثانية، بينما linked.AddFirst(x) نفس العدد ≈ ٦ ملي ثانية. نفس الشغل، فرق ٣٥٠ ضعف.

بس اقلب العملة: لفّة على ١٠ مليون عنصر في List<int> ≈ ٨ ملي، وفي LinkedList<int> ≈ ١٢٠ ملي. الـ array بلوك متصل، والـ linked list عبارة عن nodes متبعترة كل واحدة بتقولك «اللي بعدي فين» — وكل قفزة احتمال cache miss.
لو مش فاهم المقايضة دي: هتختار LinkedList<T> عشان سمعت إن «الحذف فيها O(1)» وهي في الحقيقة O(n) لأنك بتدوّر على العنصر الأول، هتكتب O(n²) مخفية وإنت بتلف بالـ index على linked list، وهتفضل تستخدم Insert(0, x) في حلقة من غير ما تعرف إنها بتنسخ المصفوفة كلها كل مرة.
2

الفكرة في صورة: نفس الست عناصر — وشكلين مختلفين تماماً في الذاكرة

الاتنين فيهم ٦ عناصر والمرور عليهم O(n) في الحالتين. الفرق إن الإطار الأخضر بيمشي على بلوك واحد (الجهاز جايب ١٦ عنصر مع أول قراءة)، والإطار الأحمر بيلف في الذاكرة ورا pointer — ومحدش يقدر يتوقّع رايح فين، فمفيش prefetch يفيدك.

ثمن مخفي: LinkedListNode<int> في .NET 64-bit بياخد ≈ ٤٨ بايت (object header + next + prev + مرجع للـ list + القيمة) عشان يخزّن int بـ ٤ بايت. يعني ١٠ مليون int = ٤٠ ميجا في array، وأكتر من ٤٥٠ ميجا في linked list، وكمان ١٠ مليون جسم على الـ GC.
3

خطوة بخطوة: اعكس linked list بتلات pointers

ده أشهر سؤال انترفيو على الموضوع. المفتاح: قبل ما تلمس curr.Next، خزّن اللي بعده — وإلا هتفقد باقي القايمة للأبد.

خطوة 1 من 6 
Node? prev = null, curr = head;
while (curr != null)
{
    var next = curr.Next;   // 1) خزّن اللي بعده الأول
    curr.Next = prev;        // 2) اقلب السهم
    prev = curr;             // 3) قدّم prev
    curr = next;             // 4) قدّم curr
}
// prev هو الـ head الجديد — مش curr (curr بقى null)
4

مثال واقعي من شغلك

أ. الإضافة من الأول: List<T> مقابل LinkedList<T>

❌ نسخ المصفوفة كلها كل مرة
var list = new List<int>();
for (int i = 0; i < 100_000; i++)
    list.Insert(0, i);   // ≈ 2100 ms — O(n²)
✅ node جديدة وخلاص
var linked = new LinkedList<int>();
for (int i = 0; i < 100_000; i++)
    linked.AddFirst(i);  // ≈ 6 ms — O(1) للعنصر

وبالعكس تماماً في المرور: foreach على ١٠ مليون عنصر ≈ ٨ ملي في List مقابل ≈ ١٢٠ ملي في LinkedList. يعني اختار على حسب العملية الغالبة عندك، مش على حسب السمعة.

ب. المكان اللي بتكسب فيه فعلاً: LRU cache

القاعدة: LinkedList بتكسب لما تكون ماسك الـ node نفسها — والـ Dictionary هو اللي بيديك الـ node دي في O(1). ده بالظبط شكل أي LRU حقيقي: 

class LruCache<K, V> where K : notnull
{
    private readonly int _cap;
    private readonly Dictionary<K, LinkedListNode<(K Key, V Val)>> _map = new();
    private readonly LinkedList<(K Key, V Val)> _order = new();

    public LruCache(int cap) => _cap = cap;

    public bool TryGet(K key, out V val)
    {
        if (!_map.TryGetValue(key, out var node)) { val = default!; return false; }
        _order.Remove(node);        // O(1) — إحنا ماسكين الـ node
        _order.AddFirst(node);      // بقى أحدث واحد
        val = node.Value.Val;
        return true;
    }

    public void Set(K key, V val)
    {
        if (_map.TryGetValue(key, out var old)) { _order.Remove(old); _map.Remove(key); }
        else if (_map.Count >= _cap)
        {
            var lru = _order.Last!;  // أقدم عنصر
            _order.RemoveLast();
            _map.Remove(lru.Value.Key);
        }
        _map[key] = _order.AddFirst((key, val));
    }
}
Remove(node) هنا O(1) حقيقية لأننا مش بندوّر. لو كتبت _order.Remove(value) (بالقيمة مش بالـ node) بتبقى O(n) وكل الفكرة تروح. والفرق ده هو كل الدرس.

ج. المؤشر السريع والبطيء — جرّب بنفسك

slow بيتحرك خطوة وfast خطوتين. لو فيه cycle الاتنين لازم يتقابلوا، ولو مفيش الـ fast بيخلص والـ slow بيبقى واقف في النص بالظبط.

👣 خطوات: 0 🔎 النتيجة: — 
static bool HasCycle(Node? head)
{
    var slow = head; var fast = head;
    while (fast != null && fast.Next != null)   // الشرطين مع بعض أو NullReference
    {
        slow = slow!.Next;
        fast = fast.Next.Next;
        if (ReferenceEquals(slow, fast)) return true;
    }
    return false;
}
ليه لازم يتقابلوا؟ أول ما الاتنين يدخلوا الدايرة، الـ fast بيقرّب من الـ slow خطوة واحدة كل تكرار — فالمسافة بينهم بتقل ١ كل مرة لحد ما توصل صفر. مفيش قفز فوق بعض.
5

غلطات بتحصل كتير

  • «الحذف في LinkedList بـ O(1)» — الحذف نفسه O(1) بس لما تكون ماسك الـ node. linked.Remove(value) بتلف على القايمة الأول → O(n). لازم Dictionary جنبها عشان تاخد المكسب.
  • اللف بالـ index — for (i…) { node = GetAt(i); } على linked list = O(n²) مخفية. لف بالـ foreach أو امسك node = node.Next بنفسك.
  • الرجوع بـ curr بعد العكس — بعد ما الحلقة تخلص curr بيبقى null. الـ head الجديد هو prev.
  • تعديل curr.Next قبل ما تخزّن next — بتقطع باقي القايمة وتفضل تدور على bug مش موجود في الكود اللي بعده.
  • فحص fast.Next.Next من غير ما تفحص fast.Next — NullReferenceException على أي قايمة عدد عناصرها فردي.
6

اختبر نفسك

1. في خوارزمية Floyd، ليه الـ fast (خطوتين) والـ slow (خطوة) لازم يتقابلوا لو فيه cycle؟
أول ما الاتنين يبقوا جوّه الدايرة، الـ fast بيكسب موقع واحد على الـ slow كل تكرار — فالفرق بينهم بينزل لصفر ومستحيل يقفز فوقه.
2. إمتى LinkedList<T> تكسب List<T> فعلاً في كود إنتاج؟
ده الموقف الوحيد اللي المكسب فيه حقيقي: الـ node في إيدك فالحذف/الإضافة O(1) من غير أي إزاحة ولا بحث. والذاكرة عكس ما ناس فاكرة — الـ node بتاخد ≈٤٨ بايت للـ int الواحد.
7

الخلاصة في ٣ نقاط

  1. الـ linked list بتبيع لك حذف/إضافة بـ O(1) وبتاخد منها الوصول بالـ index والـ cache locality — دي مقايضة مش ترقية.
  2. المكسب بيتحقق بس لما تكون ماسك الـ node نفسها، وعشان كده كل LRU حقيقي = Dictionary + LinkedList.
  3. اتنين حيلة بيحلّوا عيلة كاملة من الأسئلة: عكس بتلات pointers (والـ head الجديد هو prev)، ومؤشر سريع وبطيء للنص وللـ cycle.
