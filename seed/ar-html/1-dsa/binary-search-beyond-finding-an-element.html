الـ Binary Search مش «دوّر على رقم» — دي أداة بتسأل سؤال واحد وترمي نص الاحتمالات

Binary Search: Beyond Finding an Element
1

ليه الدرس ده مهم؟

عندك Dictionary كبير في الـ cache بتاع الـ API: قايمة List<PricePoint> فيها ٢ مليون صف مترتّبين بالتاريخ، وendpoint في ASP.NET Core بيرجّع سعر يوم معيّن. كتبتها prices.FirstOrDefault(p => p.Day == day) فبقت ٩ ملي ثانية للريكوست الواحد. مع ٣٠٠ ريكوست في الثانية ده بياكل أكتر من ٢ ثانية CPU كل ثانية — الـ thread pool بيختنق وأنت لسه مش بتعمل أي حاجة غير بحث.

نفس الداتا، نفس الترتيب، prices.BinarySearch(...) = ٢١ مقارنة بدل ٢ مليون. وده أقل جزء مهم في الدرس. الجزء التاني: نفس الفكرة بتحل أسئلة ملهاش علاقة بـ array خالص — «أول commit كسر الـ build من ٤٢٠ commit»، أو «أكبر batch size يخلّص الـ import قبل الـ command timeout» — بدل ما تجرب ٤٢٠ مرة، تجرب ٩.

الشرط الوحيد مش «array مترتّب» — الشرط هو إن الإجابة monotonic: يعني الشرط بيقلب من false لـ true مرة واحدة بس وميرجعش. الترتيب مجرد أشهر حالة من الحالات دي.
لو مش فاهم الدرس ده: هتفضل تعمل OrderBy + لفّة كاملة على داتا مترتّبة أصلاً، وهتكتب (lo + hi) / 2 اللي بيعمل overflow على مصفوفات كبيرة، وهتقرا الرقم السالب اللي BinarySearch بترجّعه غلط فتفقد مكان الإدخال المجاني اللي كان في إيدك.

الفرق مش في السرعة — في شكل النمو. ١٦ عنصر = ٤ خطوات، ١٠٢٤ = ١٠ خطوات، مليون = ٢٠، مليار = ٣٠. لما تضاعف الداتا، الـ linear scan بياخد الضعف والـ binary search بياخد خطوة واحدة زيادة.

مثال واقعي من شغلك

أ. بحث في cache مترتّب جوّه ASP.NET Core

❌ قبل — لفّة كاملة على كل ريكوست
// prices: List<PricePoint> مترتّبة بالـ Day، 2M صف
var row = prices.FirstOrDefault(p => p.Day == day);
// ~9.4 ms · 2,000,000 مقارنة · 0 allocation بس CPU مقتول
✅ بعد — نفس الليستة، نفس الترتيب
int i = prices.BinarySearch(
        new PricePoint { Day = day }, DayComparer.Instance);
var row = i >= 0 ? prices[i] : null;
// ~0.0009 ms · 21 مقارنة · نفس النتيجة
الرقم السالب هدية مش خطأ: List<T>.BinarySearch لما ملاقيش بترجّع ~insertionPoint (المكمّل). يعني int ip = i < 0 ? ~i : i; بيعطيك مكان الإدخال الصح على طول — ده هو الـ lower_bound مجاناً، ومفيد جداً لو بتدوّر على «أقرب تاريخ قبل كذا».

ب. الاستخدام اللي بيفرق فعلاً: ابحث في مساحة الإجابات

// أول قيمة الشرط بيبقى فيها true — طول ما الشرط monotonic
static int FirstTrue(int lo, int hi, Func<int, bool> condition)
{
    while (lo < hi)                       // الاتفاق: الإجابة في [lo, hi]
    {
        int mid = lo + (hi - lo) / 2;    // بيمنع الـ int overflow
        if (condition(mid)) hi = mid;    // mid نفسه لسه مرشّح
        else lo = mid + 1;              // mid خرج من اللعبة
    }
    return lo;
}

// 1) أول commit كسر الـ build: 9 محاولات بدل 420
int firstBad = FirstTrue(1, 420, v => IsBuildBroken(v));

// 2) أكبر batch size يخلّص قبل الـ 25 ثانية (SqlCommand.CommandTimeout = 30)
int tooSlow = FirstTrue(100, 50_000, n => MeasureImport(n) > 25_000);
int best = tooSlow - 1;                 // 16 قياس بدل ما تجرب بالعين

ديمو: ٣٢ نسخة build. أول نسخة مكسورة بتتحدد عشوائي، وFirstTrue بيلاقيها بـ ٥ محاولات.

🧪 محاولات binary: 0 🐌 لو مشيت واحد واحد: —
الحاجة اللي بتفتح دماغك: لو الشرط بتاعك بيتحقق مرة واحدة ومبيرجعش، إنت عندك binary search مستني — حتى لو مفيش array في المسألة أصلاً.
5

غلطات بتحصل كتير

  • mid = (lo + hi) / 2 — على مصفوفة كبيرة (أو لما تبحث في مساحة قيم كبيرة) الجمع بيتعدى int.MaxValue فيبقى سالب والـ index يرمي exception. اكتب lo + (hi - lo) / 2 دايماً — نفس النتيجة رياضياً، من غير overflow.
  • بحث ثنائي على داتا مش مترتّبة — BinarySearch مش بترمي exception، بترجّع نتيجة غلط بهدوء. ولو عملت OrderBy قبل كل بحث، الـ O(n log n) بتاع الترتيب بياكل كل الكسب — رتّب مرة واحدة واحفظ الترتيب.
  • خلط الاتفاقين — while (lo <= hi) لازم يمشي مع hi = mid - 1، وwhile (lo < hi) لازم يمشي مع hi = mid. خلطهم = loop لا نهائي أو إجابة ناقصة عنصر. اختار اتفاق واحد وثبّت عليه.
  • قراءة الرقم السالب كـ «مش موجود» وبس — ~i هو مكان الإدخال؛ لو رميته بترجع تلف على الليستة تاني عشان تلاقي أقرب عنصر كنت ماسكه خلاص.
  • استخدامها على شرط مش monotonic — «أول يوم المبيعات فيه فوق المتوسط» بيقلب true/false كذا مرة، فالـ binary search هترجّع واحد منهم عشوائي. monotonic = شرط للصحة، مش تفصيلة.
6

اختبر نفسك

1. ليه نكتب mid = lo + (hi - lo) / 2 بدل (lo + hi) / 2؟
الاتنين متساويين رياضياً، بس lo + hi ممكن يعمل overflow على indices كبيرة فيطلع رقم سالب. الصيغة التانية مبتجمعش رقمين كبيرين خالص.
2. إيه الشرط اللي لازم يتحقق عشان تستخدم binary search على «مساحة الإجابات» مش على array؟
الترتيب نفسه مجرد حالة خاصة من الـ monotonicity. طول ما condition(x) بيقلب مرة واحدة بس، كل مقارنة بتستبعد نص المساحة بثقة — ودي الحاجة الوحيدة اللي الخوارزمية محتاجاها.
7

الخلاصة في ٣ نقاط

  1. Binary search مش بتقلل الخطوات — بتغيّر شكل النمو: مضاعفة الداتا = خطوة واحدة زيادة بس.
  2. الشرط الحقيقي هو الـ monotonicity، فأي سؤال شكله «أول قيمة الشرط بيتحقق عندها» ينفع فيه.
  3. ثبّت اتفاق واحد للمدى واكتب lo + (hi - lo) / 2 — كل باجات الدرس ده بتيجي من ±1 وoverflow.
