Stacks: LIFO and Its Surprising Uses
1

ليه الدرس ده مهم؟

عندك endpoint في ASP.NET Core بيرجّع شجرة التصنيفات (Category وتحته children). كتبته recursion عادي، وشغال تمام على الـ dev data اللي عمقها ٥ مستويات. في الإنتاج جات داتا مستوردة غلط فيها حلقة — تصنيف أبوه نفسه بشكل غير مباشر. النتيجة مش 500، النتيجة إن الـ process بيموت: StackOverflowException مبيتلقطش بـ try/catch ومبيشغّلش أي middleware — الـ worker بيتقتل والـ requests التانية اللي في نفسه بتضيع معاه.

الـ thread في .NET له stack ثابت، ١ ميجابايت افتراضياً. كل نداء method بياخد frame (المتغيرات المحلية + عنوان الرجوع) — حوالي ١٠٠ بايت للميثود البسيطة. يعني سقفك في حدود ١٠ آلاف نداء متداخل. الحل إنك تنقل الرصة من الـ thread stack لـ Stack<T> صريح على الـ heap: نفس الخوارزمية بالظبط، بس السقف بقى الرام مش الميجابايت.
لو مش فاهم الدرس ده: هتكتب recursion على داتا مش إنت اللي محدد عمقها، هتعمل undo/redo بـ List وInsert(0, x) فتدفع O(n) في كل خطوة، وهتفضل تحل مسائل «أقرب رقم أكبر» بلفّتين O(n²) وهي O(n) بـ stack واحد.
2

الفكرة في صورة: باب واحد بس — من فوق

ده الـ call stack بيشتغل: كل method بتنادي واحدة تانية بتترص فوقها، ولما ترجع بتتشال من فوق. عشان الدخول والخروج من طرف واحد، الـ Push والـ Pop والـ Peek كلهم O(1) — مفيش أي إزاحة لباقي العناصر زي ما بيحصل في List.Insert(0, x).

القاعدة اللي تفضل في دمّاغك: لو المسألة فيها تعشيش (nesting) أو محتاج آخر حاجة حصلت — فكّر stack على طول. ولو محتاج أول حاجة حصلت فده queue، درس تاني.

مثال واقعي من شغلك

أ. recursion على عمق مش إنت اللي محدده

❌ recursion — العمق على الـ thread stack
void Walk(Category c, List<Category> acc)
{
    acc.Add(c);
    foreach (var k in c.Children)
        Walk(k, acc);       // عمق 12k → الـ process بيموت
}
✅ stack صريح — العمق على الـ heap
void Walk(Category root, List<Category> acc)
{
    var st = new Stack<Category>();
    st.Push(root);
    var seen = new HashSet<int>();
    while (st.TryPop(out var c))
    {
        if (!seen.Add(c.Id)) continue;  // الحلقة بقت قابلة للكشف
        acc.Add(c);
        foreach (var k in c.Children) st.Push(k);
    }
}

مكسبين مش مكسب واحد: العمق بقى محدود بالرام (ملايين عقدة بدل ~١٠ آلاف)، والأهم إنك بقيت قادر تحرس على الحلقات وتوقف بـ exception عادي بدل ما الـ process يتقتل. تمن الحركة: الترتيب بقى عكسي داخل كل مستوى — لو مهم، اعمل push للـ children بالعكس.

ب. Monotonic stack: من O(n²) لـ O(n)

// المطلوب: لكل سعر، أول سعر أعلى منه جاي بعديه (مسافة الانتظار)
// ❌ لفّتين متداخلتين: 100k عنصر ≈ 2,400 ms
for (int i = 0; i < p.Length; i++)
    for (int j = i + 1; j < p.Length; j++)
        if (p[j] > p[i]) { res[i] = j - i; break; }

// ✅ stack واحد فيه الـ indices المستنية سعر أعلى: نفس الـ 100k ≈ 3 ms
var waiting = new Stack<int>();
for (int i = 0; i < p.Length; i++)
{
    while (waiting.Count > 0 && p[i] > p[waiting.Peek()])
    {
        int prev = waiting.Pop();
        res[prev] = i - prev;
    }
    waiting.Push(i);
}
ليه دي O(n) والكود فيه while جوه for؟ لأن كل index بيدخل الرصة مرة واحدة وبيخرج منها مرة واحدة على الأكثر. عدد العمليات الكلي ≤ 2n مهما كان شكل الداتا — ده الـ amortized analysis، مش شكل الأقواس المتداخلة.

ج. في Angular: مصفوفة عادية هي الـ stack

private undo: Command[] = [];
private redo: Command[] = [];

apply(c: Command) {
  c.do();
  this.undo.push(c);
  this.redo.length = 0;        // فرع جديد → الـ redo خلاص مش صالح
}
undoLast() {
  const c = this.undo.pop();   // undefined لو فاضية
  if (!c) return;
  c.undo();
  this.redo.push(c);
}

في JS استخدم push/pop على مصفوفة عادية — الاتنين على الآخر فـ O(1). الغلط الشائع إنك تستخدم unshift/shift عشان «أحدث حاجة تبان الأول» فتدفع O(n) في كل خطوة وإنت مش محتاج.

غلطات بتحصل كتير

  • try/catch حوالين recursion عميق — StackOverflowException في .NET Core مبيتلقطش خالص: الـ runtime بينهي الـ process فوراً. الحماية الوحيدة إنك تحدّ العمق بنفسك أو تشيل الـ recursion أصلاً.
  • اللفّ على Stack<T> وتوقع ترتيب الإدخال — الـ foreach وToArray() بيرجّعوا من فوق لتحت، يعني معكوس. ناس كتير تطبع لوج ويستغربوا الترتيب، أو يعملوا ToArray() ويحسبوه بنفس ترتيب الـ Push.
  • Pop() على رصة فاضية — InvalidOperationException. استخدم TryPop(out var x). وفي كود متزامن if (Count > 0) Pop() مش آمن — Stack<T> مش thread‑safe، ده شغل ConcurrentStack<T> وTryPop.
  • Undo/Redo من غير تفضية رصة الـ redo بعد أي أمر جديد — الـ redo هيرجّع خطوة من تاريخ مبقى موجود، فالمستند بيتبهدل. (اضغط undo مرتين وبعدها «اكتب كلمة» في الديمو فوق وشوف.)
  • استخدام List مع Insert(0, x) / RemoveAt(0) كـ stack — كل عملية بتزحّق كل العناصر، فالـ O(1) بقت O(n) والحلقة كلها O(n²) بدون سبب.
7

اختبر نفسك

1. أنهي مسألة دي طبيعتها stack؟
التعشيش بطبيعته LIFO: آخر قوس فتحته لازم يقفل الأول. أما BFS فمحتاج «أول واحد دخل أول واحد يطلع» يعني queue.
2. عملت Push('a') بعدين Push('b') بعدين Push('c'). stack.ToArray() بيرجّع إيه؟
الـ enumeration في Stack<T> بيمشي من الـ top للقاع، فـ ToArray() وforeach الاتنين معكوسين بالنسبة للإدخال. ده موثّق ومضمون، مش تفصيلة تنفيذ.
8

الخلاصة في ٣ نقاط

  1. الـ stack طرف واحد بس — عشان كده Push/Pop/Peek كلهم O(1) حقيقية بلا إزاحة.
  2. أي recursion هي stack مستخبي على الـ thread؛ حوّلها لـ Stack<T> صريح لما يكون العمق من داتا مش إنت اللي مسيطر عليها.
  3. تعشيش، undo/redo، و«أقرب أكبر منه» تلاتتهم نفس الأداة — لو شوفت «آخر حاجة حصلت» فكّر stack.
