كل حركة مؤشر بتشيل صف كامل من جدول الاحتمالات

Two Pointers: O(n²) → O(n)
1

ليه الدرس ده مهم؟

عندك endpoint في ASP.NET Core بيعمل تسوية (reconciliation): بيجيب قيود اليوم من SQL Server — ٢٠ ألف صف — ويدوّر على قيدين مجموعهم يساوي مبلغ معيّن. كتبتها الطريقة الطبيعية: foreach جوه foreach. يبقى عدد المقارنات 20000 × 20000 ÷ 2 ≈ 200,000,000، والـ request بياخد حوالي ٨٥٠ ملي ثانية.

نفس الشغل بمؤشرين على داتا مترتّبة: Array.Sort تقريباً ٢ ملي ثانية، وبعدها مرور واحد ٢٠ ألف خطوة = جزء من الملي ثانية. من ٨٥٠ ملي لـ أقل من ٣ ملي — ونفس النتيجة بالظبط.

السر مش إن المؤشرين «أسرع». السر إن كل خطوة بتستبعد احتمالات كتير مرة واحدة مش احتمال واحد. لما تعرف إن أكبر عنصر لو جُمع على أصغر عنصر وطلع أكبر من الهدف، يبقى العنصر الكبير ده مع أي حاجة في المدى هيطلع أكبر — فبتشيله كله من الحسبة بمقارنة واحدة.
لو مش فاهم الدرس ده: هتفضل تكتب O(n²) على داتا بتكبر مع الوقت، فالـ endpoint يشتغل تمام على ١٠٠٠ صف في الـ dev وينفجر على ٥٠ ألف في الإنتاج — وكل ما الداتا تتضاعف، الوقت يتربّع (×٤) مش يتضاعف.

الفكرة في صورة: نافذة البحث بتضيق كل خطوة

المؤشرين مبيرجعوش ورا أبداً. left بيزيد بس وright بينقص بس، فمجموع حركتهم على طول الطريق = n خطوة كحد أقصى. ده كل الإثبات: مفيش عنصر بيتزار مرتين.

مثال واقعي من شغلك

أ. النمط الأول — من الطرفين (لازم مترتّب)

❌ قبل — ٢٠ ألف صف ≈ ٨٥٠ ms
foreach (var a in entries)
  foreach (var b in entries)
    if (a.Id != b.Id && a.Amount + b.Amount == target)
        return (a, b);
// ~200,000,000 مقارنة
✅ بعد — ترتيب + مرور واحد ≈ 3 ms
var amounts = entries.Select(e => e.Amount).ToArray();
Array.Sort(amounts, entries);   // keys + items

int left = 0, right = amounts.Length - 1;
while (left < right)
{
    decimal sum = amounts[left] + amounts[right];
    if (sum == target) return (entries[left], entries[right]);
    if (sum < target) left++;   // عايز أكبر
    else right--;              // عايز أصغر
}
كن أمين مع نفسك: لو الداتا مش مترتّبة ومحتاج سؤال واحد بس، HashSet<decimal> بيحلها في O(n) من غير ترتيب — وده أسرع. المؤشرين بيكسبوا لما: الداتا مترتّبة أصلاً (جاية من ORDER BY أو من فهرس)، أو مش عايز أي تخصيص ذاكرة زيادة، أو السؤال نفسه محتاج ترتيب — زي «أقرب مجموع للهدف» أو «كل الأزواج اللي مجموعهم أقل من X»، وديّ الـ hashing مبيحلهاش.

ب. النمط التاني — سريع/بطيء (ضغط في نفس المكان)

// ❌ بيخصّص HashSet + مصفوفة جديدة: ٢٠ ألف int ≈ 300 KB allocations
var unique = sorted.Distinct().ToArray();

// ✅ المؤشر اللي بيقرا والمؤشر اللي بيكتب — صفر allocation
int write = 1;
for (int read = 1; read < a.Length; read++)
    if (a[read] != a[read - 1])
        a[write++] = a[read];

Span<int> result = a.AsSpan(0, write);   // الطول الحقيقي = write

read بيمشي على كل عنصر مرة واحدة وwrite مبيسبقهوش أبداً — فده O(n) زمن وO(1) ذاكرة. الـ GC مبيشتغلش خالص، وده اللي بيبان في الـ p99 مش في المتوسط.

ج. مؤشر لكل مصفوفة — أساس خطوة الدمج في MergeSort

int i = 0, j = 0, k = 0;
while (i < x.Length && j < y.Length)
    merged[k++] = (x[i] <= y[j]) ? x[i++] : y[j++];
while (i < x.Length) merged[k++] = x[i++];
while (j < y.Length) merged[k++] = y[j++];
// مرور واحد على الاتنين = O(n + m)

غلطات بتحصل كتير

  • مؤشرين من الطرفين على داتا مش مترتّبة — القاعدة «حرّك الشمال يبقى المجموع أكبر» مبقتش صحيحة، فالكود يرجّع نتيجة غلط من غير ما يرمي exception. وده أسوأ نوع بج.
  • نسيان تكلفة الـ sort. لو بتترّب مخصوص عشان تستخدم مؤشرين على سؤال واحد، إنت بتدفع O(n log n) مقابل حل O(n) بـ HashSet. اترّب لو الترتيب هيتعاد استخدامه أو السؤال محتاجه.
  • while (left <= right) بدل < — عند التساوي بتجمع العنصر على نفسه وتطلّع زوج وهمي (arr[i] + arr[i]).
  • تحريك المؤشرين الاتنين في نفس الخطوة لما المجموع مش مساوي الهدف — بتقفز فوق أزواج صحيحة. كل خطوة مؤشر واحد بس يتحرك، والاتجاه بيتحدد من المقارنة.
  • استخدام المصفوفة كلها بعد الضغط في نفس المكان — العناصر بعد write لسه فيها القيم القديمة. الطول الحقيقي هو write، فرجّع AsSpan(0, write) أو Array.Resize.
6

اختبر نفسك

1. ليه نمط «من الطرفين» محتاج المصفوفة تكون مترتّبة؟
الخوارزمية معتمدة على إنها تعرف أي اتجاه بيزوّد المجموع وأي اتجاه بيقلّله — وده بيبقى مضمون بس لما الداتا مترتّبة. من غير ترتيب القرار نفسه بيبقى تخمين.
2. عملت إزالة تكرار بالنمط سريع/بطيء على int[2000] وطلع write = 1200. تستخدم إيه بعد كده؟
الكتابة في نفس المكان مبتصغّرش المصفوفة. العناصر من 1200 لـ 1999 لسه شايلة قيم قديمة — write هو الطول الحقيقي الوحيد.
7

الخلاصة في ٣ نقاط

  1. مؤشرين من الطرفين بيحوّلوا O(n²) لـ O(n) لأن كل مقارنة بتستبعد عنصر كامل مع كل اللي فاضل، مش احتمال واحد.
  2. الشرط اللي الخوارزمية كلها واقفة عليه هو الترتيب — من غيره بترجّع نتيجة غلط في صمت.
  3. نمط سريع/بطيء (قارئ وكاتب) بيعمل فلترة وضغط في نفس المصفوفة بصفر تخصيص ذاكرة.
