الجدول هو الفهرس — يعني إيه clustered index؟

Clustered Indexes: The Table IS the Index
1

ليه الدرس ده مهم؟

عندك جدول Orders فيه ٥ مليون صف. استعلام بسيط WHERE OrderId = 4821993 بيرجع في ١ ملي ثانية، واستعلام تاني WHERE CustomerEmail = '...' بياخد ٤ ثواني. نفس الجدول ونفس السيرفر.

السبب: الـ clustered index مش نسخة جنب الجدول — هو الجدول نفسه مترتّب على شكل شجرة (B-tree) بعمود المفتاح. الأوراق (leaf pages) بتاعة الشجرة دي هي صفحات البيانات الحقيقية. عشان كده الجدول ميقدرش يكون ليه غير clustered index واحد بس.
لو مش فاهمه: هتختار GUID عشوائي كمفتاح clustered فتموّت الإدخال بالـ page splits، وهتستغرب ليه استعلام على عمود من غير فهرس بيقرا عشرات الآلاف من الصفحات.
2

الشجرة على الطبيعة — جرّب بنفسك

دوس على أي ID عشان تشوف الـ seek (٣ قراءات بس)، وبعدين دوس «scan» عشان تشوف الفرق لما مفيش فهرس مناسب.

Root page — أعلى الشجرة
Intermediate pages — بتقول تروح فين
Leaf pages = صفحات البيانات نفسها (الصفوف كاملة)
📄 Logical reads: 0 🎯 الوضع: —
3

خطوة بخطوة داخل الـ seek

خطوة 1 من 5
4

مثال واقعي: اقرا الأرقام بنفسك

SET STATISTICS IO ON;

-- 1) على المفتاح الـ clustered → seek
SELECT * FROM Orders WHERE OrderId = 4821993;
-- Table 'Orders'. logical reads 3        ← ارتفاع الشجرة بس

-- 2) على عمود من غير فهرس → scan للجدول كله
SELECT * FROM Orders WHERE CustomerEmail = 'a@b.com';
-- Table 'Orders'. logical reads 41,882   ← كل صفحات الجدول

اختيار المفتاح الـ clustered — الفرق في الإدخال

💥 Page splits: 0 📄 عدد الصفحات: 4
مفتاح ضيق ومتزايد وثابت (زي INT IDENTITY أو BIGINT) بيخلي كل صف جديد يروح لآخر صفحة = مفيش splits، والشجرة تفضل مرصوصة.
مفتاح عشوائي (زي NEWID()) بيرمي كل صف في نص صفحة عشوائية → الصفحة تتقسم، fragmentation يعلى، والإدخال يبطأ. لو محتاج GUID استخدمه كـ UNIQUE nonclustered وخلي الـ clustered على عمود متزايد.
حتة كتير حد بينساها: مفتاح الـ clustered متكرر جوّه كل nonclustered index (عشان يقدر يرجع للصف). فمفتاح عريض = كل الفهارس التانية تتخن على الديسك وفي الذاكرة.
5

غلطات بتحصل كتير

  • «الـ Primary Key لازم يكون Clustered» — دي الافتراضية بس مش قاعدة. PRIMARY KEY NONCLUSTERED موجود، والـ clustered ممكن يكون على عمود تاني أنسب للاستعلامات.
  • GUID عشوائي كمفتاح clustered — page splits وتفتيت مستمر. لو لازم، فكّر في NEWSEQUENTIALID() أو خلي الـ GUID nonclustered.
  • مفتاح clustered عريض (مثلاً nvarchar(200) أو ٣ أعمدة) — بيتنسخ في كل فهرس تاني.
  • فهارس كتير على جدول كتابة عالية — كل INSERT/UPDATE بيصيان كل فهرس.
  • قراءة الخطة بس من غير STATISTICS IO — عدد الـ logical reads هو المقياس اللي مبيكدبش.
6

اختبر نفسك

1. جدول فيه ٥ مليون صف وشجرة الـ clustered index ارتفاعها ٣ مستويات. كام صفحة تقريباً بيقراهم seek على المفتاح؟
الـ seek بينزل من الجذر للورقة، فالتكلفة = ارتفاع الشجرة مش عدد الصفوف. ده معنى O(log n) عملياً.
2. ليه المفتاح الـ clustered العريض مشكلة؟
كل فهرس nonclustered بيخزن مفتاح الـ clustered كمؤشر للصف — فالعرض بيتضاعف على كل الفهارس.
7

الخلاصة في ٣ نقاط

  1. الـ clustered index مش نسخة — هو الجدول مترتّب كشجرة، وأوراقها هي بياناتك.
  2. Seek = نزول من الجذر للورقة (٣–٤ قراءات مهما كبر الجدول). Scan = كل الصفحات.
  3. اختار مفتاح ضيق، متزايد، ثابت — لأنه بيتكرر في كل فهرس تاني وبيحدد سرعة الإدخال.
