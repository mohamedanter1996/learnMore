Reading Execution Plans: Your Debugger for SQL
1

ليه الدرس ده مهم؟

عندك endpoint في ASP.NET Core بيرجّع أوردرات عميل. على جهازك بيرد في ٦ ملي ثانية، وعلى الإنتاج نفس الكود بياخد ٤.٢ ثانية — من غير ما تغيّر سطر. نفس الـ SQL، نفس الفهارس، نفس EF Core. الفرق الوحيد: عدد الصفوف اللي الـ optimizer فاكر إنها هترجع.

الـ execution plan هو الإجابة الوحيدة على سؤال «هو عمل إيه بالظبط؟». بيوريك شجرة الـ operators اللي الـ optimizer اختارها، وكمان — لو طلبت actual plan — بيوريك Estimated vs Actual rows. الفرق بين الرقمين ده هو ٨٠٪ من التشخيص.
لو مش عارف تقراها: هتفضل تضيف فهارس بالتخمين، وتصدّق الـ cost % وهو مجرد تقدير، وتقعد تحسّن الـ operator الغلط ساعتين والمشكلة الحقيقية إن الـ statistics بايتة وسطر واحد اتقدّر مكان ٥٠ ألف.
2

الفكرة في صورة: الصفوف بتمشي من اليمين للشمال

الـ operator اللي على أقصى اليمين هو اللي بيلمس الداتا فعلاً (Seek / Scan)، وكل operator بيسلّم صفوفه للي على شماله لغاية SELECT. السهم بينهم = الصفوف اللي عدّت، وسُمكه = عددها.

إزاي تجيب الخطة أصلاً؟ في SSMS: Ctrl+M وبعدين نفّذ (actual plan)، أو Ctrl+L للـ estimated من غير تنفيذ. بالـ T-SQL: SET STATISTICS XML ON. ومع EF Core: query.ToQueryString() يديك الـ SQL الحقيقي، الصقه في SSMS وشغّله بالـ actual plan. دايماً الـ actual — لأنه بس هو اللي فيه الأعمدة الحقيقية للمقارنة.
3

اقرا خطة بنفسك — غيّر الشكل وغيّر عدد الصفوف

الاستعلام: SELECT OrderId, Total, Status FROM Orders WHERE CustomerId = @cid; — اختار شكل الخطة، وبعدين غيّر عدد الصفوف الحقيقي وشوف الأرقام بتتحرك. دوس على أي operator عشان تقرا تفاصيله.

الصفوف الراجعة فعلاً:
📄 Logical reads: — ⏱️ الزمن: — 📐 Estimated / Actual: —
تدفّق طبيعي سهم تخين / operator غالي ⚠ تحذير على الـ operator
دوس على أي operator فوق عشان تشوف تفاصيله — زي ما بتعمل hover في SSMS.

5

مثال واقعي: من EF Core لغاية الأرقام

أ. هات الـ SQL الحقيقي من EF Core

// أي IQueryable — من غير ما تنفّذه
var query = db.Orders
    .Where(o => o.CustomerId == cid)
    .Select(o => new { o.OrderId, o.Total, o.Status });

var sql = query.ToQueryString();   // نص T-SQL كامل بالـ parameters

// أو سجّل كل حاجة على الـ console وقت التطوير
options.LogTo(Console.WriteLine, LogLevel.Information);

ب. شغّله في SSMS بالـ actual plan + اقرا الأرقام

SET STATISTICS IO, TIME ON;

-- قبل: فهرس على CustomerId بس (مش مغطّي)
SELECT OrderId, Total, Status FROM Orders WHERE CustomerId = 91;
-- Index Seek → Key Lookup × 50,000
-- logical reads 150,182   |   elapsed time = 4,254 ms

-- الحل: خلي الفهرس يغطّي الأعمدة المطلوبة
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
    ON Orders(CustomerId) INCLUDE (Total, Status)
    WITH (DROP_EXISTING = ON);

-- بعد: Index Seek لوحده — الـ Key Lookup اختفى من الخطة
SELECT OrderId, Total, Status FROM Orders WHERE CustomerId = 91;
-- logical reads 182       |   elapsed time = 118 ms
825× أقل قراءات. ومحدش غيّر سطر C#. الخطة هي اللي قالت المشكلة فين — الـ Key Lookup كان بيتنفّذ مرة لكل صف راجع.

ج. ولو الـ Estimated بعيد عن الـ Actual؟

-- 1) statistics بايتة → حدّثها وشوف الخطة اتغيّرت ولا لأ
UPDATE STATISTICS Orders WITH FULLSCAN;

-- 2) قيمة parameter شاذة (parameter sniffing) → خطة لكل تنفيذ
SELECT OrderId, Total FROM Orders WHERE CustomerId = @cid
OPTION (RECOMPILE);

-- 3) شوف الخطة المتخزنة في الكاش من غير ما تعيد التنفيذ
SELECT qp.query_plan, st.text
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) AS qp
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
ORDER BY qs.total_logical_reads DESC;
ترتيب التشخيص الصح: الفرق بين Estimated و Actual الأول ← بعدين السهم التخين ← بعدين علامة ⚠ الصفرا ← وآخر حاجة cost %. الـ cost تقدير من الـ optimizer نفسه، فلو تقديره غلط أصلاً فالنسبة دي كمان غلط.
6

غلطات بتحصل كتير

  • الاعتماد على الـ estimated plan — مفيهوش actual rows، يعني مفيش مقارنة، يعني ضاع أهم دليل عندك. اطلب الـ actual (Ctrl+M) طول ما تقدر تنفّذ الاستعلام.
  • مطاردة الـ operator صاحب أعلى cost % — النسبة دي محسوبة من تقدير ممكن يكون غلط ١٠٠٠ ضعف. ابدأ من Estimated vs Actual، وأكّد بـ SET STATISTICS IO.
  • تجاهل المثلث الأصفر ⚠ على الـ operator — دي مش زينة، دي CONVERT_IMPLICIT أو spill على tempdb أو join predicate ناقص، والـ plan حرفياً بيقولك المشكلة.
  • «شفت Scan يبقى في مشكلة» — الـ Scan طبيعي جداً لجدول صغير أو لتقرير بياخد نص الجدول. المشكلة هي Scan على جدول كبير في استعلام انتقائي.
  • قراية الخطة من الشمال لليمين — SELECT آخر خطوة مش أولها. ابدأ من أقصى يمين الشجرة حيث الداتا بتتلمس فعلاً.
7

اختبر نفسك

1. في actual plan: operator عليه Estimated rows = 1 و Actual rows = 50,000. ده معناه إيه غالباً؟
الـ optimizer اختار operators (زي Nested Loops) وهو فاكر إن صف واحد هيعدّي. لما يعدّي ٥٠ ألف في نفس الشكل، ده بيبقى كارثة أداء.
2. أنهي رقم في الخطة تثق فيه الأول لما تقارن نسختين من نفس الاستعلام؟
الـ logical reads قياس فعلي لعدد الصفحات اللي اتقرت، مش تقدير — وبيفضل ثابت مهما كان السيرفر مشغول أو الكاش دافي.
8

الخلاصة في ٣ نقاط

  1. الخطة بتتقرا من اليمين للشمال، والبداية دايماً عند الـ operator اللي بيلمس الداتا.
  2. الفرق بين Estimated و Actual rows هو أسرع تشخيص عندك — فرق كبير معناه إن شكل الخطة اتاخد لحجم بيانات غير الحقيقي.
  3. الـ cost % تقدير، والـ logical reads قياس — قارن بالقياس مش بالتقدير.
