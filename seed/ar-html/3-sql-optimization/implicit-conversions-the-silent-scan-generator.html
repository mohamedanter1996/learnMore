ليه الدرس ده مهم؟

جدول Customers فيه ٣ مليون صف، وعمود AccountNumber VARCHAR(20) عليه فهرس nonclustered. بتشغّل الاستعلام في SSMS فبيرجع في ٠.٤ ملي ثانية بـ ٣ قراءات منطقية. نفس الاستعلام بالظبط من الـ API بتاعك بياخد ٧٤٠ ملي ثانية و٣٨,١١٢ قراءة. نفس السيرفر، نفس الفهرس، نفس النص.

السبب إن الـ string في C# بيتبعت افتراضياً كـ NVARCHAR. والعمود VARCHAR. لما النوعين يختلفوا، SQL Server بيحوّل طرف للتاني — والقرار بتاع data type precedence، مش بتاعك. وفي الحالة دي الطرف اللي بيتحول هو العمود، صف صف، قبل أي مقارنة.
لو مش فاهمه: هتفضل تضيف فهارس وتعيد كتابة الاستعلام والخطة زي ما هي scan، وهتقول «الـ SSMS سريع يبقى المشكلة في الـ ORM» من غير ما تعرف إن المشكلة سطر AddWithValue واحد. وفي أسوأ الحالات (WHERE Code = 123 على عمود نصي) هتاخد Conversion failed في الـ production على صف واحد فيه حروف.

مثال واقعي من كود .NET

أ. ADO.NET الخام — الفرق سطر واحد

❌ AddWithValue — بيبعت NVARCHAR
var cmd = new SqlCommand(
  "SELECT * FROM Customers WHERE AccountNumber = @acc", conn);
cmd.Parameters.AddWithValue("@acc", acc);
// Index Scan · logical reads 38,112 · ~740 ms
✅ نوع صريح — VarChar بطول العمود
var cmd = new SqlCommand(
  "SELECT * FROM Customers WHERE AccountNumber = @acc", conn);
cmd.Parameters.Add("@acc", SqlDbType.VarChar, 20).Value = acc;
// Index Seek · logical reads 3 · ~0.4 ms

نفس الـ SQL حرف بحرف. اللي اتغير هو نوع الـ parameter اللي اتبعت على السلك — ومعاه الخطة كلها.

ب. Dapper و EF Core

// Dapper: DbString بيخليك تحدد ansi + الطول
conn.QuerySingleOrDefault<Customer>(sql, new {
    acc = new DbString { Value = acc, IsAnsi = true, Length = 20 }
});

// EF Core: صلّحها مرة واحدة في الموديل وكل استعلام بعدها يطلع صح
modelBuilder.Entity<Customer>()
    .Property(c => c.AccountNumber)
    .HasColumnType("varchar(20)");
EF Core بيبعت الأنواع صح لو الموديل عارف نوع العمود. لو عملت scaffold من داتابيز موجودة هتلاقيها متظبطة؛ لو كتبت الـ entity بإيدك و سبت string من غير HasColumnType، هيفترض nvarchar(max) ويقع في نفس الفخ.

ج. دوّر عليها في السيرفر بتاعك

-- الخطط اللي في الكاش ومتأثرة فعلاً بتحويل ضمني
SELECT TOP 20 qs.execution_count, qt.text
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) qt
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) qp
WHERE CAST(qp.query_plan AS NVARCHAR(MAX)) LIKE '%PlanAffectingConvert%';

في الخطة الرسومية هتلاقي علامة ⚠ على الـ SELECT operator بتقول Type conversion in expression … may affect "CardinalityEstimate". في الـ XML الكلمة اللي بتدوّر عليها هي PlanAffectingConvert.

5

غلطات بتحصل كتير

  • AddWithValue في كل حتة — بيستنتج النوع من قيمة C#: الـ string بيبقى nvarchar، والـ decimal بياخد precision من القيمة نفسها فكل قيمة تولّد plan جديد. حدد النوع والطول دايماً.
  • تسكيت الـ warning بـ CAST على العمود — CAST(AccountNumber AS NVARCHAR(20)) = @p هي نفس الكارثة بالظبط، بس بقت مكتوبة بإيدك. حوّل الـ parameter: WHERE AccountNumber = CAST(@p AS VARCHAR(20)).
  • WHERE Code = 123 على عمود VARCHAR — الـ int أعلى من varchar في السلّم، فالعمود بيتحول لـ int. scan + احتمال Conversion failed when converting the varchar value … to data type int على أول صف فيه حرف. حط القيمة بين علامتين تنصيص.
  • JOIN بين عمودين نوعهم اتفرّق مع الوقت (FK int مقابل PK bigint، أو varchar مقابل nvarchar) — التحويل بيقع على عمود الجوين، فبتخسر الـ seek جوّه الـ nested loops وبتخسر دقة الـ estimates كمان.
  • الرد على الـ scan بفهرس جديد — الـ Missing Index DMV هتقترح عليك فهرس، وهتعمله، والخطة هتفضل scan لأن المشكلة مش نقص فهرس، المشكلة إن العمود مش ظاهر بقيمته الأصلية في الـ predicate.
6

اختبر نفسك

1. parameter جاي من .NET كـ string بيستعلم على عمود VARCHAR وبيعمل scan. ليه؟
الـ nvarchar أعلى في السلّم فبيكسب، والطرف اللي بيتحول هو العمود — وتحويل العمود مش SARGable. الحل: DbType.AnsiString / SqlDbType.VarChar أو ظبط نوع العمود في الموديل.
2. العمود NVARCHAR(20) والـ parameter اتبعت VARCHAR. إيه اللي بيحصل؟
التحويل الضمني مش مصيبة في ذاته. المصيبة بس لما الطرف الأدنى يكون العمود. هنا الأدنى هو الـ parameter، فبيتحول قيمة واحدة ساعة الـ compile والفهرس يفضل مستعمل.
7

الخلاصة في ٣ نقاط

  1. اختلاف الأنواع في الـ predicate بيجبر SQL Server على تحويل طرف، وجدول الـ data type precedence هو اللي بيختار مين — int فوق nvarchar فوق varchar.
  2. التحويل على الـ parameter بيحصل مرة واحدة ومش مشكلة؛ التحويل على العمود معناه function على كل صف = predicate مش SARGable = scan.
  3. صلّحها من المنبع: نوع الـ parameter = نوع العمود (SqlDbType.VarChar، DbString { IsAnsi = true }، HasColumnType("varchar(20)")) ودوّر على PlanAffectingConvert في الـ plan cache.
