الفهرس لقى الصف… بس مش شايل بياناته — دي ضريبة الـ Key Lookup

Nonclustered Indexes and the Key Lookup Tax
1

ليه الدرس ده مهم؟

عملت فهرس على Orders (CustomerId) عشان الاستعلام WHERE CustomerId = 42. الاستعلام اللي بيرجع ٥ أوردرات بقى فوري. وبعد شهر نفس الاستعلام لعميل عنده ٨٠٠٠ أوردر رجع في ٣ ثواني، والخطة بتقول Clustered Index Scan — الفهرس اللي إنت عملته متجاهَل تماماً.

السبب: ورقة الـ nonclustered index مش فيها الصف كله. فيها أعمدة المفتاح + مفتاح الـ clustering بس. أي عمود تاني في الـ SELECT لازم يتجاب برحلة كاملة جوّه الـ clustered index — لكل صف لوحده. الرحلة دي اسمها Key Lookup، وتمنها ٣–٤ قراءات منطقية في المرة.
لو مش فاهمه: هتفضل تعمل فهارس والـ optimizer يرميها، وتقول «الإحصائيات قديمة» وتعمل UPDATE STATISTICS من غير فايدة، وتحاول تفرض WITH (INDEX(...)) فتبقى أبطأ من الـ scan نفسه. المشكلة مش في الفهرس — في إن الفهرس مش مغطّي الاستعلام.
2

الفكرة في صورة

الورقة اليمين فيها الصف كامل. الورقة الشمال فيها مفتاحين بس — فأي عمود زيادة = رحلة.

الشجرتين على الطبيعة — شغّل الاستعلام بنفسك

اختار كام صف مطابق، وقرّر الفهرس يكون INCLUDE ولا لأ، وبعدين دوس «شغّل الاستعلام» وبصّ على عدّاد الـ logical reads وعلى اسم الـ operator في الخطة.

مثال واقعي

أ. نفس الاستعلام، فهرس عادي مقابل فهرس مغطّي

SET STATISTICS IO ON;

-- الفهرس العادي: المفتاح بس
CREATE INDEX IX_Orders_CustomerId ON Orders (CustomerId);

SELECT OrderDate, Total FROM Orders WHERE CustomerId = 42;
-- Index Seek + Key Lookup  ·  1,000 صف  ·  logical reads 3,104

-- الفهرس المغطّي: نفس المفتاح + الأعمدة اللي بترجّعها
CREATE INDEX IX_Orders_CustomerId_Covering
ON Orders (CustomerId)                 -- key: اللي بتدوّر وترتّب بيه
INCLUDE (OrderDate, Total);            -- payload في الأوراق بس

SELECT OrderDate, Total FROM Orders WHERE CustomerId = 42;
-- Index Seek لوحده  ·  1,000 صف  ·  logical reads 9   ← صفر lookups
❌ غير مغطّي — ضريبة لكل صف
// 1,000 صف مطابق
3 (seek) + 1000 × 3 (lookup)
= 3,104 logical reads
✅ مغطّي — الورقة فيها كل حاجة
// نفس الـ 1,000 صف
9 صفحات فهرس متتابعة
= 9 logical reads

ب. نقطة الانقلاب (tipping point) — ليه الفهرس بيتجاهَل خالص

الـ optimizer بيقارن بالتكلفة: لو الـ lookups المتوقعة أغلى من قراية الجدول كله، بيسيب الفهرس ويعمل scan. النسبة بتلف حوالي ٠.٥٪–٢٪ من صفوف الجدول (مش رقم ثابت — بيتحسب من عدد الصفحات والـ statistics). 

-- جدول 5 مليون صف، 41,882 صفحة
SELECT OrderDate, Total FROM Orders WHERE CustomerId = 77;   -- 8,000 صف متوقعين
-- 8,000 × 3 = 24,000 random read  >  41,882 sequential read؟ قريبة جداً
-- النتيجة: Clustered Index Scan. الفهرس موجود ومش مستخدم — وده قرار صح مش باج.
الترجمة العملية: «ليه الفهرس بتاعي مش شغال؟» في نص الحالات معناها «الفهرس مش مغطّي والصفوف المطابقة كتير». العلاج INCLUDE، مش INDEX hint.

ج. في EF Core: الـ projection هو اللي بيخلّي التغطية ممكنة

// ❌ بيجيب الـ entity كله → كل أعمدة Orders → مفيش فهرس يقدر يغطّي
var rows = await db.Orders
    .Where(o => o.CustomerId == 42)
    .ToListAsync();

// ✅ بترجّع عمودين → IX (CustomerId) INCLUDE (OrderDate, Total) يغطّي الاستعلام
var rows = await db.Orders
    .Where(o => o.CustomerId == 42)
    .Select(o => new { o.OrderDate, o.Total })
    .ToListAsync();
ولو بتعرّف الفهرس من الـ model بدل SQL يدوي: modelBuilder.Entity<Order>().HasIndex(o => o.CustomerId).IncludeProperties(o => new { o.OrderDate, o.Total });
5

غلطات بتحصل كتير

  • حشر أعمدة التغطية في المفتاح — ON Orders (CustomerId, OrderDate, Total) بدل INCLUDE. أعمدة المفتاح مترتّبة ومتكرّرة في كل مستويات الشجرة، فالفهرس يتخن والصيانة تغلى. المفتاح للـ WHERE والـ ORDER BY بس.
  • SELECT * — بيخلي التغطية مستحيلة عملياً (هتعمل INCLUDE للجدول كله؟)، وأي عمود جديد في الجدول بيكسر التغطية بأثر رجعي.
  • فهرس لكل استعلام — ٢٠ فهرس على جدول كتابة عالية معناها كل INSERT بيصيان ٢٠ شجرة. راجع الفهارس المتشابهة: فهرس (CustomerId) بيبقى زيادة لو عندك (CustomerId, Status).
  • فرض الفهرس بـ hint لما الخطة تعمل scan — WITH (INDEX(IX_Orders_CustomerId)) بيحوّل الـ scan لـ ٢٤ ألف lookup عشوائي. الـ optimizer كان صح؛ غيّر الفهرس مش الخطة.
  • ترتيب أعمدة المفتاح غلط — المساواة الأول بعدين المدى/الترتيب. فهرس (OrderDate, CustomerId) مش بينفع كويس مع WHERE CustomerId = 42 AND OrderDate >= @d؛ العكس هو الصح. وقيس دايماً بـ SET STATISTICS IO ON — الثواني بيكدب عليك بسبب الـ cache، عدد الـ logical reads لأ.
6

اختبر نفسك

1. الخطة بتوريك Key Lookup لكل صف جاي من فهرس nonclustered. معنى كده:
ورقة الـ NC فيها أعمدة المفتاح + مفتاح الـ clustering بس. الأعمدة الناقصة لازم تتجاب من الصف نفسه — والعلاج INCLUDE مش rebuild ولا UPDATE STATISTICS.
2. أعمدة INCLUDE بتختلف عن أعمدة المفتاح في إنها:
الـ INCLUDE payload رخيص في الصيانة ومش محسوب على حدود حجم المفتاح، بس القدرة على الـ seek/sort بتجيلك من أعمدة المفتاح لوحدها.
7

الخلاصة في ٣ نقاط

  1. ورقة الـ nonclustered index فيها المفتاح + مفتاح الـ clustering بس، فأي عمود زيادة في الـ SELECT تمنه رحلة Key Lookup لكل صف.
  2. لما الصفوف المطابقة تكتر، الـ optimizer بيحسب إن الـ lookups أغلى من الـ scan فيرمي الفهرس — ودي إجابة سؤال «ليه الفهرس بتاعي مش مستخدم؟».
  3. غطّي الاستعلام: المفتاح لأعمدة الـ WHERE/ORDER BY، وINCLUDE لأعمدة الـ SELECT — واثبت الفرق بـ logical reads مش بالثواني.
