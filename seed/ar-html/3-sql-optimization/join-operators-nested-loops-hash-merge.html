Join Operators: Nested Loops, Hash, Merge
1

ليه الدرس ده مهم؟

تقرير مبيعات بيعمل JOIN بين Orders (٢ مليون صف) وCustomers (٢٠٠ ألف صف). على الـ staging بيخلص في ٤٠٠ ملي ثانية، على الإنتاج بياخد ٢٨ ثانية. نفس الكود، نفس الفهارس، نفس الإصدار. تفتح الـ actual plan تلاقي Nested Loops ومكتوب جنبه Actual Number of Executions = 184,000 والتقدير كان 12.

الـ JOIN اللي بتكتبه منطقي — بيقول «وصّل الصفوف دي بدي». الـ optimizer بيختار واحدة من تلات خوارزميات فيزيائية: Nested Loops، Hash Match، Merge Join. وهم حرفياً تلات حاجات إنت عارفهم من الـ DSA: الـ nested for loop، الـ Dictionary، وخطوة الدمج في MergeSort.
لو مش فاهمه: هتبص على الخطة وتقول «المشكلة إن فيه Nested Loops» وتحطّ OPTION (HASH JOIN) عشان تهرب — فتثبّت قرار كان صح لحجم داتا واحد، وتكسر كل الاستعلامات الصغيرة اللي كانت شغالة. المشكلة مش العامل، المشكلة التقدير اللي اختاره.

التلاتة بيطلّعوا نفس النتيجة بالظبط. الفرق في العملة اللي بتدفعها: Nested Loops بتدفع نزلة في الشجرة لكل صف خارجي، Hash بيدفع ذاكرة، وMerge بيدفع شرط إن المدخلين مترتبين.

4

مثال واقعي: نفس الاستعلام، خطتين

SET STATISTICS IO, TIME ON;

-- إحصائيات قديمة: المحرك قدّر 12 صف من Orders، الحقيقة 184,000
SELECT c.Name, SUM(o.Total)
FROM Orders o JOIN Customers c ON c.Id = o.CustomerId
WHERE o.CreatedAt >= '2026-01-01'
GROUP BY c.Name;

-- Plan: Nested Loops، Actual Number of Executions = 184,000
-- Table 'Customers'. Scan count 184000, logical reads 552,418
-- Table 'Orders'.    Scan count 1,      logical reads 21,690
-- CPU time = 24,331 ms,  elapsed time = 28,114 ms
-- نفس الاستعلام بالحرف، بس بعد ما الإحصائيات بقت صح
UPDATE STATISTICS Orders WITH FULLSCAN;

-- Plan: Hash Match (build على Customers الأصغر، probe بـ Orders)
-- Table 'Customers'. Scan count 1, logical reads 1,432
-- Table 'Orders'.    Scan count 1, logical reads 21,690
-- CPU time = 812 ms,  elapsed time = 430 ms        ← 65× أسرع
لاحظ إن إحنا مغيرناش الاستعلام ولا ضفنا hint. غيّرنا المعلومة اللي الـ optimizer بيقرر بيها، فهو لوحده سابّ الـ Nested Loops واختار Hash Match. ده الشكل الصح للإصلاح.

أرقام تقريبية للتوضيح (الجدول الداخلي ٢٠٠ ألف صف ≈ ١٤٣٢ صفحة، وارتفاع الفهرس ٣). نقطة الانقلاب بتيجي حوالي ٥٠٠ صف خارجي — بعدها تكلفة الـ seek المتكررة بتعدّي مسح كامل مرة واحدة.

قراءة سريعة للخطة: سهم خارجي تخين داخل على Nested Loops = التقدير كدب. علامة ⚠ على Hash Match = spill للـ tempdb لأن الـ memory grant طلع أقل من اللازم. Sort ظاهر فجأة قبل Merge Join = الترتيب مش جاي من فهرس، فكّر في فهرس يدّيه مجاناً.
5

غلطات بتحصل كتير

  • استخدام join hints كعلاج — OPTION (HASH JOIN) أو LOOP JOIN بيجمّد قرار كان صح لحجم داتا واحد. بكرة الداتا تكبر أو تصغر والـ hint يفضل مكانه. صلّح الـ estimates والفهارس وسيب الاختيار للمحرك.
  • اعتبار Nested Loops هي المشكلة — هي عرض، مش مرض. السبب إن المحرك فاكر الصفوف قليلة (إحصائيات قديمة، أو predicate مش SARGable، أو متغير محلي مبيعرفش قيمته).
  • تجاهل علامة الـ spill على Hash Match — الصفراء دي معناها إن جزء من الـ hash table نزل الـ tempdb. العلاج تصليح التقدير، مش زيادة الذاكرة ولا تغيير الـ MAXDOP.
  • «Hash Match معناها خطة وحشة» — لأ. لتقرير بيجمع مليون صف، الـ Hash هو العامل الصح، والـ Nested Loops في مكانه ده هي الكارثة.
  • الحكم من الـ estimated plan بس — الـ estimated بيوريك قرار المحرك، والـ actual بيوريك هل القرار ده كان مبني على حقيقة ولا على وهم. قارن Estimated Rows بـ Actual Rows — الفرق هو كل الحكاية.
6

اختبر نفسك

1. Nested Loops بتوصّل ٥٠,٠٠٠ صف خارجي بـ seek على الجدول الداخلي. ليه ده بطيء؟
الـ loops بتلمع لما المدخل الخارجي صغير. على الكميات، الـ seek لكل صف بيخسر قدام بناء hash مرة واحدة + مسح متدفق.
2. شفت ⚠ على Hash Match في الـ actual plan. أقرب تفسير إيه؟
الـ grant بيتحسب من التقدير قبل ما الاستعلام يشتغل. تقدير أقل من الحقيقة = ذاكرة أقل = spill على الديسك. العلاج عند التقدير نفسه.
7

الخلاصة في ٣ نقاط

  1. الـ JOIN نية منطقية — المحرك بينفّذها بواحدة من تلاتة: loop لكل صف، hash في الذاكرة، أو مرور على مدخلين مترتبين.
  2. كل واحد بيكسب في مكانه: Loops لمدخل خارجي صغير وجوّا مفهرس، Hash للكميات الكبيرة غير المرتبة، Merge لما الترتيب جاهز مجاناً.
  3. إنت مبتختارش العامل — إنت بتخلّي الاختيار الصح ممكن: إحصائيات محدّثة، predicates قابلة للـ seek، وفهارس مفيدة. الـ hints آخر حاجة، مش أولها.
