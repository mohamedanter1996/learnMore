SARGability: Don't Wrap Columns in Functions
1

ليه الدرس ده مهم؟

جدول Orders فيه ٥٠٠ ألف صف، وعامل عليه فهرس على OrderDate. بتطلب طلبات سنة ٢٠٢٦ (٦١,٣٢٠ صف) بـ WHERE YEAR(OrderDate) = 2026 → ١٥٤٣ logical reads و~٢١٠ ملي ثانية. بتكتب نفس الشرط بالظبط على شكل مدى: OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01' → ١٥٨ logical read و~٢٤ ملي ثانية. نفس النتيجة، نفس الفهرس، نفس الصفوف.

SARGable = Search ARGument-able، يعني الشرط يقدر يستعمل index seek. القاعدة سطر واحد: العمود يقف لوحده على طرف، والحسابات كلها تروح للطرف التاني. الفهرس مترتّب بالقيمة الخام للعمود — مش بناتج YEAR() ولا CAST() ولا UPPER().
لو مش فاهمه: هتضيف فهارس ومتحسّش بفرق، وهتفضل تقول «الفهرس موجود أهو» والخطة scan. والأوحش: الدالة على العمود بتعمي الـ cardinality estimate، فالمحرّك يقدّر ٥٠٠ صف بدل ٦١ ألف، يختار Nested Loops، وتلاقي key lookups بالملايين في الـ join اللي بعده.
2

الفكرة في صورة

الفهرس شجرة مترتّبة بالقيمة الخام. لما تكتب YEAR(OrderDate) إنت بتسأل عن قيمة مش موجودة في الترتيب — فمفيش نقطة دخول، والمحرّك مضطر يقرا كل إدخال ويحسب الدالة عليه. لما تسيب العمود عريان وتحوّل الشرط لمدى، الترتيب نفسه بيوصّلك لأول صف مطابق ويقرا اللي بعده ورا بعضه.

3

نفس الفهرس، توقّعات مختلفة — جرّب بنفسك

الشريط ده إدخالات الفهرس مترتّبة بـ OrderDate. دوس على كل زرار وبصّ على عداد الصفوف والـ reads.

🔍 صفوف اتفحصت: 0 ✅ صفوف رجعت: 0 📄 Logical reads: 0 🎯 العملية: —
ما اتقراش اتقرا واتحسبت عليه الدالة مطابق ورجع

خد بالك من الحتة دي: التوقّع بالـ CAST بيرجع صف واحد بس — ومع ذلك بيقرا الجدول كله. عدد الصفوف الراجعة مالوش دعوة؛ اللي بيحدد الشغل هو إذا كان الفهرس ينفع يوصّلك للصف ولا لأ.

مثال واقعي: الأرقام على جدول ٥٠٠ ألف صف

SET STATISTICS IO, TIME ON;

-- ❌ الدالة ملفوفة على العمود → Index Scan
SELECT OrderId, Total FROM Orders WHERE YEAR(OrderDate) = 2026;
-- logical reads 1543 | CPU 141 ms | elapsed 210 ms | Estimated Rows 500 مقابل 61320 فعلي

-- ✅ نفس المنطق كمدى نصف مفتوح → Index Seek
SELECT OrderId, Total FROM Orders
WHERE OrderDate >= '2026-01-01' AND OrderDate < '2027-01-01';
-- logical reads 158  | CPU 15 ms  | elapsed 24 ms  | Estimated Rows 61101 (من الـ histogram)

-- ✅ يوم واحد بالظبط — لاحظ 8 reads بدل 1543
SELECT OrderId FROM Orders
WHERE OrderDate >= '2026-08-24' AND OrderDate < '2026-08-25';
-- logical reads 8
صيغة المدى النصف مفتوح (>= البداية AND < اليوم اللي بعده) هي أكتر إصلاح هتعمله في حياتك. احفظها كده بالظبط ومتستخدمش BETWEEN مع أعمدة الوقت — BETWEEN @d AND @d2 بتشمل الطرف الأخير، فبتقع في لعبة 23:59:59.997 وبتفرق حسب نوع العمود (datetime مقابل datetime2).

من EF Core

// ❌ بتترجم لـ WHERE DATEPART(year, [o].[OrderDate]) = 2026
var rows = await db.Orders
    .Where(o => o.OrderDate.Year == 2026)
    .ToListAsync();

// ✅ بتترجم لمدى SARGable
var start = new DateTime(2026, 1, 1);
var end   = start.AddYears(1);
var rows2 = await db.Orders
    .Where(o => o.OrderDate >= start && o.OrderDate < end)
    .ToListAsync();

نفس القصة مع .Date == و.ToString() و.Substring() جوّه Where — كلها بتتحوّل لدالة على العمود في الـ SQL النهائي. اقرا الـ SQL المتولّد قبل ما تحكم.

معمل التوقّعات — دوس على أي شرط

اختار شرط من فوق عشان تشوف هو SARGable ولا لأ، وإيه إعادة الكتابة.
لو الحساب مطلوب فعلاً: مفيش حاجة اسمها فهرس على YEAR(OrderDate) مباشرة. اعمل persisted computed column وافهرسه: ALTER TABLE Orders ADD OrderYear AS YEAR(OrderDate) PERSISTED; وبعدها فهرس عادي عليه. ساعتها الشرط WHERE OrderYear = 2026 بقى على عمود حقيقي مترتّب.
6

غلطات بتحصل كتير

  • «الفهرس موجود يبقى فيه seek» — وجود الفهرس شرط لازم مش كافي. الشرط هو اللي بيقرر إذا كان الفهرس ينفع يستخدم ترتيبه ولا لأ. اقرا الخطة: كلمة Scan جنب اسم الفهرس معناها إنك ضيّعته.
  • BETWEEN مع أعمدة الوقت — BETWEEN '2026-01-01' AND '2026-12-31' بتفقد كل طلبات يوم ٣١ ديسمبر بعد منتصف الليل. استخدم المدى النصف مفتوح دايماً.
  • لفّ العمود بـ UPPER أو LTRIM/RTRIM «للأمان» — الـ collation الافتراضي أصلاً case-insensitive، والمقارنة بـ = بتتجاهل المسافات في الآخر. إنت بتدفع scan مقابل لا حاجة.
  • الاعتماد على EF Core إنه «هيحسّنها» — o.OrderDate.Year == 2026 بتترجم حرفياً لـ DATEPART على العمود. الـ ORM بيترجم، مش بيعيد الصياغة.
  • نسيان الـ cardinality estimate — حتى لو الـ scan نفسه مقبول على جدول صغير، التقدير الغلط بيتسرّب للـ joins اللي بعده ويطلّع خطة كارثية على جدول كبير.
7

اختبر نفسك

1. WHERE CAST(CreatedAt AS date) = '2026-07-05' بيعمل scan رغم وجود فهرس على CreatedAt — ليه؟
إدخالات الفهرس مترتّبة بـ CreatedAt، مش بـ CAST(CreatedAt AS date). أعد الكتابة كمدى نصف مفتوح: >= '2026-07-05' AND < '2026-07-06'.
2. أنهي نمط LIKE يقدر يستخدم index seek؟
البادئة المعروفة بتتحوّل لمدى في الشجرة. الـ wildcard في الأول مبيديش نقطة دخول خالص — لو محتاجه بجد، ده شغل full-text search.
8

الخلاصة في ٣ نقاط

  1. العمود يقف لوحده على طرف الشرط، وأي حساب يروح للطرف التاني — دي كل قصة الـ SARGability.
  2. أي دالة على العمود (YEAR، CAST، ISNULL، أو حتى تحويل ضمني) بتلغي ترتيب الفهرس فتتحوّل لـ scan.
  3. الخسارة مزدوجة: scan زيادة + تقدير صفوف غلط بيخرّب الخطة كلها بعد كده — والعلاج غالباً مدى نصف مفتوح من سطرين.
