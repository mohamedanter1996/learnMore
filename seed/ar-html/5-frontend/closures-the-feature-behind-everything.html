Closures: The Feature Behind Everything
1

ليه الدرس ده مهم؟

شاشة تقرير في Angular بتحمّل ٢٠ ألف صف من الـ API — تقريباً ٤٠ ميجا في الذاكرة. في ngOnInit عاملها subscribe على تحديثات SignalR. المستخدم بيدخل الشاشة ويخرج منها ١٠ مرات في الساعة. لو أخدت snapshot للـ heap من الـ DevTools هتلاقيه طلع من ٧٨ ميجا لـ ٦١٢ ميجا، والـ ReportComponent نفسه موجود ١٠ مرات في الـ heap وهو متدمّر خلاص.

مفيش bug في الكود بمعنى الغلط المنطقي. اللي حصل إن الـ callback اللي كتبته شايل شنطة فيها this — يعني الـ component بكل داتاه. وطول ما الاشتراك عايش، الشنطة عايشة، والـ Garbage Collector مش مسموح له يلمسها لأنها لسه موصولة.
لو مش فاهم الدرس ده: هتكتب takeUntilDestroyed كطقس بتحفظه من غير ما تعرف بتحل إيه، هتتخض من 3, 3, 3 في لفّة var وتفتكرها bug في الـ JavaScript، ومش هتعرف تقرا Retainers في الـ DevTools ولا تفهم إزاي callback من ٣ سطور بيحبس ٤٠ ميجا.
2

الفكرة في صورة: الـ frame بيموت، الشنطة لأ

الحكاية في سطر واحد: الـ frame بتاع النداء بيتخلق على الـ stack ويتشال لما الـ function ترجع، بس المتغيرات اللي فيه لو حد جوّاني بيستخدمها بتتخزن في object على الـ heap اسمه Environment، والـ function الجوّانية بتشيل مؤشر ليه في خانة مخفية [[Environment]]. دي الـ closure — مش سحر، object عادي على الـ heap وليه مالك.

الفخ الأول: بتمسك المتغير، مش قيمته

دوس على الزرين وبصّ على عدد الصناديق في السطر اللي فوق الـ output.

var بتعمل binding واحد للـ function كلها، فالتلات closures ماسكين نفس الصندوق، ولما الـ timer يشتغل بعد اللفّة الصندوق بقى فيه 3. let بتعمل binding جديد كل لفّة، فكل closure عندها صندوقها. نفس الكود بالحرف، وفرق في النتيجة.

مثال واقعي من شغلك

أ. الـ closure اللي بتحبس ٤٠ ميجا

❌ قبل — الاشتراك أطول عمراً من الـ component
export class ReportComponent implements OnInit {
  private rows: Row[] = [];

  ngOnInit() {
    this.api.getRows().subscribe(r => this.rows = r);   // ~40 MB
    this.hub.onTick.subscribe(() => this.recalc(this.rows));
  }                                  // الشنطة فيها this = الـ component كله
}
// بعد ١٠ دخول/خروج: heap 78 MB → 612 MB، و١٠ نسخ من الـ component لسه في الـ Retainers
✅ بعد — الاشتراك بيموت مع الـ component
import { Component, DestroyRef, inject, OnInit } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

export class ReportComponent implements OnInit {
  private readonly destroyRef = inject(DestroyRef);

  ngOnInit() {
    this.hub.onTick
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe(() => this.recalc(this.rows));
  }
}
// نفس الـ ١٠ دخول/خروج: heap يرجع 78 MB بعد أول GC

جرّبها بنفسك: افتح الشاشة واخرج منها كذا مرة، مرة والـ takeUntilDestroyed مش مفعّل ومرة وهو مفعّل.

ب. نفس الآلية بس في خدمتك: debounce

function debounce<T extends (...a: any[]) => void>(fn: T, ms: number) {
  let timer: ReturnType<typeof setTimeout> | undefined;  // عايش في الشنطة
  return (...args: Parameters<T>) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

const search = debounce(q => this.api.search(q), 300);
// كلمة من ١١ حرف: 11 request → request واحد. ومفيش متغير برّه اتوسخ
حتة كتير حد بينساها: V8 بيعمل Context واحد للـ scope يشيل كل المتغيرات اللي أي closure جوّاني بيستخدمها. يعني لو عندك callback صغير وcallback تاني في نفس الـ scope ماسك object ٥٠ ميجا — الاتنين بيتشاركوا نفس الـ Context، فالصغير بيحبس الـ ٥٠ ميجا كمان. الحل: طلّع اللي محتاجه بس (const n = huge.length;) جوّه function منفصلة.
5

غلطات بتحصل كتير

  • «الـ closure بتاخد snapshot للقيمة» — لأ، بتمسك الـ binding نفسه. عشان كده for (var i…) مع setTimeout بيطبع 3, 3, 3 وإنت متوقع 0, 1, 2.
  • حل مشكلة الـ var بـ IIFE أو object مؤقت — شغل زيادة على الفاضي. let بتعمل binding لكل لفّة، وخلاص.
  • subscribe جوّه component من غير إنهاء — الـ callback شايل this، فالـ component بكل داتاه وخدماته محبوس. دي مش حالة خاصة، دي الآلية ورا معظم الـ leaks.
  • Map/cache عالمي القيم فيه functions — كل واحدة شايلة الـ scope اللي اتولدت فيه. الـ cache بيكبر ويكبر والـ leak صامت لأن الكود «شغال تمام».
  • الاعتماد على إن الـ closure بتشيل اللي بتستخدمه بس — الـ Context مشترك على مستوى الـ scope، فجار صغير ممكن يحبس جار تخين. صغّر الـ scope بدل ما تراهن على الـ engine.
6

اختبر نفسك

1. الـ closures بتسبب memory leak إمتى؟
الـ GC بيفضي اللي مش موصول (unreachable) بس. scope بتاع function لسه عايشة = موصول، فعمر الـ callback بقى هو عمر الداتا.
2. for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); بيطبع 3, 3, 3. ليه؟
التلات closures ماسكين نفس الصندوق. let بتعمل صندوق لكل لفّة فالنتيجة تبقى 0, 1, 2.
7

الخلاصة في ٣ نقاط

  1. الـ closure = شنطة على الـ heap: الـ frame بيتشال، والمتغيرات اللي حد جوّاني بيستخدمها تفضل عايشة معاه.
  2. بتمسك الـ binding مش القيمة — عشان كده let في اللفّات مش رفاهية.
  3. عمر الـ callback = عمر كل اللي في شنطته، فاسأل عند كل subscribe: ده شايل إيه ولحد إمتى؟
