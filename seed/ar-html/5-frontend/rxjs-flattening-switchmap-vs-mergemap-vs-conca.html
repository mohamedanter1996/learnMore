السؤال الوحيد: جه trigger جديد والشغل القديم لسه شغّال — تعمل إيه؟

RxJS Flattening: switchMap vs mergeMap vs concatMap vs exhaustMap
1

ليه الدرس ده مهم؟

عندك في Angular خانة بحث بتنادي /api/orders/search. المستخدم كتب "ahmed" — ٥ حروف = ٥ طلبات. رد الحرف التالت رجع في ٩٠٠ ملي ثانية ورد الحرف الخامس رجع في ٢٠٠. النتيجة اللي قاعدة على الشاشة في الآخر بتاعة "ahm" والمستخدم كاتب "ahmed".

وفي نفس التطبيق زرار «احفظ الأوردر» متوصّل بـ mergeMap. في لوج أسبوع واحد: ١٤١٢ دوسة على الزرار طلّعت ١٧٣١ طلب POST — يعني ٣١٩ أوردر مكرر في الداتابيز، كلهم من ناس دوست مرتين لأن الزرار «مردّش بسرعة».

الأربع operators دول بيعملوا نفس الحاجة بالظبط: بياخدوا قيمة من stream خارجي، بيحوّلوها لـ observable جوّاني (طلب HTTP مثلاً)، وبيفرّدوا نتايجه في الـ stream الخارجي. الاختلاف الوحيد بينهم هو سياسة التعامل مع التزامن — إيه اللي يحصل لما trigger جديد يوصل والجوّاني لسه شغّال.
لو مش فاهم الدرس ده: هتكتب bugs مبتظهرش على جهازك أبداً — لأن الـ API عندك بيرد في ٢٠ ملي ثانية فمفيش تداخل أصلاً. هتظهر بس في الإنتاج على شبكة بطيئة: نتايج بحث قديمة بتكتب فوق الجديدة، أوردرات مكررة، وطلبات بتتكدّس على المتصفح لحد ما يقف.
2

الفكرة في صورة: يعني إيه «flattening» أصلاً؟

كل كورة في الأعلى = قيمة من الـ stream الخارجي (دوسة زرار، حرف اتكتب، تغيّر في route param). الـ fn بتحوّلها لـ observable جوّاني — فلو سِبتها كده هيبقى عندك Observable<Observable<T>>، وده اللي الـ flattening بيحلّه: بيعمل subscribe على الجوّاني وبيطلّع قيمه على الشريط اللي تحت مباشرةً.

الحتة المهمة: «flattening» مش بس فرد — هو كمان إدارة الـ subscriptions الجوّانية. والأربعة بيختلفوا في نقطة واحدة: لما كورة جديدة تنزل والجوّاني القديم لسه مفتوح، مين يعيش ومين يموت.
3

مثال واقعي من شغلك

أ. البحث أثناء الكتابة — switchMap

❌ nested subscribe
this.search.valueChanges.subscribe(q => {
  this.api.search(q).subscribe(r => {
    this.results = r;   // مين رد الأخير؟ مش إنت
  });
});
// 5 حروف = 5 طلبات، والنتيجة النهائية
// بتاعة أبطأ رد مش أحدث حرف
✅ switchMap
this.results$ = this.search.valueChanges.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => this.api.search(q))
);
// 5 حروف ≈ طلب واحد بعد الـ debounce،
// وأي طلب سابق بيتعمله unsubscribe → XHR abort

في قياس على شبكة Fast 3G: من ٥ طلبات و٩٠٠ ms لآخر رسم صحيح، لـ ١ طلب و٣٢٠ ms — والأهم إن الرد القديم بقى مستحيل يكتب فوق الجديد.

ب. زرار الحفظ — exhaustMap مش switchMap

// ❌ switchMap على كتابة: الدوسة التانية بتعمل abort للأولى —
// بس الإلغاء client-side! الطلب ممكن يكون وصل السيرفر واتنفّذ،
// وإنت بس رميت الرد. أوردر اتعمل والمستخدم شايف إنه فشل.
this.save$ = this.clicks$.pipe(switchMap(() => this.api.save(order)));

// ✅ exhaustMap: الأول بيكمّل، وأي دوسة وهو شغّال بتتطنش
this.save$ = this.clicks$.pipe(
  exhaustMap(() => this.api.save(order)),
  takeUntilDestroyed(this.destroyRef)
);
// نفس أسبوع اللوج: 1412 دوسة → 1412 POST، صفر تكرار

ج. رفع ملفات — mergeMap بسقف

// ❌ من غير سقف: 50 ملف = 50 طلب مرة واحدة.
// المتصفح بيسمح بـ ~6 اتصالات للـ host الواحد → الباقي في طابور
// جوّه المتصفح، وبيزحم أي طلب تاني في الصفحة كلها.
from(files).pipe(mergeMap(f => this.api.upload(f)));

// ✅ سقف صريح — 4 بالتوازي وبس
from(files).pipe(mergeMap(f => this.api.upload(f), 4));

د. كتابات لازم تتنفّذ بالترتيب — concatMap

// ترتيب العناصر بالسحب: كل حركة PATCH لازم توصل بترتيبها،
// وإلا الترتيب النهائي في السيرفر غير اللي على الشاشة
this.reorder$.pipe(
  concatMap(move => this.api.patchOrder(move))
);
// التمن: لو الشبكة بطيئة الطابور بيطوّل — concatMap بيأخّر، مبيرميش
5

غلطات بتحصل كتير

  • «switchMap هو الافتراضي في كل حاجة» — صح للقراءات، كارثة للكتابات. الإلغاء client-side: الـ XHR بيتقفل عندك، لكن السيرفر ممكن يكون نفّذ الطلب خلاص. يبقى عندك كتابة حصلت وإنت رميت ردّها.
  • mergeMap من غير سقف — ١٠٠ عنصر = ١٠٠ طلب في نفس اللحظة. حد الـ ٦ اتصالات لكل host بيحوّلها لطابور مخفي بيعطّل الصفحة كلها. اكتب الرقم: mergeMap(fn, 4).
  • subscribe جوّه subscribe — مش بس شكل وحش: الجوّاني ملوش أي علاقة بالخارجي، فلا بيتلغي ولا بيترتّب ولا الأخطاء بتوصل للـ pipe. ده بالظبط اللي الـ flattening اخترع عشانه.
  • concatMap على البحث — بيحافظ على الترتيب فعلاً، بس بيحط كل حرف في طابور. المستخدم خلّص كتابة والنتايج لسه بتوصل واحدة ورا التانية من حروف قديمة.
  • exhaustMap من غير timeout — لو الطلب الأول علّق ومرجعش أبداً، الباب فضل مقفول والزرار مات لحد ما المستخدم يعمل refresh. حط timeout(15000) وcatchError جوّه الـ observable الجوّاني عشان الـ pipe الخارجي ميموتش.
6

اختبر نفسك

1. ليه switchMap هو الصح في البحث أثناء الكتابة؟
الـ bug الأزلي في الـ typeahead هو وصول الردود بترتيب مقلوب. سياسة «الأحدث بس» بتحل ده هيكلياً مش بشرط if على آخر قيمة.
2. زرار submit متوصّل بـ mergeMap. المستخدم المستعجل يقدر يعمل إيه؟
merge بيشغّل كل trigger بالتوازي. في كتابة مش idempotent ده تكرار بالتصميم. exhaustMap هو الحل في الفرونت، و idempotency key في السيرفر هو الحزام التاني.
7

الخلاصة في ٣ نقاط

  1. الأربعة بيعملوا نفس التحويل، والفرق الوحيد سياسة التزامن: switchMap يلغي، mergeMap يوازي، concatMap يطوّر في طابور، exhaustMap يطنش.
  2. قاعدة الجيب: قراءات → switchMap (الرد القديم أخطر من الإلغاء)، كتابات → exhaustMap للأزرار أو concatMap لما كله لازم يحصل بترتيبه، وmergeMap بسقف للفان-أوت المستقل.
  3. إلغاء الـ switchMap بيقفل الـ subscription عندك بس — مش ضمان إن السيرفر ما نفّذش، فخلي الكتابات محمية من ناحيتين: الـ operator الصح + idempotency في الـ API.
