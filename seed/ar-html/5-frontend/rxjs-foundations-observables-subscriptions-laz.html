الـ Observable وصفة مش أكلة — ومحدش بيطبخ غير لما تعمل subscribe

RxJS Foundations: Observables, Subscriptions, Laziness
1

ليه الدرس ده مهم؟

موقف حقيقي: زر «حفظ» في شاشة Angular. كتبت this.http.post('/api/orders', order) وخلاص. الشاشة مبتعملش error، الـ console نضيف، الـ ASP.NET Core logs مفيهاش أي request — والأوردر مش بيتحفظ. مفيش bug في الـ API خالص، إنت بس عملت الوصفة وما طبختهاش.

وموقف تاني: جدول بيستخدم {{ orders$ | async }} في مكانين في نفس الـ template (مرة للعدّاد ومرة للصفوف). تبويب الـ Network بيقول request-ين لنفس الـ endpoint، ٢ × ١٨٠ ملي ثانية و٢ × نفس الـ payload. ولا حلقة for ولا استدعاء مكرر في الكود — السبب إن الـ observable cold، فكل subscribe بيشغّل الوصفة من الأول.

الـ Observable = stream كسول من ٠ لما لا نهاية قيمة على مدى الزمن، ينفع تلغيه. الـ Promise بيشتغل لحظة ما تعمله وبيرجع قيمة واحدة ومش بيتلغي. الفرق مش تفصيلة في الـ API — هو اللي بيحدد إمتى الشغل بيحصل وكام مرة.
لو مش فاهم الدرس ده: هتكتب عمليات حفظ مبتتنفذش بصمت، هتضاعف طلبات الـ HTTP من غير ما تعرف، وأول ما الـ API يرجّع ٥٠٠ مرة واحدة هتلاقي خانة البحث ميتة للأبد وانت فاكر إن الـ debounceTime هو السبب.
2

الفكرة في صورة: الـ subscribe هو اللي بيولّع النار

الترتيب ده هو كل الدرس: الاشتراك بيسبق الإنتاج. قبل الـ subscribe الـ observable مجرد object فيه دالة مستنية حد ينداها. عشان كده http.post(...) لوحده مش request، وinterval(1000) لوحده مش تايمر شغّال.

جرّب بنفسك: cold مقابل shareReplay

دوس subscribe() كذا مرة وبصّ على عدّاد الطلبات. بعدين شغّل shareReplay(1) واعمل reset وكرّر — نفس عدد المشتركين، طلب واحد.

cold — unicast
🌐 طلبات HTTP: 0 👥 مشتركين: 0

الوضع الحالي: كل مشترك جديد = تنفيذ جديد للوصفة = طلب HTTP جديد.

shareReplay(1) الافتراضي معناه { bufferSize: 1, refCount: false } — يعني بيشترك في المصدر مرة واحدة، بيحتفظ بآخر قيمة ويعيدها لأي مشترك جديد، ومبيفصلش لما عدد المشتركين يرجع صفر. لو عايزه يفصل ويعيد الطلب بعد كده استخدم shareReplay({ bufferSize: 1, refCount: true }).
5

مثال واقعي من شغلك

أ. نفس الـ observable في مكانين في الـ template

❌ request-ين — ٢ × ١٨٠ ms، ٢ × payload
// component
orders$ = this.http.get<Order[]>('/api/orders');

// template: async pipe مرتين = اشتراكين = تنفيذين
// <span>{{ (orders$ | async)?.length }}</span>
// <tr *ngFor="let o of orders$ | async">
✅ request واحد — ١٨٠ ms، والتاني من الكاش
orders$ = this.http.get<Order[]>('/api/orders').pipe(
  shareReplay(1)
);

// نفس الـ template بالظبط — الاشتراك التاني
// بياخد آخر قيمة محفوظة من غير أي شبكة

نفس الـ markup بالحرف. الفرق سطر واحد، والنتيجة نصّ زمن التحميل ونصّ الحمل على الـ API.

ب. الحفظ اللي «مش بيشتغل»

// ❌ صفر requests — الوصفة اتعملت وما حدش طبخها
save() {
  this.http.post('/api/orders', this.form.value);
}

// ✅ الاشتراك هو اللي بينفّذ. takeUntilDestroyed عشان الإلغاء لو الشاشة اتقفلت
private destroyRef = inject(DestroyRef);

save() {
  this.http.post('/api/orders', this.form.value)
    .pipe(takeUntilDestroyed(this.destroyRef))
    .subscribe(() => this.router.navigate(['/orders']));
}

ج. أخطر تفصيلة: مكان الـ catchError

❌ خانة بحث بتموت بعد أول فشل
results$ = this.query$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => this.api.search(q)),
  catchError(() => of([]))   // برّه
);
// أول 500 من الـ API → الـ error حدث نهائي
// للـ stream الخارجي → الاشتراك يتقفل
// والكتابة بعد كده مبتعملش أي حاجة
✅ الفشل بيضحّي بطلب واحد بس
results$ = this.query$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap(q => this.api.search(q).pipe(
    catchError(() => of([]))  // جوّه
  ))
);
// الـ inner observable هو اللي بيموت ويترجم لـ []
// والـ stream الخارجي خالد
stream: alive

اكتب حرفين، بعدين خلي واحد يفشل، وشوف الفرق بين المكانين.

6

غلطات بتحصل كتير

  • استدعاء http.post/put/delete من غير subscribe — صفر requests وصفر أخطاء. لو محتاج تعامله كـ Promise استخدم firstValueFrom()، بس الاشتراك لازم يحصل بشكل أو بتاني.
  • الاعتماد على إن الـ observable «القيمة» — هو الوصفة. اشتراكين = تنفيذين. لو عايز تنفيذ واحد مشترك بينهم استخدم shareReplay، ولو عايز الـ template يقرا من مكان واحد خزّنه في signal.
  • catchError على الـ stream الخارجي — بيمسك الخطأ مرة واحدة وبعدها الاشتراك مقفول نهائياً. حطه جوّه الـ switchMap عشان البلاست radius يبقى طلب واحد.
  • نسيان إن الـ error حدث نهائي — بعد error مفيش next تاني ومفيش complete. فـ «الـ stream بيرجع لوحده» مش موجود إلا لو استخدمت retry أو retryWhen صراحةً.
  • الخوف الزايد من الـ unsubscribe في HTTP — الـ HTTP observable بيطلّع قيمة وبيكمّل، والـ complete بيفكّ الاشتراك لوحده. اللي بيسرّب فعلاً هو اللي عمره ما بيكمّل: interval، fromEvent، الـ stores، الـ WebSocket.
7

اختبر نفسك

1. سطر this.http.post('/api/orders', o); لوحده من غير .subscribe() — بيحصل إيه؟
الـ cold observable وصفة، والـ subscribe هو «اطبخ». الحفظ اللي مبيتبعتش بصمت ده أشهر خطأ في أول شهور RxJS.
2. خانة بحث بتوقف عن الشغل للأبد بعد أول فشل من الـ API. السبب؟
الـ error بيمشي على السلسلة كلها وينهي الاشتراك. لما تتعامل معاه جوّه الـ inner observable، اللي بيموت هو الطلب الواحد بس والـ stream الخارجي يفضل حيّ.
8

الخلاصة في ٣ نقاط

  1. الـ Observable وصفة كسولة: مفيش أي شغل بيحصل قبل الـ subscribe، فاستدعاء من غير اشتراك = صفر تنفيذ.
  2. الـ cold observable بيعيد تنفيذ نفسه لكل مشترك — فاشتراكين على نفس http.get = request-ين، وshareReplay(1) بيرجّعهم واحد.
  3. العقد next* ثم (complete أو error): الـ error نهائي وبيقتل الاشتراك، فحطّ الـ catchError جوّه الـ switchMap عشان الـ stream الخارجي يعيش.
