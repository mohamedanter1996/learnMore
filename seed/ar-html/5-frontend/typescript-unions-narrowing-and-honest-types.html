TypeScript: Unions, Narrowing, and Honest Types
1

ليه الدرس ده مهم؟

عندك كمبوننت عرض طلبات في Angular فيها التلاتة الكلاسيك: loading: boolean، error: string | null، orders: Order[]. جالك تيكيت من الـ QA: «الشاشة بتوري الـ spinner ورسالة الخطأ مع بعض». دخلت على الكود، لقيت مسار واحد بيسيب loading = true وهو بيحط الـ error.

التلات حقول دول بيسمحوا بـ ٨ تركيبات (2×2×2). منهم ٤ بس ليهم معنى. الأربعة الباقيين مش ممنوعين من الـ compiler — ممنوعين بانضباطك إنت وإنت بتكتب. وده بيفشل.

الحل إنك تقلب الحالة من تلات حقول مستقلة لـ شكل واحد من تلاتة — discriminated union. كل حالة شايلة داتاها هي بس، والـ compiler بعد كده بيضيّق النوع لوحده (narrowing) فيعرف إن data موجودة في حالة 'loaded' بس.
لو مش فاهم الدرس ده: هتفضل تكتب ! و?. في كل سطر عشان تسكّت الـ compiler، وهتعمل as على كل response جاي من الـ API، وأول ما تضيف حالة جديدة ('refreshing' مثلاً) الشاشة هتفضل تشتغل غلط من غير أي compile error، وهتكتشفها من تيكيت.
2

الفكرة في صورة: الـ discriminant هو البوابة

الفكرة كلها إن فيه حقل واحد نوعه literal type ('loading' | 'error' | 'loaded') مشترك بين كل الأشكال. أول ما تقارنه بقيمة، TypeScript بيشيل الأشكال اللي مستحيل تكون هي، وده اللي بيخلي state.data يبقى مسموح جوّه فرع 'loaded' ومرفوض بره.

4

مثال واقعي: كمبوننت طلبات في Angular

أ. قبل — تلات حقول مستقلة

export class OrdersComponent {
  loading = false;
  error: string | null = null;
  orders: Order[] = [];

  load(): void {
    this.loading = true;
    this.api.getOrders().subscribe({
      next: o => { this.orders = o; this.loading = false; },
      error: e => { this.error = e.message; }   // ← نسي loading = false
    });
  }
}
<!-- والتمبليت بيداري على الفجوة -->
@if (loading) { <app-spinner /> }
@if (error) { <p class="err">{{ error }}</p> }
@if (!loading && !error && orders?.length) { ... }
<span>{{ orders?.[0]?.total }}</span>
التمبليت ده فيه ٣ أماكن بتستخدم ?. عشان تعدّي الـ strictNullChecks، وشرط مركّب من تلات نفيات عشان يعبّر عن حالة واحدة. والبَج اللي فوق (spinner + error مع بعض) مفيش حاجة في النوع تمنعه.

ب. بعد — اتحاد واحد، وكل حالة شايلة داتاها

type OrdersState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'loaded'; orders: readonly Order[] };

export class OrdersComponent {
  private readonly destroyRef = inject(DestroyRef);
  readonly state = signal<OrdersState>({ status: 'idle' });

  load(): void {
    this.state.set({ status: 'loading' });
    this.api.getOrders()
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe({
        next: orders => this.state.set({ status: 'loaded', orders }),
        error: (e: HttpErrorResponse) => this.state.set({ status: 'error', message: e.message })
      });
  }
}
<!-- @let بيخزن القيمة في مرجع ثابت، فالـ narrowing بيشتغل جوّه الـ switch -->
@let s = state();

@switch (s.status) {
  @case ('idle')    { <button (click)="load()">تحميل</button> }
  @case ('loading') { <app-spinner /> }
  @case ('error')   { <p class="err">{{ s.message }}</p> }
  @case ('loaded')  { <app-order-table [rows]="s.orders" /> }
}
الفرق المقاس على نفس الكمبوننت: التركيبات الممكنة من ٨ لـ ٤ (وكلهم بمعنى)، الـ ?. من ٣ لـ صفر، والشرط المركّب من تلات نفيات بقى @case واحد. والحالة الرابعة ('idle') — اللي الـ booleans كانت بتخبّيها جوّه «كله false» — بقت ظاهرة ومكتوبة.

ج. الحماية من المستقبل: exhaustiveness check

function label(s: OrdersState): string {
  switch (s.status) {
    case 'idle':    return 'جاهز';
    case 'loading': return 'بيحمّل…';
    case 'error':   return s.message;
    case 'loaded':  return `${s.orders.length} طلب`;
    default: {
      const _exhaustive: never = s;   // ضفت 'refreshing'؟ → compile error هنا
      return _exhaustive;
    }
  }
}

السطر ده هو اللي بيحوّل «لازم أفتكر أعدّل كل الـ switches» لـ «الـ build هيوقف ويقولي فين». بلاش default بيرجع قيمة افتراضية ساكتة — ده بيلغى الفايدة.

د. الصدق على الحدود: unknown مش any

// ❌ as = وعد الـ compiler مش قادر يتحقق منه. غيّروا الحقل في الباك إند؟ undefined في الإنتاج.
const orders = (await res.json()) as Order[];

// ✅ تحقّق مرة واحدة على الحد، وبعد كده النوع صادق
const raw: unknown = await res.json();
const parsed = OrderSchema.array().safeParse(raw);
if (!parsed.success) return { status: 'error', message: 'شكل غير متوقع من الـ API' };
return { status: 'loaded', orders: parsed.data };
http.get<Order[]>(url) كمان مش تحقق — ده مجرد generic بيقول للـ compiler «افترض إنها كده». ده مقبول لو إنت صاحب العقد وواعي بالقرار؛ المشكلة لما تفتكره فحص حقيقي.

دي كل القيم اللي الـ { loading, error, orders } بيسمح بيها. الـ union بيسمح بأربعة بس — والأربعة الباقيين مش محتاجين code review، محتاجين type.

5

غلطات بتحصل كتير

  • الـ discriminant نوعه string مش literal — لو كتبت status: string (أو جبتها من interface مولّد بـ string)، مفيش narrowing خالص والـ switch بيبقى تزويق. لازم status: 'loading' | 'error' | … — أو as const على الكائن.
  • الـ narrowing بيضيع بعد نداء دالة — if (this.cache !== null) { refresh(); this.cache.length } بيرفض، لأن this.cache property والـ compiler مش ضامن إن refresh() مغيّرهاش. الحل: const c = this.cache; وبعدين ضيّق على c.
  • استخدام as لإسكات الـ compiler — as مش تحويل، هو إعلان إنك متأكد. كل as نقطة ممكن الإنتاج يخالفك فيها. خليه على الحدود اللي فعلاً عارفها، وضيّق بالـ guards في باقي الكود.
  • any واحد في دالة helper — الـ any بيعدّي: أي حاجة تلمسه تبقى any وتختفي من الفحص بالسكات. لو شكل الداتا مجهول استخدم unknown، بيجبرك تتحقق قبل أي استخدام.
  • رشّ ! و?. على كل سطر — كل ! هو اعتراف إن النوع بيقول حاجة وإنت بتقول غيرها. عادةً العلاج إنك تصلّح الـ type (union) مش إنك تسكّت الرسالة. ونفس الكلام على default: بيرجع قيمة افتراضية بدل const _exhaustive: never = s — كده إضافة حالة جديدة تمر بسلام وتظهر في الإنتاج كـ UI فاضي.
6

اختبر نفسك

1. ليه الـ discriminated union أحسن من كائن بحقول optional؟
النوع نفسه بيفرض إن كل حالة شايلة داتاها هي بس — فعيلة bugs كاملة بتتشال وقت الـ compile. الـ union مالهوش أي أثر وقت التشغيل أصلاً؛ الكسب كله في وقت الـ build.
2. عندك state: { status: 'loading' } | { status: 'error'; message: string } | { status: 'loaded'; data: Order[] }، وكتبت if (state.status !== 'loading') { … }. جوّه الـ block، تقدر تقرا state.message مباشرة؟
الـ narrowing بيشيل شكل واحد بس. المسموح دايماً = تقاطع خصائص الأشكال اللي لسه ممكنة، فمحتاج شرط تاني (=== 'error' أو 'message' in state) توصل لـ message.
7

الخلاصة في ٣ نقاط

  1. حقول مستقلة بتضاعف الحالات الممكنة (2ⁿ) وأغلبها مالهوش معنى — الـ discriminated union بيسيب الحالات الصح بس موجودة في النوع.
  2. الـ narrowing بيدّيك الوصول للداتا بالمجان جوّه كل فرع، والـ never في الـ default بيخلي أي حالة جديدة تكسر الـ build مش الإنتاج.
  3. على حدود النظام استخدم unknown وتحقّق مرة واحدة؛ كل as أو any أو ! هو وعد الـ compiler مش قادر يراجعه.
