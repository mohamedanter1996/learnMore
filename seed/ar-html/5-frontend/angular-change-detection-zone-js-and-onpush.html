Angular مبيعرفش إن حاجة اتغيرت — هو بيسأل الشجرة كلها

Angular Change Detection: Zone.js and OnPush
1

ليه الدرس ده مهم؟

عندك شاشة OrdersList فيها ٥٠٠ صف، وكل صف بيعرض {{ fmt(row.total) }}. بتكتب في خانة البحث فوق فتلاقي الكتابة بتتهتك. تفتح Angular DevTools → profiler تلاقي دورة الـ change detection الواحدة بتاخد ١١ ملي ثانية، وكل حرف بتكتبه بيولّد ٣ دورات (keydown، keypress، input) = ٣٣ ملي ثانية لكل ضغطة زرار. الـ frame بتضيع.

السبب مش في خانة البحث — السبب إن zone.js عامل patch لكل API غير متزامن (أحداث، setTimeout، promises، HTTP). أي واحد منهم بيخلص، Angular بيفترض «يمكن حاجة اتغيرت» وبيمشي على شجرة الـ components كلها يعيد تقييم كل binding. هو مش عارف إيه اللي اتغير — هو بيسأل الكل.
لو مش فاهم الدرس ده: هتحط دوال في الـ templates وهي بتتنفذ آلاف المرات في الثانية، وهتحط OnPush على component وتستغرب ليه الشاشة واقفة بعد items.push(x)، وهتحل المشكلة بـ setTimeout أو detectChanges() في أماكن عشوائية بدل إنك تفهم مين بيعلّم مين dirty.
2

الفكرة في صورة: zone.js بيزنّ الجرس

عشان كده دورة الفحص بتتشغّل على حاجات ملهاش أي علاقة بشاشتك: حركة ماوس، analytics، setInterval لـ polling. والفحص نفسه معناه إعادة تقييم كل تعبير في كل template — ولو التعبير دالة، الدالة بتتنفذ من أول وجديد.

قاعدة رقم صفر مهما كانت استراتيجيتك: تعبيرات الـ template لازم تكون رخيصة و pure. {{ calculateTotal() }} بتتنفذ في كل دورة فحص على مستوى التطبيق كله. احسبها في الكلاس، أو computed()، أو pipe نقي.
3

الشجرة على الطبيعة — جرّب بنفسك

اقلب الوضع بين Default وOnPush، وبعدين فجّر حدث من مكان مختلف وبصّ على عداد الفحوصات. الـ components المكتوب عليها OnPush هي SideNav وOrdersList وChartPanel.

التعاقد اللي OnPush بيفرضه: الـ reference

OnPush بيقارن الـ @Input بـ ===. يعني لو عدّلت جوه نفس الـ array أو نفس الـ object، الـ reference ما اتغيرش → الفحص بيتخطّى → الشاشة بايتة. دوس بنفسك:

الحقيقة جوه الكلاس (this.items)

اللي المستخدم شايفه على الشاشة

push بيسيب نفس الـ reference → الـ component OnPush مش بياخد باله → الشاشة بايتة من غير أي error. ده أشهر bug في OnPush.
بديل واحد من اتنين: استبدل الـ reference ([...items, x])، أو قول لـ Angular صريح markForCheck(). الأول أنضف لأنه بيحافظ على التعاقد مش بيلفّ عليه.

مثال واقعي من شغلك

أ. جدول ٥٠٠ صف — دالة في الـ template

❌ قبل — Default CD + دالة في binding
@Component({
  template: `<tr *ngFor="let r of rows">
     <td>{{ fmt(r.total) }}</td></tr>`
})
export class OrdersList {
  fmt(v: number) { return new Intl.NumberFormat('ar-EG').format(v); }
}
// 500 نداء × 3 دورات لكل حرف = 1,500 نداء/ضغطة
// profiler: 11 ms لكل دورة فحص
✅ بعد — OnPush + قيمة محسوبة مرة واحدة
@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: `<tr *ngFor="let r of rows()">
     <td>{{ r.totalText }}</td></tr>`
})
export class OrdersList {
  rows = computed(() => this.raw().map(mapRow));
}
// الكتابة في خانة البحث مبقتش تفحص الجدول خالص
// profiler: 0.4 ms لكل دورة

computed() بيحسب لما المصدر يتغير بس، وOnPush بيمنع الدورات اللي مالهاش علاقة. الاتنين مع بعض — مش واحد منهم.

ب. شغل مش UI جوه الـ zone = عاصفة فحص

// ❌ 60 حركة ماوس في الثانية = 60 دورة فحص للتطبيق كله
window.addEventListener('mousemove', e => this.track(e));

// ✅ بره الـ zone: صفر دورة فحص، وبترجع جوه بس لما تحتاج ترسم
private zone = inject(NgZone);
private cdr = inject(ChangeDetectorRef);

ngOnInit() {
  this.zone.runOutsideAngular(() => {
    window.addEventListener('mousemove', e => this.track(e));
    setInterval(() => this.poll(), 500);
  });
}

onResultReady(v: Result) {
  this.result = v;
  this.cdr.markForCheck();   // لازم — إحنا بره الـ zone
}

ج. الاتجاه الحديث: signals بتقلب السؤال

// zone.js بيسأل: «حاجة حصلت؟ طيب افحص الكل»
// signals بتقول:  «القيمة دي اتغيرت، ودول المستهلكين بتوعها»

export const appConfig: ApplicationConfig = {
  providers: [provideZonelessChangeDetection()]   // بدون zone.js خالص
};
في الكود الجديد: signals + OnPush في كل حتة هو الوضع الافتراضي. zone.js بقى كوبري توافق مع الكود القديم اللي بيعدّل حالة من غير ما يبلّغ حد.
7

غلطات بتحصل كتير

  • items.push(x) مع OnPush — نفس الـ reference، فالفحص بيتخطّى والشاشة بايتة من غير أي رسالة خطأ. استبدل الـ reference أو نادي markForCheck().
  • تعديل جوه object جاي كـ @Input — filter.status = 'Open' مش بس مش بيرسم، كمان ngOnChanges مش بتتنادى خالص، لأنها بتقارن references.
  • الخلط بين markForCheck() وdetectChanges() — markForCheck بيعلّم الطريق من الـ component لحد الـ root dirty عشان الدورة الجاية تشوفه. detectChanges بيفحص الـ view ده وولاده فوراً ولوحدهم. الأول هو اللي عايزه في ٩٠٪ من الحالات.
  • subscribe يدوي جوه component OnPush — بتحدّث field جوه الـ subscribe والشاشة مش بتتغير. استخدم async pipe أو signal، أو نادي markForCheck() بعد التحديث.
  • runOutsideAngular وبعدين تحدّث الحالة وتنسى ترجع — الكود بيشتغل صح والشاشة ساكتة. ارجع بـ zone.run(...) أو علّم بـ markForCheck().
8

اختبر نفسك

1. قايمة في component OnPush مش بتتحدث بعد this.items.push(newItem) — السبب:
تعاقد OnPush هو الـ immutability: استبدل الـ reference ([...items, x]) عشان مقارنة === تشوف التغيير.
2. نداء دالة جوه binding في الـ template خطر في الوضع الافتراضي لأن:
Angular ميقدرش يعرف إن نتيجة الدالة اتغيرت غير لما ينادي الدالة — فالدالة الغالية بتبقى ضريبة على كل دورة.
9

الخلاصة في ٣ نقاط

  1. zone.js بيبلّغ Angular إن «حاجة async خلصت» بس — فالوضع الافتراضي بيفحص الشجرة كلها على أي حدث في أي مكان.
  2. OnPush بيقطع فروع كاملة من الفحص، وتمنه إن تعديلاتك تبقى باستبدال reference مش بتعديل جوه نفس الكائن.
  3. تعبيرات الـ template لازم تكون رخيصة ونقية مهما كانت استراتيجيتك — والـ signals هي الاتجاه اللي بيلغي السؤال من أساسه.
