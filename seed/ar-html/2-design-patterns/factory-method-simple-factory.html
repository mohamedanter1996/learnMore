قرار «أعمل new لمين؟» لازم يعيش في مكان واحد

Factory Method & Simple Factory
1

ليه الدرس ده مهم؟

عندك API فيه إشعارات على ٣ قنوات: Email و SMS و Push. الاختيار بين التلاتة متكرر بـ if/else في ٧ ملفات — كنترولر، ويب هوك، background job، إلخ. جالك ريكوست: «ضيف WhatsApp». فتحت ٧ ملفات، نسيت واحد، والـ bug طلع في الإنتاج بعد أسبوع.

ونفس الحكاية بشكل أخطر مع new HttpClient() جوّه كل request handler: على ٢٥٠ request/ثانية بتفضل تفتح sockets جديدة، وكل socket بيقعد في TIME_WAIT حوالي ٢٤٠ ثانية — فبتوصل لآلاف الـ sockets المفتوحة ويرجعلك SocketException والـ p99 يطلع من ٤٠ms لتايم أوت.

الحل في الحالتين واحد: مركزية قرار الإنشاء. الـ caller يقول «عايز INotifier للقناة دي» ومايعرفش ولا يهمّه الكلاس الملموس اللي هيتعمله ولا إزاي بيتبني.
لو مش فاهم الدرس ده: هتفضل تنسخ نفس الـ switch في كل حتة، وكل نوع جديد هيلمس نص المشروع، وهتقع في new HttpClient() اللي بيستهلك الـ sockets وبيمسك DNS قديم، وهتلاقي الـ dependencies بتاعة الكلاسات بتتبني بالإيد بدل ما تيجي من الـ DI.
2

الفكرة في صورة

على الشمال الأنواع الملموسة، على اليمين الأماكن اللي بتطلبها. الفرق كله في: مين اللي عارف مين.

في الحالة الأولانية كل caller مربوط بـ كل نوع ملموس (٣ × ٣ = ٩ خيوط). في الحالة التانية كل caller مربوط بخيط واحد بس للـ factory، والـ factory هو الوحيد اللي عارف الأنواع. ده هو المكسب: عدد الخيوط بيبقى n + m بدل n × m.

مثال واقعي من شغلك

أ. الـ Simple Factory — الشغال اليومي (مش من GoF)

❌ قبل — نفس الـ switch متكرر في ٧ ملفات
// OrdersController.cs
INotifier n = channel switch
{
  Channel.Email => new EmailNotifier(_smtp, _log),
  Channel.Sms   => new SmsNotifier(_twilioKey),
  _             => new PushNotifier(_fcm)
};
n.Send(msg);
// ونفس الكلام في PaymentWebhook.cs …
✅ بعد — القرار في مكان واحد، والـ DI شغّال
public sealed class NotifierFactory(IServiceProvider sp)
{
  public INotifier Create(Channel channel) => channel switch
  {
    Channel.Email => sp.GetRequiredService<EmailNotifier>(),
    Channel.Sms   => sp.GetRequiredService<SmsNotifier>(),
    Channel.Push  => sp.GetRequiredService<PushNotifier>(),
    _ => throw new ArgumentOutOfRangeException(nameof(channel))
  };
}

مهم: الـ factory مش بيعمل new بإيده — بيسأل الـ IServiceProvider، فكل notifier لسه بياخد الـ dependencies بتاعته (logger، options، HttpClient) من الـ DI عادي.

وفي .NET 8 فيه اختصار جاهز للحالة دي، الـ keyed services:

builder.Services.AddKeyedScoped<INotifier, EmailNotifier>("email");
builder.Services.AddKeyedScoped<INotifier, SmsNotifier>("sms");

// جوّه أي service
public OrderService([FromKeyedServices("email")] INotifier notifier) { }
// أو ديناميكي: sp.GetRequiredKeyedService<INotifier>(key)

ب. الـ Factory Method الأصلي (GoF) — القرار بالوراثة

public abstract class ReportExporter
{
  public byte[] Export(ReportData data)     // الخوارزمية ثابتة هنا
  {
    var writer = CreateWriter();          // ← الـ factory method
    writer.WriteHeader(data.Title);
    writer.WriteRows(data.Rows);
    return writer.GetBytes();
  }
  protected abstract IReportWriter CreateWriter();
}

public class PdfExporter : ReportExporter
{
  protected override IReportWriter CreateWriter() => new PdfWriter();
}
الفرق في سطر: الـ Simple Factory بيقرر بـ switch جوّه method واحدة، والـ Factory Method بيسيب القرار لكلاس وارث بيعمل override — من غير ما تلمس الخوارزمية الأصلية. الأول أسهل، والتاني بيدّيك امتداد من غير تعديل (Open/Closed).

ج. الـ factories اللي إنت مستخدمها من غير ما تاخد بالك

// ❌ كل request بيفتح sockets جديدة → TIME_WAIT وSocketException
using var http = new HttpClient();
var res = await http.GetAsync(path);   // p99 بيطلع من 40ms لتايم أوت

// ✅ الـ factory بيعمل pooling للـ handlers وconfig مركزي بالاسم
builder.Services.AddHttpClient("payments", c =>
{
  c.BaseAddress = new Uri(cfg["Payments:BaseUrl"]!);
  c.Timeout = TimeSpan.FromSeconds(10);
});

public class PaymentsClient(IHttpClientFactory factory)
{
  public Task<HttpResponseMessage> Charge(...)
    => factory.CreateClient("payments").PostAsync(...);
}

// ونفس الفكرة:
ILoggerFactory.CreateLogger<OrderService>();
IDbContextFactory<AppDbContext>.CreateDbContext();  // لبرّه الـ scope: jobs، Blazor
IHttpClientFactory موجود عشان يدير عمر الـ handler: بيعيد استخدام الاتصالات (فمفيش socket exhaustion) وبيدوّر الـ handler كل دقيقتين (فمفيش DNS قديم). لو مصمّم على static HttpClient واحد، لازم تظبط SocketsHttpHandler.PooledConnectionLifetime بإيدك.

5

غلطات بتحصل كتير

  • Factory بيرجّع نوع ملموس — EmailNotifier Create(...) بدل INotifier. كده الـ caller لسه مربوط بالتفاصيل ومكسبتش حاجة غير سطر زيادة.
  • Factory بيعمل new بإيده جوّه — بيقتل الـ DI: الـ logger والـ options والـ HttpClient بتتبني بالإيد، والـ lifetime بيبوظ. اسأل الـ IServiceProvider أو استخدم keyed services.
  • حقن IServiceProvider في كل كلاس بدل factory بواجهة صريحة — ده service locator، بيخفي الـ dependencies وبيخلي الأخطاء تظهر وقت التشغيل مش وقت الكومبايل.
  • Factory لكل حاجة — لو الإنشاء مفيهوش قرار ولا config ولا pooling، الـ constructor العادي أوضح. الـ factory بيتكتب لما الـ caller مش المفروض يعرف حاجة عشان يبني الحاجة.
  • ‏switch من غير حالة افتراضية — أي قيمة جديدة في الـ enum بترجّع null وتتحول لـ NullReferenceException بعيد عن السبب. ارمي ArgumentOutOfRangeException في مكانها.
6

اختبر نفسك

1. IHttpClientFactory موجود أساساً لأن:
الـ factory بيدير عمر الـ handlers (فمفيش socket exhaustion ولا DNS قديم) وبيجمّع الإعدادات المسمّاة في مكان واحد — دي مكاسب الـ factory الكلاسيكية.
2. إيه الفرق الجوهري بين Simple Factory و Factory Method؟
الـ Factory Method (GoF) بيثبّت الخوارزمية في الكلاس الأب ويسيب خطوة الإنشاء abstract — فالامتداد بيحصل بوراثة من غير تعديل الأصل.
7

الخلاصة في ٣ نقاط

  1. الـ factory بيمركز قرار «أعمل new لمين» في مكان واحد، فالـ caller يعتمد على الواجهة بس.
  2. Simple Factory = switch في method واحدة؛ Factory Method = خطوة إنشاء abstract الابن بيعملها override.
  3. لو الإنشاء محتاج معرفة مش من حق الـ caller (config، شرط، pooling) — اخفيه ورا factory؛ غير كده الـ constructor كفاية.
