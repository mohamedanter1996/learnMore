SOLID II: Open/Closed Principle
1

ليه الدرس ده مهم؟

عندك PaymentService فيه switch على نوع الدفع: فيزا، فودافون كاش، أمازون باي. جه المنتج قال «ضيف انستاباي». إنت هتفتح نفس الملف اللي شغال في الإنتاج من سنتين، تزوّد case، وتعمل ديبلوي. يعني عشان تضيف حاجة جديدة، لمست كود قديم شغال وسليم.

مبدأ الـ OCP بيقول: الكود لازم يبقى مفتوح للإضافة (أقدر أضيف سلوك جديد) ومقفول للتعديل (من غير ما أفتح الكود القديم المتستيست). الوسيلة: abstraction + polymorphism بدل switch بيكبر للأبد.
لو مش فاهمه: كل feature جديدة = رجوع لنفس الملف، ريجرشن في حاجات مالهاش علاقة، merge conflicts دايمة، وملف واحد بيبقى ٨٠٠ سطر ومحدش عايز يقربله.
2

شوف الفرق بعينك

دوس «أضف طريقة دفع» كذا مرة، وبصّ على العداد بتاع «تعديلات في كود قديم» في الناحيتين.

❌ من غير OCP — switch

switch (type) {
}
تعديلات في كود قديم0
ملفات محتاجة إعادة اختبار1

✅ مع OCP — استراتيجيات

IPaymentHandler h = resolve(type);
h.Pay(amount);
— الملف ده مبيتفتحش تاني

ملفات جديدة (بس)0

خطوة بخطوة: إزاي تحوّل الـ switch

4
مثال واقعي بـ ASP.NET Core


// 1) العقد
public interface IPaymentHandler {
    string Method { get; }               // "visa" | "vodafone-cash" | ...
    Task<PaymentResult> PayAsync(Order o);
}

// 2) كل طريقة في ملف لوحدها — إضافة، مش تعديل
public class VisaHandler : IPaymentHandler {
    public string Method => "visa";
    public Task<PaymentResult> PayAsync(Order o) => ...;
}

// 3) التسجيل مرة واحدة في Program.cs
builder.Services.AddScoped<IPaymentHandler, VisaHandler>();
builder.Services.AddScoped<IPaymentHandler, VodafoneCashHandler>();

// 4) الاختيار من غير أي switch
public class PaymentService(IEnumerable<IPaymentHandler> handlers) {
    public Task<PaymentResult> PayAsync(Order o) {
        var h = handlers.FirstOrDefault(x => x.Method == o.Method)
                ?? throw new NotSupportedException(o.Method);
        return h.PayAsync(o);
    }
}

  

    انستاباي جديد؟ ملف جديد InstapayHandler.cs + سطر تسجيل واحد.
    PaymentService متفتحش، والتستات القديمة كلها فضلت خضرا.
  

  

    نفس الفكرة بتتكرر عندك في حتت كتير: قواعد الخصم، مصدّرات التقارير (PDF/Excel/CSV)،
    قنوات الإشعارات (Email/SMS/Push)، وقواعد التحقق. أي switch بيكبر مع كل feature = مرشّح للتحويل.
  






  
5
غلطات بتحصل كتير

  
    
    
  • فهم المبدأ إنه «ممنوع تعديل أي كود» — لأ. إصلاح باج تعديل طبيعي. المقصود: إضافة
      سلوك جديد ماتحتاجش تفتح الكود القديم.
    • 
    
  • Interface لكل كلاس في المشروع — تجريد من غير سبب بيزوّد التعقيد. طبّق OCP على المحاور
      اللي فعلاً بتتغير كل شوية (طرق الدفع، قواعد التسعير).
    • 
    
  • نسيان التسجيل في الـ DI — الكلاس الجديد متعرّفش لوحده. سطر AddScoped جزء من الحل
      (أو Scrutor يسجّل كل اللي بيطبّق الواجهة أوتوماتيك).
    • 
    
  • switch واحد باقي في الـ factory — ده مقبول ومتمركز في مكان واحد، لكن الأنضف
      إن الـ DI هو اللي يجمّع كل الـ handlers.
    •

اختبر نفسك


  

    
1. أضفت InstapayHandler جديد وسجلته في DI من غير ما تفتح PaymentService. ده إيه؟

    
    
    
    
سلوك جديد اتضاف من غير ما الكود القديم المتستيست يتفتح — ده جوهر المبدأ.

  


  

    
2. إمتى الـ switch يفضل مقبول؟

    
    
    
    
المبدأ مش حرب على الكلمة المفتاحية. لو الحالات مش بتكبر، الـ switch أبسط وأوضح.
