الـ Singleton مش بترن بتكتبه بإيدك — ده عمر بتسجّله في الـ container

Singleton: The Pattern You Should Rarely Hand-Roll
1

ليه الدرس ده مهم؟

عندك PlanCache في ASP.NET Core بالشكل الكلاسيكي: static Instance وجوّاه lock على كل قراءة. على الورق تمام. في الإنتاج: ٨ requests في نفس اللحظة بيستنوا في طابور على نفس الـ lock، فالـ endpoint اللي كان بيرد في ٦ ملي ثانية بقى بيرد في ٨٠ ملي ثانية تحت الضغط — ومفيش حرف في الكود اتغير.

وفي الـ tests: اختبار واحد لوحده بينجح، و١٢٠ اختبار بالتوازي بيفشلوا بالعشوائي — لأن كلهم بيكتبوا في نفس الـ PlanCache.Instance. وأسوأ سيناريو: singleton بياخد AppDbContext في الـ constructor → ObjectDisposedException من ثاني request.

الفكرة كلها جملة واحدة: خلّي الـ lifetime هو الـ singleton، مش البترن. services.AddSingleton<IPlanCache, PlanCache>() بتديك نفس النسخة الواحدة بالظبط، بس محقونة — باينة في الـ constructor، وقابلة للاستبدال في الـ tests، وعمرها بيتحدد من مكان واحد مش مسمّر في الكلاس.
لو مش فاهم الدرس ده: هتكتب dependencies مخفية مستحيل تعمل لها fake، هتقع في captive dependency وتفضل تدور على سبب الـ ObjectDisposedException، وهتـ«تحلها» بإنك تسجّل الـ DbContext singleton — وده بيحوّل مشكلة واضحة لداتا بايتة وأخطاء concurrency مش بتتكرر وقت الـ debug.
2

الفكرة في صورة: الـ scopes بتيجي وتمشي، والمقبوض عليه فاضل

كل request بيفتح scope ويقفله، والـ scoped services بتتولد وتموت معاه. أما الـ singleton فبيتولد مرة واحدة في الـ root ويعيش لآخر الدنيا. فلو في اللحظة اللي اتولد فيها خد مرجع لحاجة scoped — المرجع ده بيتجمّد عنده: الـ scopes بعد كده بتيجي وتمشي، وهو لسه شادّ في واحدة اتقفلت ومتعملها Dispose. ده اللي اسمه captive dependency.

مثال واقعي من شغلك

أ. نفس الـ cache: lock على كل قراءة مقابل نسخة محقونة lock-free

❌ Singleton بالإيد — طابور على كل قراءة
public sealed class PlanCache
{
  private static readonly Lazy<PlanCache> _i =
      new(() => new PlanCache());
  public static PlanCache Instance => _i.Value;
  private readonly object _gate = new();
  private readonly Dictionary<int, Plan> _map = new();
  private PlanCache() { }

  public Plan Get(int id)
  {
    lock (_gate)                 // كل قراءة تقف في الطابور
      return _map[id];
  }
}
// الاستخدام مدفون جوّه method:
var plan = PlanCache.Instance.Get(id);
// 8 threads × 1M read ≈ 620 ms
✅ Singleton lifetime — محقون وباين
public sealed class PlanCache : IPlanCache
{
  private readonly ConcurrentDictionary<int, Plan> _map
      = new();
  private readonly IDbContextFactory<AppDbContext> _f;
  public PlanCache(IDbContextFactory<AppDbContext> f) => _f = f;

  public async Task<Plan> GetAsync(int id)
  {
    if (_map.TryGetValue(id, out var hit)) return hit;
    await using var db = await _f.CreateDbContextAsync();
    var plan = await db.Plans.FindAsync(id);
    return _map[id] = plan;      // قراءة بدون lock
  }
}
// Program.cs
builder.Services.AddDbContextFactory<AppDbContext>(...);
builder.Services.AddSingleton<IPlanCache, PlanCache>();
// نفس الحمل ≈ 38 ms + 0 allocations على الـ hit

نفس النسخة الواحدة في الحالتين. الفرق: الأولى بتـserialize كل القراءات ومفيش حد يقدر يستبدلها في test، والتانية قراءة lock-free وفي الـ test بتبعت fake للـ constructor وخلاص.

ب. المصيدة: singleton جوّاه scoped

// ❌ captive dependency — AppDbContext عمره scoped
public class PlanCache(AppDbContext db) : IPlanCache { ... }
builder.Services.AddSingleton<IPlanCache, PlanCache>();

// في Development الـ scope validation بترمي عند أول resolve:
// InvalidOperationException: Cannot consume scoped service
// 'AppDbContext' from singleton 'IPlanCache'.

// ✅ لو محتاج DbContext جوّه singleton، افتح scope قصير بإيدك
public class PlanCache(IServiceScopeFactory scopes) : IPlanCache
{
  public async Task<Plan> GetAsync(int id)
  {
    using var scope = scopes.CreateScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
    return await db.Plans.FindAsync(id);
  }
}

// وخلي الفحص ده شغال على طول، مش في Development بس:
builder.Host.UseDefaultServiceProvider(o =>
{
  o.ValidateScopes = true;    // يرمي على القبضة
  o.ValidateOnBuild = true;   // يرمي عند الـ startup مش عند أول request
});

غلطات بتحصل كتير

  • Cache.Instance جوّه method — الـ dependency مخفية تماماً: الـ constructor بيقول إن الكلاس مش محتاج حاجة، والـ test مش لاقية حتة تبدّلها. لو هتسيب static، على الأقل خلّيه يتحقن من الـ constructor.
  • Singleton بياخد AppDbContext — captive dependency: context واحد لكل التطبيق، مش thread-safe، وداتا بايتة في الـ change tracker. الحل IDbContextFactory أو IServiceScopeFactory، مش تحويل الـ context لـ singleton.
  • «الـ Transient جوّه singleton آمن» — غلط. بيتعمله resolve مرة واحدة وقت بناء الـ singleton وبيعيش معاه للأبد، فبقى singleton فعلياً. والأخطر إنه مفيش exception بيحذّرك من ده.
  • double-checked locking بالإيد على field من غير volatile، أو lock (this) / lock (typeof(X)) — أي حد برّا الكلاس يقدر يقفل على نفس الحاجة ويعمل deadlock. Lazy<T> بيعمل ده صح من الأول.
  • state متغيّر static — الـ tests بتبقى مرتبطة بترتيب التشغيل، وتفشل بالتوازي بس. وبعدها تحس إن الحل هو [Collection] وتشغيل تسلسلي، والمشكلة الحقيقية إن الـ state مشترك.
  • إلغاء ValidateScopes في Production (وهي الافتراضية برّا Development) — فالقبضة اللي كان ممكن تظهر كـ exception واضح بتتحول لباج صامت.
6

اختبر نفسك

1. خدمة مسجّلة AddSingleton وبتاخد AppDbContext (scoped) في الـ constructor. الخطر هو:
الـ singleton بيعيش أطول من الـ scope، فبيجمّد نسخة DbContext واحدة لعمر التطبيق: مش thread-safe، داتا قديمة في الـ change tracker، وObjectDisposedException بعد أول request. في Development الـ scope validation بترمي وتنبّهك.
2. سجّلت IClock كـ AddTransient وحقنته في singleton. بيحصل إيه؟
الـ container بيحقن وقت البناء بس. الـ singleton بيتبنى مرة واحدة ⇒ الـ transient بيتولد مرة واحدة ويتمسك للأبد. ومفيش validation على الحالة دي، فلو الكلاس بيحتفظ بـ state ده بيبوظ بصمت. محتاج نسخة جديدة كل مرة؟ احقن Func<IClock> أو factory.
7

الخلاصة في ٣ نقاط

  1. عايز نسخة واحدة؟ سجّل AddSingleton وحقنها — singleton الـ lifetime، مش البترن: نفس النسخة بس باينة في الـ constructor وقابلة للاستبدال.
  2. الـ static Instance تكلفته dependency مخفية وstate مشترك بين الـ tests وlifetime مسمّر في الكود — تلاتة بتوجعك في الصيانة مش في أول يوم.
  3. خدمة ممنوعة تاخد حاجة عمرها أقصر منها: Singleton + Scoped = captive dependency، والحل IDbContextFactory أو scope قصير من IServiceScopeFactory.
