Strategy: Swappable Algorithms
1

ليه الدرس ده مهم؟

عندك CheckoutService بيحسب الخصم. النهارده فيه خصم VIP وخصم كوبون. الشهر الجاي «خصم أول أوردر»، وبعده «خصم الجمعة البيضا»، وبعده «خصم الموظفين». لو كل واحد فيهم if جديد جوّه نفس الميثود، الميثود دي هتوصل ٢٠٠ سطر وكل حساب فاتورة في الشركة بيعدّي عليها.

الـ Strategy بيقلب السؤال: بدل ما الخدمة تسأل «العميل نوعه إيه وأعمل إيه؟»، كل خصم بيبقى كلاس صغير بيرد على سؤالين بس: AppliesTo — أنا ينطبق عليّا؟ وApply — طيب خد الحساب. الخدمة بقت أنبوبة بتمرّر الرقم على اللي ينطبق.
لو مش فاهمه: هتفضل تعدّل نفس الملف كل sprint، والتست بتاع «الخصم القديم» هيقع بسبب فيتشر مالهاش علاقة، ومحدش هيقدر يجرّب خصم لوحده لأنه متلحّم جوّه if.

ده اللي شفته في درس Open/Closed — بس هنا الصورة كاملة: الشكل، البديل الخفيف بالـ delegates، وترتيب التنفيذ اللي بيوقع ناس كتير.

5

الشكل في الكود

// 1) الواجهة: سؤالين بس
public interface IDiscountStrategy {
    bool AppliesTo(Customer c);
    decimal Apply(decimal total);
}

// 2) كل خصم كلاس لوحده — يتقرا لوحده، يتستيست لوحده
public class VipDiscount : IDiscountStrategy {
    public bool AppliesTo(Customer c) => c.IsVip;
    public decimal Apply(decimal total) => total * 0.85m;
}

// 3) الخدمة: بتمرّر الرقم على اللي ينطبق، ومبتعرفش أي اسم
public class CheckoutService(IEnumerable<IDiscountStrategy> strategies) {
    public decimal FinalTotal(Customer c, decimal total) =>
        strategies.Where(s => s.AppliesTo(c))
                  .Aggregate(total, (t, s) => s.Apply(t));
}

// 4) التسجيل — ترتيب التسجيل هو ترتيب التنفيذ
builder.Services.AddScoped<IDiscountStrategy, VipDiscount>();
builder.Services.AddScoped<IDiscountStrategy, CouponDiscount>();
إنت مستخدمه أصلاً: IComparer<T> اللي بتبعته لـ Sort = استراتيجية مقارنة. الـ authentication schemes في ASP.NET Core (JWT مقابل Cookies) = استراتيجيات. الـ output formatters (JSON مقابل XML) = استراتيجيات.

البديل الخفيف: delegate بدل كلاس

var shippingRules = new Dictionary<string, Func<Order, decimal>> {
    ["DHL"]    = o => o.Weight * 2.5m,
    ["Aramex"] = o => o.Weight * 2.0m + 10
};

var cost = shippingRules[order.Carrier](order);
امتى كلاس وامتى delegate؟ كلاس لو الاستراتيجية محتاجة حاجات محقونة بالـ DI (ريبوزيتوري، لوجر، إعدادات) أو ليها تستات خاصة بيها. delegate لو سطر حسابي واحد ومفيش اعتماديات.
6

غلطات بتحصل كتير

  • الاعتماد على ترتيب التسجيل من غير ما تقصده — Aggregate بيمشي بترتيب الـ IEnumerable، يعني ترتيب AddScoped. لو الترتيب مهم فعلاً، حط int Order في الواجهة وOrderBy(s => s.Order) قبل التنفيذ.
  • استراتيجية بتاخد قرارها من نوع العميل بـ if جوّاها — رجّعت الـ switch من الشباك. AppliesTo شرط واحد بسيط، مش شجرة قرارات.
  • نسيان التسجيل في الـ DI — الكلاس موجود والتستات خضرا والخصم مش شغال في الإنتاج، لأن IEnumerable<IDiscountStrategy> مبيشوفش غير المسجّل. (Scrutor بيسجّل الكل أوتوماتيك.)
  • واجهة بتكبر لكل استراتيجية جديدة — لو ضفت ميثود عشان حالة واحدة، الباقي كله هيرمي NotImplementedException. ده كسر لـ Interface Segregation، والحل استراتيجية تانية مش ميثود تانية.
  • كلاس لكل سطر حسابي — تلات كلاسات + تلات تسجيلات عشان weight * 2 تعقيد من غير عائد. الـ Dictionary<string, Func<>> أوضح هنا.
7

اختبر نفسك

1. لما تبعت IComparer<T> لـ List<T>.Sort — ده أنهي pattern؟
الـ Sort بيمسك الخوارزمية الثابتة (الترتيب نفسه)، والـ comparer المحقون هو الجزء المتبدّل — ده Strategy بالظبط.
2. خصمين شغالين مع بعض والناتج بيختلف لما تعكس ترتيب AddScoped. إيه التصرف الصح؟
لو الترتيب جزء من قواعد الشغل، لازم يبقى مكتوب في الكود مش ناتج بالصدفة من ترتيب سطور التسجيل.
8

الخلاصة في ٣ نقاط

  1. Strategy = عيلة خوارزميات ورا واجهة واحدة، والاختيار وقت التشغيل مش وقت الكتابة.
  2. كل استراتيجية بترد على سؤالين: AppliesTo وApply — والخدمة بتمرّر بس.
  3. كلاس لو فيه اعتماديات أو تستات، delegate لو سطر واحد. ولو الترتيب مهم، اكتبه صريح.
