الـ Builder مش «method chaining» — دي تجميعة على مراحل وخطوة واحدة بتقفلها

Builder: Constructing Complex Objects Step by Step
1

ليه الدرس ده مهم؟

عندك Order فيه constructor بـ ٩ parameters: عميل، سطور، خصم، عنوان شحن، عملة، مصدر الطلب، ملاحظات… و٤٠ unit test بينادوه. جالك requirement يضيف CouponCode — فالـ compiler وقّف ٤٠ ملف، وقعدت ساعتين تحط null في كل نداء. وفي نفس الوقت أي حد يقرا test بياخد ٣٠ ثانية يعرف إيه الـ parameter اللي فعلاً بيختبره وسط ٨ قيم مش مهمة.

الـ Builder بيفصل طريقة التجميع عن شكل الكائن النهائي: كائن مؤقت بيشيل الأجزاء خطوة خطوة بـ defaults معقولة، وفي الآخر Build() بتتحقق من الحالة وتطلع المنتج الجاهز. إنت بتستخدمه كل يوم حرفياً: WebApplication.CreateBuilder(args) … إضافات … builder.Build(). وكمان StringBuilder وConfigurationBuilder وHostBuilder وModelBuilder بتاع EF Core.
لو مش فاهم الدرس ده: هتفضل تنسخ constructors طويلة في كل test، وهتسيب كائنات نص مبنية تخرج من الـ service وتوصل للداتابيز من غير أي validation، وهتخلط بين الـ Builder و«أي API بيرجع this» فتكتب Builder لـ DTO بتلات properties وتزوّد كود بلا فايدة.
2

الفكرة في صورة: خط تجميع + خطوة قفل

لاحظ تلات حاجات: الأجزاء بتدخل بأي ترتيب واللي مش بتحدده بياخد default، الحالة المؤقتة قابلة للتغيير (mutable) عن قصد، والمنتج مبيوجدش إلا بعد Build(). الحاجة الوحيدة اللي مش جزء من البترن هي إن كل method ترجّع this — ده شكل كتابة (fluent) مش البترن. بترن الـ Builder = تجميع على مراحل + خطوة تجميع نهائية.

ب. الـ builder نفسه — والـ validation مكانها فين

public class OrderBuilder
{
    private Customer _customer = TestData.DefaultCustomer;
    private readonly List<OrderLine> _lines = [];
    private decimal _discount = 0m;

    public OrderBuilder ForCustomer(Customer c) { _customer = c; return this; }
    public OrderBuilder WithDiscount(decimal pct) { _discount = pct; return this; }

    public OrderBuilder WithLine(string sku, int qty, decimal price)
    { _lines.Add(new(sku, qty, price)); return this; }

    public Order Build()
    {
        // الشرط اللي الكائن نفسه مش مسموح يتخلق من غيره
        if (_lines.Count == 0)
            throw new InvalidOperationException("Order needs at least one line.");

        // نسخة جديدة من السطور — عشان تعديل الـ builder بعد كده ميلمسش المنتج
        return new Order(_customer, _lines.ToList(), _discount);
    }
}
السطر المهم هو _lines.ToList(). لو رجّعت الليستة نفسها، المنتج والـ builder بيشاركوا نفس الـ List — فأول WithLine بعد Build() بتعدّل طلب «خلص» بالفعل. ده bug بيظهر بس لما الـ builder يُعاد استخدامه، يعني في الـ tests الجماعية بالأخص.

ج. نفس العقلية في الـ runtime: StringBuilder

// ❌ كل += بتخلق string جديد وتنسخ اللي قبله
string s = "";
for (int i = 0; i < 10_000; i++) s += "line\n";
// ~500 MB allocations · ~300 ms (تقريبي) — النمو O(n²) في النسخ

// ✅ حالة مؤقتة واحدة بتكبر، وخطوة واحدة في الآخر بتطلّع المنتج
var sb = new StringBuilder();
for (int i = 0; i < 10_000; i++) sb.Append("line\n");
string s2 = sb.ToString();   // ~400 KB allocations · أقل من 1 ms

sb.ToString() هي Build() بالظبط: الحالة المؤقتة mutable وأرخص، والمنتج النهائي immutable وبيتولد مرة واحدة.

غلطات بتحصل كتير

  • Builder لـ DTO بتلات properties — في C# الـ object initializer مع required بيعمل نفس القراءة وبيديك أمان وقت الـ compile. البترن للحالات اللي فيها أجزاء اختيارية كتير أو تجميع لازم يتفحص ككل.
  • إعادة استخدام نفس الـ builder لمنتجين وهو بيرجّع الـ collection بالمرجع — المنتج التاني بيورث سطور الأول. إمّا Build() تاخد snapshot، أو الـ builder يبقى single-use ويرمي لو اتنادى تاني.
  • مفيش validation في Build() — ساعتها الـ builder بقى مجرد طريقة أطول لكتابة constructor. القيمة الحقيقية إن فيه مكان واحد مستحيل تخلق منه كائن ناقص.
  • التعديل على الـ builder بعد Build() وتوقّع إن المنتج يتغير — في ASP.NET Core الـ builder.Services بيبقى read-only بعد builder.Build()، فأي Add... بعدها بترمي InvalidOperationException بدل ما تتجاهلك بصمت.
  • خلط الـ Builder بأي API بيرجع this — الـ chaining شكل كتابة. ولو كتبت builder immutable (كل method ترجّع نسخة جديدة) لازم تستقبل الناتج: b = b.WithLine(...)، وإلا السطر بيروح في الهوا من غير أي error.

اختبر نفسك

1. WebApplication.CreateBuilder(args) … .Build() بيوضّح بترن الـ Builder عشان:
جوهر البترن = تجميع على مراحل + خطوة تجميع نهائية. الـ chaining مجرد تحلية في الكتابة، وstatic أو singleton مالهمش علاقة.
2. إيه الحاجة اللي بتحوّل الـ builder من «constructor أطول» لحاجة فيها قيمة فعلية؟
الـ Build() هي البوابة: بتتحقق من الحالة ككل وبتنسخ الـ collections. من غيرها إنت بس غيّرت شكل نداء الـ constructor.
8

الخلاصة في ٣ نقاط

  1. الـ Builder = حالة مؤقتة mutable بتتجمّع على مراحل بـ defaults معقولة، وBuild() واحدة بتتحقق منها وتطلّع المنتج النهائي.
  2. القيمة في Build() نفسها — validation للحالة ككل و snapshot للـ collections — مش في إن الـ methods بترجّع this.
  3. أعلى مكسب بتاخده منه هو Test Data Builder: كل test بيقول اللي يهمه بس، وتغيير الـ constructor بيتصلح في ملف واحد بدل ٤٠.
