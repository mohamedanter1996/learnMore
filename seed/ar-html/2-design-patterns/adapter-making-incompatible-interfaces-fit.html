Adapter: Making Incompatible Interfaces Fit
1

ليه الدرس ده مهم؟

عندك ASP.NET Core API، وOrderService بينادي TwilioClient مباشرة في ٦ أماكن. الإدارة قررت تنقل لمزود محلي أرخص. عملت grep "Twilio." على الـ solution: ٢٣ ملف بيستوردوا أنواع المزود — فيهم controllers وملفين tests. وفوق ده، الـ unit tests بتاعة OrderService بتاخد ٤.٢ ثانية لأنها بتضرب HTTP حقيقي، وبتفشل عشوائي مرة من كل عشر runs.

الحل مش إنك تعدّل في الـ SDK (مش بتاعك) ولا تعدّل كودك على مزاجهم. كودك بيعرّف الـ port اللي هو محتاجه — ISmsSender — وclass واحد صغير اسمه الـ adapter بيعمل implement للـ port ده وبيلفّ الـ SDK جوّاه ويترجم. نفس فكرة وصلة الكهربا بتاعة السفر: الجهاز ما اتغيرش، الفيشة ما اتغيرتش، الوصلة في النص هي اللي بتترجم.
لو مش فاهم الدرس ده: أنواع المزود هتتسرّب في كل طبقات المشروع، تبديل المزود يبقى عملية جراحية في ٢٣ ملف بدل ملف واحد، والـ tests بتاعتك هتفضل بطيئة ومتقلّبة لأنها مش قادرة تستبدل المزود بـ fake.
2

الفكرة في صورة: النداء رايح، والترجمة في النص

OrderService كودك — شايف الـ port بس
TwilioSmsAdapter : ISmsSender — المترجم
TwilioClient SDK — مكتوب على مزاجهم
SendAsync(phone, message)
SmsDeliveryException ◀ MessageStatus.Failed
النداء بشكل كودك الخطأ مترجم لنوعك

بصّ على الاتجاهين. النداء رايح من اليمين للشمال: OrderService بينادي شكل واحد بس هو SendAsync(phone, message)، والـ adapter بيحوّله لشكل الـ SDK. والخطأ جاي راجع: MessageStatus.Failed بيتحوّل جوّه الـ adapter لـ SmsDeliveryException قبل ما يطلع. الصندوق الشمال ما بيتعدّاش الصندوق اللي في النص أبداً — لا أنواعه ولا exceptions بتاعته. دي حدود الـ adapter.

خطوة بخطوة: إيه اللي بيحصل جوّه الملف ده بالظبط

الشكل بتاعك (الـ port) ↔ الشكل بتاعهم (الـ SDK)
string phone ▶ PhoneNumber to تحويل نوع: الـ port بياخد string عادي، الـ SDK عايز نوعه الخاص.
string message ▶ string body نفس الحاجة باسم مختلف — ترجمة أسماء، أرخص حتة في الـ adapter.
(مش موجود في الـ port) ▶ string from رقم المُرسِل تفصيلة مزود — الـ adapter بيجيبها من IOptions<TwilioOptions>.
Task (بلا قيمة راجعة) ◀ Task<MessageResource> نوع المزود الراجع بيتبلع هنا — لو خرج من الملف ده، الحدود اتخرقت.
SmsDeliveryException ◀ MessageStatus.Failed ترجمة الأخطاء: كودك بيـ catch نوع بتاعه، مش ApiException بتاعتهم.

مثال واقعي من شغلك

أ. قبل: الـ SDK متغلغل في منطق الشغل

public class OrderService(TwilioClient twilio, IConfiguration cfg)
{
    public async Task ConfirmAsync(Order order)
    {
        // منطق business + تفاصيل مزود في نفس الميثود
        var res = await twilio.CreateMessage(
            new PhoneNumber(order.Phone),
            cfg["Twilio:From"],
            $"طلبك {order.Id} اتأكد");

        if (res.Status == MessageStatus.Failed)
            throw new Exception(res.ErrorMessage);   // نوع مزود طالع بره
    }
}
// الـ unit test لازم يضرب HTTP حقيقي  → 4.2 s، وبيفشل 1 من 10 runs
// تبديل المزود → 23 ملف فيهم using Twilio;

ب. بعد: الـ port بتاعك + adapter واحد

// 1) الـ port — الشكل اللي كودك محتاجه فعلاً، مفيش أي كلمة Twilio
public interface ISmsSender
{
    Task SendAsync(string phone, string message, CancellationToken ct = default);
}

// 2) الـ adapter — الملف الوحيد في المشروع اللي يعرف إن Twilio موجودة
public class TwilioSmsAdapter(TwilioClient client, IOptions<TwilioOptions> opt) : ISmsSender
{
    public async Task SendAsync(string phone, string message, CancellationToken ct = default)
    {
        var result = await client.CreateMessage(
            new PhoneNumber(phone), opt.Value.FromNumber, message);

        if (result.Status == MessageStatus.Failed)
            throw new SmsDeliveryException(result.ErrorMessage);   // ترجمة الخطأ
    }
}

// 3) منطق الشغل بقى نضيف — ومبيعرفش حتى اسم المزود
public class OrderService(ISmsSender sms)
{
    public Task ConfirmAsync(Order order) =>
        sms.SendAsync(order.Phone, $"طلبك {order.Id} اتأكد");
}
// الـ unit test بيحقن FakeSmsSender → 0.08 s، صفر شبكة، صفر تقلّب

التبديل كله سطر واحد في Program.cs، وملف adapter جديد. OrderService والـ controllers والـ tests ما اتغيروش ولا حرف — لأنهم أصلاً مش شايفين غير ISmsSender.
الفريمورك مليان adapters: StreamReader adapter بيحوّل Stream (بايتات) لـ TextReader (حروف)، وكل logging provider بيحوّل Serilog أو NLog لـ ILogger، وكل EF Core database provider هو adapter بين موديل EF وقاعدة بيانات معيّنة.
5

غلطات بتحصل كتير

  • adapter بيسرّب أنواع المزود في الـ signature — زي Task<MessageResource> SendAsync(...). كل كود بيستهلك الـ port بقى مربوط بالمزود، والحدود بقت ديكور.
  • الـ port مرسوم على شكل الـ SDK — نفس الأسماء ونفس الـ parameters ونفس الترتيب. ده مش adapter، ده pass-through؛ أول مزود تاني هتعيد كتابة كل حاجة.
  • منطق business جوّه الـ adapter — حساب خصم، قرار «نبعت ولا لأ»، retry policy بتاعة الدومين. الـ adapter ترجمة بس؛ أي قرار بيروح للدومين.
  • exceptions المزود بتفلت زي ما هي — ApiException أو HttpRequestException طالعة لـ controller. نص فايدة الـ adapter في ترجمة الأخطاء، ولو سيبتها كودك هيـ catch أنواع vendor.
  • خلط Adapter مع Decorator وFacade — الـ Adapter بيغيّر الشكل لـ interface عندك، الـ Decorator بيحافظ على نفس الـ interface ويضيف سلوك (caching، logging)، والـ Facade بيبسّط subsystem كبير في باب واحد.
6

اختبر نفسك

1. الفايدة المعمارية الأساسية من adapter حوالين SDK خارجي إيه؟
الدومين بيعتمد على الـ port بتاعه، والـ adapter هو الملف الوحيد اللي يعرف إن المزود موجود. الأداء وال retries حاجات تانية خالص.
2. إيه الفرق بين Adapter وDecorator؟
TwilioSmsAdapter بيحوّل شكل لشكل تاني. لكن CachingSmsSender : ISmsSender اللي بياخد ISmsSender جوّاه ويضيف cache = decorator، لأن الداخل والخارج نفس الـ interface.
7

الخلاصة في ٣ نقاط

  1. كودك بيعرّف الـ port اللي هو محتاجه، والـ adapter بيلفّ المكتبة الجاهزة ويترجم — ومحدش من الطرفين بيتغير.
  2. الـ adapter مش بيترجم أسماء methods بس: الأنواع، الـ DTOs، الـ exceptions، وأسلوب الـ retry والـ paging كلهم بيتحوّلوا لأسلوبك.
  3. القاعدة الحديدية: أنواع المزود تقف عند حدود الـ adapter — لو TwilioClient ظهر في controller، الحدود اتخرقت.
