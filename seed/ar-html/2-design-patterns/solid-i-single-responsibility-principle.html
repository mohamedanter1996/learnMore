المسؤولية مش «بيعمل إيه» — المسؤولية هي «مين بيطلب منه يتغير»

SOLID I: Single Responsibility Principle
1

ليه الدرس ده مهم؟

عندك OrderService.cs في ASP.NET Core، بقى ٦٤٠ سطر. جواه قواعد الأوردر، وحفظ بـ EF Core، وإرسال إيميل تأكيد، وlogging. الأسبوع اللي فات طلبوا منك تغيّر مزوّد الإيميل بس — الـ pull request طلع فيه تعديل في الملف ده، والاختبارات وقعت في حتة الـ validation اللي إنت أصلاً ملمستهاش. ملف الاختبار بتاعه ١٦٠ سطر، وكل اختبار واحد بياخد ١٫٢ ثانية لأنه بيفتح DbContext حقيقي وSmtpClient بيستنى timeout.

الكلام المشهور «الكلاس يعمل حاجة واحدة» تعريف ناقص. التعريف الشغّال: الكلاس يبقى ليه سبب واحد بس يخليك تفتحه وتعدّله — يعني محور تغيير واحد، وصاحب طلب واحد. الـ OrderService اللي فوق ليه أربع أصحاب طلبات مختلفين تماماً: البيزنس، الـ DBA، الماركتنج، والـ ops.
لو مش فاهم الدرس ده: كل تعديل صغير هيبقى مخاطرة في كود ملهوش علاقة، والاختبارات هتحتاج تزوّر الدنيا كلها عشان تجرب سطر واحد، والـ merge conflicts هتعيش في نفس الملف على طول. وعلى الناحية التانية — لو فهمته غلط — هتطلّع ٤٠ كلاس كل واحد فيه method واحدة لشاشة CRUD عادية، وده أسوأ من اللي كنت فيه.
2

الفكرة في صورة: أربع جهات بتدق على نفس الباب

الرسمة دي هي الـ SRP كله. مش مهم الكلاس فيه كام method ولا كام سطر — المهم كام سهم داخل عليه. سهم واحد = مسؤولية واحدة. أربع سهام من أربع جهات مختلفة = أربع مسؤوليات متشابكة في ملف واحد.

مثال واقعي من شغلك

أ. الكلاس قبل الفصل

public class OrderService
{
    private readonly AppDbContext _db;
    private readonly ILogger<OrderService> _log;

    public async Task PlaceOrderAsync(Order o)
    {
        if (o.Total <= 0) throw new InvalidOperationException("Total");
        if (o.Lines.Count == 0) throw new InvalidOperationException("Empty");  // ← البيزنس

        _db.Orders.Add(o);
        await _db.SaveChangesAsync();                                     // ← التخزين

        using var smtp = new SmtpClient("smtp.internal");
        await smtp.SendMailAsync(BuildConfirmation(o));                    // ← الإشعارات

        _log.LogInformation("Order {Id} placed", o.Id);                     // ← الـ ops
    }
}

ب. بعد الفصل — كل محور تغيير في مكانه

public class OrderService(
    IOrderValidator validator,
    IOrderRepository repository,
    IOrderNotifier notifier)
{
    public async Task PlaceOrderAsync(Order o)
    {
        validator.Validate(o);
        await repository.AddAsync(o);
        await notifier.OrderPlacedAsync(o);
    }
}

// Program.cs — كل واحد يتبدّل لوحده من غير ما تلمس OrderService
builder.Services.AddScoped<IOrderValidator, OrderValidator>();
builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<IOrderNotifier, SendGridOrderNotifier>();
// والـ logging اتنقل لـ middleware في الـ pipeline، مش جوّه كود الأوردر

OrderService بقى منسّق (orchestrator): بيقول الترتيب، مش بيعرف تفاصيل حد. ده بالظبط سبب التغيير الوحيد بتاعه — لو خطوات عملية الأوردر نفسها اتغيرت.

ج. الفرق اللي تقدر تقيسه

// قبل: الاختبار لازم يشغّل الدنيا كلها
// OrderServiceTests.cs — 160 سطر، 1,200 ms للاختبار الواحد (LocalDB + SMTP timeout)

// بعد: mock واحد لكل محور، مفيش I/O خالص
[Fact]
public async Task PlaceOrder_SavesThenNotifies()
{
    var repo = new Mock<IOrderRepository>();
    var notifier = new Mock<IOrderNotifier>();
    var sut = new OrderService(new Mock<IOrderValidator>().Object, repo.Object, notifier.Object);

    await sut.PlaceOrderAsync(new Order { Total = 50 });

    repo.Verify(r => r.AddAsync(It.IsAny<Order>()), Times.Once);
}
// 22 سطر، 3 ms. وتبديل SMTP بـ SendGrid لمس ملف واحد جديد + سطر في Program.cs
المقياس اللي تحكم بيه: لما المتطلب X يتغير، بتفتح كام كلاس؟ واحد = ممتاز. كلاس واحد بيتغير لأسباب ملهاش علاقة ببعض → قسّمه. متطلب واحد بيلمس خمس كلاسات دايماً → إنت قسّمت زيادة.
5

غلطات بتحصل كتير

  • «الكلاس يعمل حاجة واحدة» — دي ترجمة ضايعة. المقياس هو محور التغيير مش عدد الأفعال. كلاس فيه ٨ methods كلهم بيخدموا نفس صاحب الطلب = SRP سليم.
  • التقسيم بعدد السطور — «أي كلاس فوق ١٠٠ سطر يتقسّم». ده بيقطع الكلاس في نص مسؤولية واحدة وينتج OrderServicePart2 اللي محدش فاهم هو ليه موجود.
  • فصلت الكلاس بس نادتيه بـ new — new OrderValidator() جوّه PlaceOrderAsync بيخلي الفصل شكلي: لسه مستحيل تختبره لوحده ولسه التغيير بيلمس ملفين. الفصل يتم بـ interface + DI.
  • كلاسات اسمها OrderManager أو Helpers — اسم من غير مسؤولية محددة معناه إنك متعرفش محور التغيير، فالملف ده هيبقى مكب لأي كود مش لاقي مكان.
  • SRP على شاشة CRUD بسيطة — ٤٠ كلاس بـ method واحدة لفورم فيه ٦ حقول. التعقيد اللي زوّدته أكبر من التعقيد اللي شلته.
6

اختبر نفسك

1. أدق صياغة لمبدأ الـ SRP هي:
المبدأ عن محاور التغيير (مين بيطلب التعديل)، مش عن الحجم ولا عدد الـ methods.
2. طلبوا يغيّروا نسبة خصم واحدة، فاضطريت تفتح ٦ كلاسات صغيرة عشان تنفّذ التغيير. ده معناه إيه؟
SRP مقياسه في الاتجاهين: كلاس بيتغير لأسباب مختلفة = قسّمه، ومتطلب واحد بيلمس كذا كلاس = لمّه.
7

الخلاصة في ٣ نقاط

  1. SRP = سبب واحد للتغيير، يعني صاحب طلب واحد — مش عدد methods ولا عدد سطور.
  2. لما تفصل، افصل بـ interface وDI؛ الفصل من غير حقن هو نفس التشابك باسم جديد.
  3. المقياس في الاتجاهين: كلاس بيتغير لأسباب مختلفة قسّمه، ومتطلب بيلمس خمس كلاسات لمّه.
