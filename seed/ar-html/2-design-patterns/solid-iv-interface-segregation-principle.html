SOLID IV: Interface Segregation Principle
1

ليه الدرس ده مهم؟

عندك IReportService فيه ٥ members: توليد PDF، توليد Excel، إرسال بالإيميل، جدولة، وتاريخ التشغيل. وعندك ٣ مستهلكين: ReportsController بيحمّل ملفات بس، NightlyDigestJob بيجدول ويبعت، وHistoryPageApi بيقرا التاريخ. يعني ١٥ ارتباط في الكود، واللي مستخدم فعلاً منهم ٥.

النتيجة العملية: غيّرت signature بتاع ScheduleAsync — الـ ReportsController اللي عمره ما نده الجدولة يعيد compile ويعيد test. وكل fake في التستات لازم يحقّق الـ ٥ members، فتلاقي throw new NotImplementedException() مزروع في كل مكان.

الـ ISP بيقول حاجة واحدة: قسّم الـ interface بالأدوار — IReportGenerator وIReportScheduler وIReportHistory — بحيث كل مستهلك يشوف العقد بتاعه هو بس. والمقياس مش عدد الكلاسات، المقياس المستهلك معتمد على إيه.
لو مش فاهم الدرس ده: هتفضل تكتب fakes فيها methods مرمية NotImplementedException، وأي تعديل في حتة هيفضل يكسّر build ناس مالهمش دعوة، وهتاخد List<T> في الـ parameters وإنت بتلف عليها بس — فتمنع اللي بيناديك إنه يبعت array أو نتيجة LINQ.
2

الفكرة في صورة: تغيير واحد بيوصل لكل المعتمدين

الـ interface التخين بيحوّل «سطح التعامل» لسطح واحد مشترك. إنت مش بتشارك implementation — إنت بتشارك سبب للتغيير. والـ ISP هو اللي بيقطع الشراكة دي، مش الـ DI ولا الـ layering.

مثال واقعي: التكلفة اللي تقدر تقيسها

أ. الـ fake في التست

❌ قبل — fake لـ interface تخين
class FakeReportService : IReportService
{
    public byte[] GeneratePdf(ReportData d) => new byte[8];
    public byte[] GenerateExcel(ReportData d)
        => throw new NotImplementedException();
    public Task EmailReportAsync(int id, string to)
        => throw new NotImplementedException();
    public Task ScheduleAsync(int id, string cron)
        => throw new NotImplementedException();
    public Task<List<Report>> GetHistoryAsync()
        => throw new NotImplementedException();
}
// 5 members · 4 منهم NotImplementedException
✅ بعد — fake لعقد الدور بس
class FakeGenerator : IReportGenerator
{
    public byte[] Generate(ReportData d, ReportFormat f)
        => new byte[8];
}
// member واحد · صفر NotImplementedException

// أو بـ NSubstitute من غير كلاس خالص:
var gen = Substitute.For<IReportGenerator>();
gen.Generate(default, default).ReturnsForAnyArgs(new byte[8]);

كل NotImplementedException في fake هو إشارة إن الـ interface أوسع من الدور. دي أرخص طريقة تكتشف بيها خرق الـ ISP — الكومبايلر بيوريك الفاتورة بنفسه.

ب. التقسيمة نفسها — وكلاس واحد لسه بيعمل الكل

public interface IReportGenerator { byte[] Generate(ReportData d, ReportFormat f); }
public interface IReportScheduler { Task ScheduleAsync(int reportId, string cron); }
public interface IReportHistory   { Task<List<Report>> GetHistoryAsync(); }

// implementation واحدة برضه — ISP مش بيطلب منك تكسّر الكلاس
public class ReportService : IReportGenerator, IReportScheduler, IReportHistory { /* ... */ }

services.AddScoped<ReportService>();
services.AddScoped<IReportGenerator>(sp => sp.GetRequiredService<ReportService>());
services.AddScoped<IReportScheduler>(sp => sp.GetRequiredService<ReportService>());
services.AddScoped<IReportHistory>(sp => sp.GetRequiredService<ReportService>());
// نفس الـ instance في الـ scope الواحد — مش ٣ نسخ

د. أضيق عقد يكفيك — ISP اليومي

// ❌ العقد أوسع من الاستخدام: أنا بلف بس، بس منعت الـ array والـ LINQ result
public decimal Total(List<OrderLine> lines)
{
    decimal t = 0;
    foreach (var l in lines) t += l.Amount;
    return t;
}

// ✅ IEnumerable<T> = اللف بس. دلوقتي بتقبل array و List و نتيجة Select من غير ToList()
public decimal Total(IEnumerable<OrderLine> lines)
    => lines.Sum(l => l.Amount);
والعكس صحيح: لو محتاج Count من غير لفّة، اطلب ICollection<T> أو IReadOnlyCollection<T>. الـ ISP مش «اطلب أضعف حاجة»، هو «اطلب بالظبط اللي بتستخدمه» — لا أوسع ولا أضيق.
الـ BCL نفسه فيه خرق مشهور: ICollection<T> فيه Add وRemove، فأي collection للقراءة بس مجبرة ترمي NotSupportedException منهم. عشان كده اتضافت IReadOnlyCollection<T> وIReadOnlyList<T> في .NET 4.5 — تقسيمة بالأدوار بعد ما التخانة عملت مشكلة.

غلطات بتحصل كتير

  • «ISP يعني interface لكل method» — لأ. ده انفجار interfaces بلا معنى. التقسيمة بتبقى بالدور يعني بمجموعة المستهلكين اللي بتستخدم نفس الحاجات مع بعض.
  • header interface لكل كلاس — IReportService بيعكس ReportService member بـ member. ده مش عقد دور، ده نسخة تانية من الكلاس بـ I في الأول، ومكسبتش حاجة.
  • تجاهل الـ NotImplementedException في الـ implementations — كل واحدة منهم بتقولك بالحرف إن العقد أوسع من الدور. دي أعراض مش تفاصيل.
  • خلط ISP بالـ SRP — الـ SRP عن الكلاس ليه سبب واحد للتغيير، الـ ISP عن المستهلك ميشوفش غير اللي بيستخدمه. كلاس واحد يعمل implement لتلات role interfaces = ISP سليم تماماً.
  • تقسيم بعد فوات الأوان على interface عامة (public API) — تقسيم interface منشورة = breaking change. لما تبقى شاكك، ابدأ ضيق وزوّد، مش العكس.
6

اختبر نفسك

1. الـ method بتلف على الـ input بس. حسب الـ ISP، نوع الـ parameter يبقى:
اعتمد على أضيق عقد بتستخدمه فعلاً — اللف لوحده محتاج IEnumerable<T> بس، وبكده بتقبل array وList ونتيجة LINQ.
2. كلاس ReportService واحد بيعمل implement لـ IReportGenerator وIReportScheduler وIReportHistory. ده خرق للـ ISP؟
الـ ISP بيتقاس عند نقطة الاعتماد: الـ ReportsController شايف IReportGenerator بس، وده اللي مهم. تكسير الكلاس قرار SRP منفصل.
7

الخلاصة في ٣ نقاط

  1. الـ interface التخين بيخلي كل مستهلك يدفع تكلفة members هو مش بيستخدمها — build وtest وfakes.
  2. قسّم بالأدوار مش بالـ methods، وسيب implementation واحدة تعمل الكل لو ده المنطقي.
  3. في كل signature بتكتبها اطلب أضيق عقد بتستخدمه فعلاً — IEnumerable<T> بدل List<T> هو ISP في أبسط صوره.
