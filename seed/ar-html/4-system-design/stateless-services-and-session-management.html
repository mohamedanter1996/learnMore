Stateless Services and Session Management
1

ليه الدرس ده مهم؟

عندك API بـ ASP.NET Core شغال على instance واحد وتمام. المرور زاد، فطلعت ٣ instances ورا load balancer بـ round robin. نفس الكود بالحرف، من غير أي deploy جديد للكود نفسه — وفجأة: المستخدمين بيتسجل خروجهم كل شوية، وعربية التسوق بتفضى، والملفات المرفوعة بترجع 404.

الأرقام من الـ logs: ٦٧٪ من الـ requests بترجع 401 (اتنين من كل تلاتة بيروحوا لـ instance غير اللي سجّلت الدخول عليه)، والـ /api/cart بيرجع سلة فاضية ٢ من كل ٣ مرات. مفيش exception في الـ logs خالص — الكود «شغال»، الافتراضات هي اللي ماتت.

الخدمة الـ stateless مش بتحتفظ بأي حاجة في ذاكرة البروسيس بين الـ requests. فأي instance يخدم أي request، والـ load balancing يبقى تافه، والـ deploy والـ crash والـ autoscale كلهم أحداث عادية محدش بيحس بيها.
لو مش فاهم الدرس ده: هتفكر إن المشكلة في Redis أو في الـ JWT expiry أو في CORS، وهتشغّل sticky sessions عشان الوجع يسكت — وتكون دفنت المشكلة مكان ما تقوم تاني في أول deploy، وفي الوقت اللي سيرفر واحد بيولع والتانيين فاضيين.
2

الفكرة في صورة: الـ request مش بيرجع لنفس السيرفر

الـ browser شايف «سيرفر» واحد، بس مفيش حاجة بتضمن إن request رقم ٢ يوصل لنفس البروسيس بتاع request رقم ١. فأي حاجة حفظتها في IMemoryCache أو في static field أو في session داخل الذاكرة — بالنسبة للـ request الجاي مش موجودة.

جرّب بنفسك: بعت requests وشوف اللي بيحصل

بصّ على توزيع الأعمدة في وضع الـ sticky — سيرفر واحد شايل كل الحمل. وبعدين اقتله وشوف كام مستخدم اتسجّل خروجه في اللحظة دي.

مثال واقعي من شغلك

أ. الـ DataProtection — السطرين اللي بيوقفوا الخروج العشوائي

❌ الافتراضي مع ٣ instances
// مفيش أي إعداد → كل instance بيولّد keyring لوحده
builder.Services.AddAuthentication()
    .AddCookie();

// النتيجة في الإنتاج:
// 6,400 × 401 في الساعة، و 67% من الـ requests
// بترجع للـ login page
✅ keyring مشترك
var redis = ConnectionMultiplexer.Connect("redis:6379");

builder.Services.AddDataProtection()
    .SetApplicationName("learnmore")
    .PersistKeysToStackExchangeRedis(redis, "DataProtection-Keys");

// 401 من الـ scale-out: صفر. التكلفة: قراءة واحدة
// للمفاتيح عند الإقلاع (~3 ms)، وبعدها من الكاش.
SetApplicationName مش تفصيلة شكلية: الـ keyring بيتشتق بـ purpose فيه اسم التطبيق. مفاتيح مشتركة + أسماء تطبيق مختلفة = نفس الـ bug بالظبط، وإنت فاكر إنك حلّيته.

ب. الـ session: من الذاكرة لـ Redis

// ❌ قبل: السلة في ذاكرة البروسيس — تضيع مع كل deploy ومع كل instance تاني
private static readonly ConcurrentDictionary<string, Cart> _carts = new();
_carts[userId] = cart;                       // 3 instances → 67% cache miss

// ✅ بعد: مخزن مشترك، أي instance يشوف نفس الحاجة
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = "redis:6379");
builder.Services.AddSession();

public async Task SaveCart(string userId, Cart cart, IDistributedCache cache) =>
    await cache.SetStringAsync($"cart:{userId}", JsonSerializer.Serialize(cart),
        new DistributedCacheEntryOptions { SlidingExpiration = TimeSpan.FromHours(2) });

التمن الحقيقي: قراءة الذاكرة المحلية ~٥٠ نانو ثانية، وقراءة Redis على نفس الشبكة ~١.٢ ملي ثانية. بتدفع ملي ثانية في الـ request عشان تكسب إنك تقتل أي instance في أي لحظة. مقايضة كسبانة.

ج. الاستثناء الشرعي: SignalR

// الاتصال المفتوح فعلاً بيعيش على سيرفر واحد — ده stateful بطبيعته.
// الحل مش sticky بس، الحل backplane عشان السيرفرات تكلّم بعضها:
builder.Services.AddSignalR()
    .AddStackExchangeRedis("redis:6379");

غلطات بتحصل كتير

  • sticky sessions كعمارة مش كعكاز — بتخفي المشكلة وتجيب تلاتة مكانها: توزيع أعرج، وdeploy بيسجّل خروج ناس، وسيرفر واحد بيولع والباقي فاضي. مقبولة كمرحلة هجرة مؤقتة، وبس.
  • مفاتيح DataProtection مشتركة بأسماء تطبيق مختلفة — نسيت SetApplicationName فالـ purpose مختلف، والـ cookie لسه مش بتتفك. الـ bug شكله «Redis مش بيشتغل».
  • static field أو IMemoryCache كمصدر حقيقة — عداد rate limit، أو feature flag، أو «آخر مرة عملنا sync». كل instance عنده نسخته، والأرقام بتبقى غلط ٣ أضعاف.
  • ملفات مرفوعة على القرص المحلي — انحفظت على A وطُلبت من B فبقت 404، وأول ما الـ container يتغيّر تروح خالص. مكانها object storage.
  • BackgroundService أو timer في كل instance — ٣ instances = الـ job بيشتغل ٣ مرات: ٣ إيميلات للعميل و٣ خصومات. عايز leader election أو scheduler برّه التطبيق.
  • «JWT خلاص بقيت stateless» — لحد ما تحتاج تسحب توكن قبل ميعاده؛ الـ revocation list حالة مشتركة لازم تعيش في مخزن مشترك.
6

اختبر نفسك

1. اتنين instances من ASP.NET Core ورا load balancer، والمستخدمين بيتسجل خروجهم عشوائياً. أرجح سبب؟
الـ auth cookie بتتشفر بمفاتيح DataProtection. لو مش متخزنة في مكان مشترك، كل instance بيولّد مفاتيحه، فالـ cookie بتبقى مفهومة على السيرفر اللي أصدرها بس.
2. إيه الاختبار العملي اللي بيقولك إنك stateless بما يكفي؟
ده الاختبار اللي بيقيس النتيجة مش الوسيلة. لو عدّيته، تبقى الـ deploy والـ crash والـ autoscale كلهم أحداث عادية — وده بالظبط اللي بيخلي الـ containers والـ serverless ممكنين من الأساس.
7

الخلاصة في ٣ نقاط

  1. Stateless = مفيش حاجة في ذاكرة البروسيس بين الـ requests، فأي instance يخدم أي request.
  2. الحالة ليها بيوت معروفة: الهوية في توكن/cookie، الـ session في Redis، الملفات في object storage، ومفاتيح الـ DataProtection مشتركة.
  3. الـ sticky sessions تأجيل للمشكلة مش حل — والاستثناء الشرعي الوحيد هو الاتصالات المفتوحة زي SignalR، ومعاها backplane.
