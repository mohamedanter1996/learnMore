Database Replication: Read Replicas and Failover
1

ليه الدرس ده مهم؟

عندك ASP.NET Core API على SQL Server. الـ primary ٨ vCPU، بيشيل ٢٤٠٠ قراءة/ث و١٥٠ كتابة/ث — يعني ٩٤٪ من الشغل قراءة. الـ CPU ثابت على ٨٨٪ وGET /api/orders الـ p95 بتاعه ٤٢٠ ملي ثانية.

ضفت readable secondary ووجّهت الاستعلامات عليه: الـ CPU نزل لـ ٣٣٪ والـ p95 بقى ١١٠ ملي ثانية — من غير ما تكبّر السيرفر. وبعد يومين جه بلاغ: مستخدم عدّل عنوانه، الصفحة رجّعت له العنوان القديم. مفيش غلط في الكود — الـ replica كان متأخر ١.٤ ثانية.

الـ replication بيخدم هدفين مختلفين، ومتخلطش بينهم: (١) High availability — الـ primary وقع، replica بيتـ promote في ثواني بدل ساعات (SQL Server: Availability Groups). (٢) توسيع القراءة — الـ SELECTs على النسخ، والـ primary يفضل فاضي للكتابة. والدايل الوحيد اللي بيحكم الاتنين: sync ولا async.
لو مش فاهم الدرس ده: هتفتكر الـ replica نسخة احتياطية (وهو بينسخ الـ DELETE الغلط في نفس الثانية)، أو هتعمل failover على replica متأخر وتخسر آخر ثواني من الأوردرات، أو هتخاف من الـ lag فتسيب كل القراءة على الـ primary وتدفع سيرفر أكبر على الفاضي.
2

الفكرة في صورة: مين بيستنى مين؟

Synchronous: الـ COMMIT ميرجعش للتطبيق غير لما الـ replica يكتب السجل على ديسكه ويأكد. صفر فقدان (RPO = 0) مقابل round-trip زيادة على كل كتابة — نفس سكة الـ WRITELOG اللي عرفتها في درس الـ transaction log. Asynchronous: الـ primary بيـ commit على طول والسجل ماشي ورا — الكتابة مش بتتأثر، بس عند الـ failover بتخسر آخر ثواني. الوصفة النموذجية: sync واحد جنبك للـ failover + async للقراءة والـ DR.

مثال واقعي: توجيه القراءة من غير ما تكسر المستخدم

❌ قبل — كل حاجة على الـ primary
// Program.cs
builder.Services.AddDbContext<AppDbContext>(o =>
  o.UseSqlServer(cfg.GetConnectionString("Primary")));

// 2400 read/s + 150 write/s على سيرفر واحد
// CPU 88%  ·  p95 = 420 ms  ·  الحل الوحيد: سيرفر أكبر
✅ بعد — context للكتابة وcontext للقراءة
builder.Services.AddDbContext<AppDbContext>(o =>
  o.UseSqlServer(cfg.GetConnectionString("Primary")));

builder.Services.AddDbContext<ReadDbContext>(o =>
  o.UseSqlServer(cfg.GetConnectionString("Replica")));

// CPU 33%  ·  p95 = 110 ms  ·  نفس الهاردوير
-- appsettings.json: الـ listener بيوجّه لوحده للـ secondary القابل للقراءة
"Replica": "Server=tcp:ag-listener,1433;Database=Shop;ApplicationIntent=ReadOnly;Encrypt=True"

الـ ApplicationIntent=ReadOnly مع AG listener بيتعامل مع الـ read-only routing list ويرمي الاتصال على secondary تلقائياً. ودي البيت الطبيعي للـ CQRS: query handlers على ReadDbContext، وcommand handlers على AppDbContext.

والـ ١.٤ ثانية بتاعة الـ lag؟ sticky-after-write

// بعد أي كتابة: علّم المستخدم ده لمدة 10 ثواني
Response.Cookies.Append("rp",
  DateTimeOffset.UtcNow.AddSeconds(10).ToUnixTimeSeconds().ToString());

// وقت القراءة: اختار المصدر على أساس العلامة دي
var readPrimary =
  Request.Cookies.TryGetValue("rp", out var v) &&
  long.TryParse(v, out var until) &&
  DateTimeOffset.UtcNow.ToUnixTimeSeconds() < until;

var orders = readPrimary
  ? await writeDb.Orders.AsNoTracking().ToListAsync()
  : await readDb.Orders.AsNoTracking().ToListAsync();

٦٪ بس من القراءات بتقع في نافذة الـ ١٠ ثواني دي — يعني ٩٤٪ من الحمل بيتشال عن الـ primary وصفر قراءة قديمة للمستخدم اللي لسه كاتب.

جرّب بنفسك: غيّر سياسة التوجيه والتأخير

القراءات بتروح فين؟
تأخير الـ replica: 1.4s
👤 المستخدم شاف: — 📉 قراءات اتشالت عن الـ primary: 100% 🔥 CPU الـ primary: 30% ⏱ p95: 110ms
قيس الـ lag، متخمّنش: SELECT * FROM sys.dm_hadr_database_replica_states فيها redo_queue_size وlast_commit_time. الفرق بين last_commit_time بتاع الـ primary والـ replica هو تأخيرك بالثواني — حطّه على لوحة مراقبة وعلى alert، لأنه بيكبر فجأة تحت الحمل وده بالظبط وقت ظهور الباج.
5

غلطات بتحصل كتير

  • «عندنا replication يبقى عندنا backup» — الـ replication بينسخ كل حاجة فوراً، بما فيها DELETE من غير WHERE. الـ backup بيحميك من الغلط البشري، الـ replica بينشره. محتاج الاتنين.
  • كل القراءات على الـ replica من غير sticky — المسارات اللي بتقرا بعد الكتابة على طول (حفظ → redirect → عرض) هي اللي بتكسر. والباج ده بيعدي من الـ staging لأن مفيش حمل فمفيش lag.
  • sync replica في region تانية — كل COMMIT بياخد الـ RTT كاملة (٨٠ ملي ثانية مثلاً)، فالكتابة بتموت. الـ sync لجارك في نفس الـ region، والـ async للبعيد.
  • failover تلقائي على replica غير متزامن — بتوعد نفسك بـ RPO صفر وبتخسر آخر ثواني فعلياً. التلقائي للـ sync بس؛ الـ async promotion قرار بشري بتقبل فيه الفقدان.
  • تفتكر إنك على replica وإنت لأ — ApplicationIntent=ReadOnly من غير listener وread-only routing list بيوصلك للـ primary وخلاص. اتأكد بـ SELECT DATABASEPROPERTYEX(DB_NAME(),'Updateability').
6

اختبر نفسك

1. مستخدم حفظ داتا وبعدها على طول شاف النسخة القديمة في الصفحة اللي بعدها. السبب الكلاسيكي في نظام فيه replicas؟
الكتابة راحت للـ primary والقراءة اللي بعدها راحت لـ replica لسه مـ applied-ش السجل. الحل: وجّه قراءات ما بعد الكتابة للـ primary لفترة قصيرة، أو استنى الـ replica يلحق الـ LSN بتاعك.
2. عايز RPO = 0 (مفيش أي فقدان عند الـ failover). إيه اللي بتدفعه مقابله؟
صفر فقدان معناه إن السجل اتكتب في مكانين قبل ما يترد على التطبيق. فالـ sync بيزوّد latency الكتابة بمقدار الـ round-trip — وعشان كده بيكون في نفس الـ region، والـ async للمسافات البعيدة.
7

الخلاصة في ٣ نقاط

  1. الـ replication بيحل هدفين منفصلين — بقاء الخدمة وتوسيع القراءة — والدايل اللي بيحكمهم هو sync (صفر فقدان، latency زيادة) مقابل async (كتابة أسرع، ممكن تخسر آخر ثواني).
  2. الـ lag مش حالة استثنائية، ده وضع التشغيل العادي: قسّم الـ endpoints لـ «لازم primary» (قراءة بعد كتابة) و«replica-safe» (قوايم، بحث، تقارير).
  3. الـ replica مش backup — بينسخ غلطاتك في نفس الثانية، وfailover على replica متأخر يعني فقدان معلن سلفاً.
