Scaling Basics: Vertical vs Horizontal
1

ليه الدرس ده مهم؟

عندك API بـ ASP.NET Core شغال على VM واحدة ٤ كور. عادي بيشيل ٩٠٠ request في الثانية والـ p95 حوالي ١٤٠ ملي ثانية. جه يوم الحملة التسويقية فطلع الترافيك ٢٬٥٠٠ request/ثانية — الـ CPU ٩٩٪، والـ timeouts بدأت. الاقتراح اللي بييجي على طول في الاجتماع: «نقسّم النظام microservices».

قبل أي قرار معماري: ٦٥٪ من الـ CPU كان رايح لاستعلام واحد بيعمل WHERE CAST(CreatedOn AS date) = @d — non-SARGable فبيعمل scan. index مظبوط + كتابة الشرط صح رجّعه من ١٨٠ ms و41,882 logical reads لـ ٣ ms و٤ قراءات. نفس الجهاز بقى يشيل ٣٬٦٠٠ request/ثانية. صفر فلوس، صفر تعقيد.

الترتيب الهندسي الأمين: حسّن → اطلع فوق (vertical) → اتوسع بالعرض (horizontal). التحسين سعة ببلاش، والـ vertical سعة من غير تعقيد، والـ horizontal سعة بلا سقف بس بتعقيد بتدفعه كل يوم بعد كده.

لو مش فاهم الدرس ده: هتشتري سيرفرات لمشكلة سببها استعلام واحد، أو هتقفز لمعمارية موزّعة لضغط متخيّل — وأول ما يبقى عندك سيرفرين هتكتشف إن الـ session بيضيع، والملفات المرفوعة بتختفي، والـ cache بيقول داتا قديمة، والـ job الليلي بيشتغل مرتين.
2

الفكرة في صورة

Vertical = نفس الصندوق يكبر. Horizontal = صناديق أكتر ورا موزّع حِمل (load balancer) بيوزّع عليهم.

الـ load balancer مش بيعرف أي سيرفر «بتاع مين» — بيوزّع على اللي رادّ على /health. ومن اللحظة دي بالظبط، أي حاجة السيرفر فاكرها جوّه الذاكرة بقت كذبة.

مثال واقعي: إيه اللي بيتكسر في ASP.NET Core

أ. الحالة (state) اللي جوّه الـ process

❌ شغال على سيرفر واحد بس
// الـ session في ذاكرة الـ process
builder.Services.AddDistributedMemoryCache();
builder.Services.AddSession();

builder.Services.AddMemoryCache();   // cache محلي

app.MapPost("/upload", async (IFormFile f) =>
{
    var path = Path.Combine(env.WebRootPath, "uploads", f.FileName);
    // اتكتب على قرص srv-1 بس
});
✅ يشتغل على N سيرفر
// حالة مشتركة برّه الـ process
builder.Services.AddStackExchangeRedisCache(o =>
    o.Configuration = cfg.GetConnectionString("Redis"));
// أو من غير Redis، في نفس الـ SQL Server:
// builder.Services.AddDistributedSqlServerCache(o => { ... });
builder.Services.AddSession();

builder.Services.AddDataProtection()
    .PersistKeysToDbContext<AppDbContext>()
    .SetApplicationName("learnmore");

// الملفات في object storage، مش على القرص
السطر اللي بينسوه: AddDataProtection(). من غير مفاتيح مشتركة، الكوكي اللي عملها srv-1 مش هيقدر srv-2 يفكها → المستخدم بيتسجل خروج «عشوائي»، و The antiforgery token could not be decrypted في اللوج. الباج ده بيظهر في اليوم الأول من الـ horizontal scaling وبياخد أيام تشخيص لو متعرفش سببه.

ب. الـ job اللي بقى بيشتغل مرتين

// IHostedService واحد × سيرفرين = تشغيلين لنفس الـ rollup
await using var conn = new SqlConnection(cs);
await conn.OpenAsync(ct);

var cmd = new SqlCommand("sp_getapplock", conn) { CommandType = CommandType.StoredProcedure };
cmd.Parameters.AddWithValue("@Resource", "nightly-rollup");
cmd.Parameters.AddWithValue("@LockMode", "Exclusive");
cmd.Parameters.AddWithValue("@LockOwner", "Session");
cmd.Parameters.AddWithValue("@LockTimeout", 0);
var rc = cmd.Parameters.Add("@ret", SqlDbType.Int);
rc.Direction = ParameterDirection.ReturnValue;

await cmd.ExecuteNonQueryAsync(ct);
if ((int)rc.Value < 0) return;   // سيرفر تاني ماسك اللوك → اخرج بهدوء

await RunRollupAsync(ct);      // واحد بس بيدخل هنا

قبل الـ lock: جدول DailySummary كان بيتكتب مرتين كل ليلة → أرقام التقرير ×٢. بعده: تشغيلة واحدة، والسيرفر التاني بيخرج في أقل من ١ ms.

ج. أرقام القرار

4 cores   ≈ 1,200 rps    $90/شهر
8 cores   ≈ 2,200 rps    $190/شهر     // ×1.8 سعة بـ ×2.1 سعر
16 cores  ≈ 4,000 rps    $450/شهر
32 cores  ≈ 7,000 rps    $1,300/شهر   // ×5.8 سعة بـ ×14 سعر — وده آخر الجهاز

2 × 4 cores ≈ 2,340 rps  $180/شهر     // + يعيش لو واحد وقع
الـ vertical بيقف عند سقف الجهاز، والسعر بيطلع أسرع من السعة قبل ما توصل للسقف ده بكتير. والأهم: جهاز واحد = نقطة فشل واحدة. أول سيرفرين مش بتشتريهم عشان السعة — بتشتريهم عشان تقدر تعمل deploy أو reboot من غير downtime.
5

غلطات بتحصل كتير

  • «هنتوسّع بالعرض عشان النظام بطيء» — التوزيع بيحل نقص السعة، مش بطء الاستعلام. request بياخد ٨٠٠ ms هيفضل ٨٠٠ ms على ٢٠ سيرفر — إنت بس دفعت أكتر عشان تستنى نفس المدة.
  • IMemoryCache مع أكتر من instance — بتمسح المفتاح على srv-1، وsrv-2 فاضل مخزّن القديم لحد ما الـ TTL يخلص. المستخدم بيشوف سعر قديم أو جديد حسب أي سيرفر ردّ عليه.
  • ملفات مرفوعة على القرص المحلي — الرفع نجح على srv-1، والتحميل بعدين وصل srv-2 → 404 متقطّع مستحيل تعيد إنتاجه على جهازك.
  • Background job من غير قفل موزّع — كل instance بيشغّل نفس الـ IHostedService، فالإيميلات بتتبعت مرتين والتجميعات بتتضاعف.
  • اعتبار الـ sticky sessions حل — بيخفي المشكلة: الحِمل بيبقى غير متوازن، وأول ما سيرفر يقع كل مستخدمينه بيضيعوا. حل مؤقت للهجرة، مش معمارية.
6

اختبر نفسك

1. الترتيب الصح للهجوم على مشكلة سعة:
التحسين سعة ببلاش، والـ vertical سعة من غير تعقيد، والـ horizontal سعة بلا سقف مقابل تعقيد دائم.
2. تطبيق ASP.NET Core بإعداداته الافتراضية طلع من instance لـ instance‑ين ورا load balancer. إيه اللي بيتكسر فوراً؟
كله من نوع واحد: حاجة السيرفر فاكرها لوحده. الحل المعياري: تطلّعها برّه الـ process (distributed cache، object storage، مفاتيح مشتركة، قفل موزّع للـ jobs).
7

الخلاصة في ٣ نقاط

  1. حسّن الأول: index أو cache بيدي سعة ببلاش، والتوزيع مش بيعالج استعلام بطيء أبداً.
  2. Vertical = سعة من غير تعقيد لحد سقف الجهاز، وسعرها بيطلع أسرع من السعة نفسها.
  3. Horizontal بتشتريه للـ availability قبل السعة — وتمنه إنك تطلّع كل حالة برّه الـ process.
