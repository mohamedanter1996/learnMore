الـ Load Balancer مش بيوزّع بس — هو اللي بيقرر مين «حيّ»

Load Balancing: Algorithms and Health
1

ليه الدرس ده مهم؟

عندك API بـ ASP.NET Core شغال على ٣ instances ورا Azure Application Gateway، بياخد ٦٠٠ request في الثانية. instance واحد بايظ (OutOfMemory) والبروسيس لسه واقف على البورت. الـ LB بيوزّع round robin، فـ ٢٠٠ request في الثانية بتاخد 502 — وده هيفضل كده لحد ما حد يلاحظ. التنبيه جه بعد ١٨ دقيقة.

نفس الموقف ومعاك health check فعّال كل ١٠ ثواني مع عتبة فشل مرتين: الـ instance بيتشال من التوزيع في ~٢٠ ثانية، وبعدها صفر أخطاء. نفس الكود، نفس السيرفرات — الفرق سطرين إعدادات.

الـ LB بيجاوب على سؤالين مختلفين: «أبعت لمين؟» (ده الـ algorithm) و «مين أصلاً يستحق يستلم؟» (ده الـ health check). التاني هو اللي بيحوّل «سيرفر وقع» من عطل لحدث محدش حسّه.
لو مش فاهم الدرس ده: هتسيب الـ round robin يبعت لسيرفر ميت، أو — الأسوأ — هتحطّ الداتابيز في الـ liveness probe، فأول ما الداتابيز تتعثر ثانيتين كل الـ instances تبقى unhealthy في نفس اللحظة والـ LB ملقاش حد يبعت له: عطل كامل خارج من عطل جزئي.
2

الفكرة في صورة: التوزيع + نبضة الصحة

L4 ولا L7؟

الـ L4 بيوزّع TCP connections بالـ IP والبورت: سريع جداً وغبي جداً — مش شايف الـ HTTP خالص. الـ L7 بيقرا الـ request نفسه، فبيعرف يوجّه بالـ path (/api على الـ API و/static على مكان تاني) وبالـ host والـ headers، ويعمل TLS termination وضغط وكاش. شغلك اليومي كله مع L7: nginx، YARP، HAProxy، Azure Application Gateway.

جرّب بنفسك: بدّل الخوارزمية واقتل سيرفر

api-3 أبطأ ٣ أضعاف (نفس الـ pool، hardware أقدم). ابعت ١٢ request بـ round robin وبصّ على عداد الـ active بتاعه، وبعدين بدّل لـ least connections واعمل نفس الحاجة. وبعد كده دوس زرار الداتابيز وشوف الـ 503 بيطلع إزاي من عطل جزئي.

مثال واقعي: YARP + health checks

أ. قبل — توزيع من غير فحص صحة

// appsettings.json — توزيع بالدور، والـ LB مش بيسأل حد عن حاله
"ReverseProxy": {
  "Clusters": {
    "api": {
      "LoadBalancingPolicy": "RoundRobin",
      "Destinations": {
        /* d1, d2, d3 — عناوين الـ 3 instances جوّه الشبكة */
      }
      /* مفيش قسم HealthCheck خالص */
    }
  }
}
// d2 مات → 1/3 من الترافيك = 200 r/s بـ 502 لحد ما حد يلاحظ (18 دقيقة)

ب. بعد — least requests + active health check

"api": {
  "LoadBalancingPolicy": "LeastRequests",
  "HealthCheck": {
    "Active": {
      "Enabled": true,
      "Interval": "00:00:10",
      "Timeout": "00:00:02",
      "Policy": "ConsecutiveFailures",
      "Path": "/health/ready"
    }
  },
  "Metadata": { "ConsecutiveFailuresHealthPolicy.Threshold": "2" },
  "Destinations": { /* نفس التلاتة */ }
}
// Program.cs في الـ API — نقطتين منفصلتين، مش واحدة
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, tags: new[] { "ready" })
    .AddCheck<QueueBacklogHealthCheck>("queue", tags: new[] { "ready" });

// liveness: «البروسيس نفسه بايظ؟» — مفيش ولا فحص اعتمادية جوّاه
app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = _ => false });

// readiness: «أبعتلك traffic؟» — الاعتماديات المشتركة مكانها هنا بس
app.MapHealthChecks("/health/ready", new HealthCheckOptions {
    Predicate = c => c.Tags.Contains("ready")
});

ج. الفرق بالأرقام (نفس الـ ٣ instances، نفس الـ ٦٠٠ r/s)

القياسقبلبعد
وقت اكتشاف instance ميت~18 دقيقة (بتنبيه بشري)~20 ثانية (٢ فشل × ١٠ ث)
عدد الـ 502 في الحادثة~216,000~4,000
p95 وقت الاستجابة والـ requests أطوالها مختلطة820 ms (round robin)310 ms (least requests)
LeastRequests مكسبه مش في المتوسط — مكسبه في الـ p95. الـ round robin بيحط request سريعة ورا تقرير بياخد ٣ ثواني لأن الدور وصل. أقل عدد مشغول بيتجنّب ده لوحده.
حتة الـ draining: لما تشيل instance بإيدك (deploy)، سيبه يخلّص اللي في إيده. في ASP.NET Core خلّي /health/ready يرجع Unhealthy أول ما يوصل SIGTERM، واستنى دورتين probe قبل ما تطفي البروسيس — كده الـ in-flight requests متموتش.
5

غلطات بتحصل كتير

  • الداتابيز في الـ liveness probe — أخطر غلطة في الدرس. الداتابيز تتعثر ثانيتين → كل الـ instances فشلت في نفس اللحظة → الـ orchestrator بيعيد تشغيلهم كلهم والـ LB ملقاش حد. الاعتماديات المشتركة مكانها readiness: متبعتش traffic، بس متقتلش البروسيس.
  • /health بيرجع 200 على طول — endpoint شكلي مش بيفحص حاجة. ده أسوأ من إنه مش موجود، لأنه بيوعدك بحماية مش موجودة: البروسيس واقف على البورت والـ thread pool مخنوق، والـ LB لسه بيبعتله.
  • جلسة في ذاكرة البروسيس + توزيع — المستخدم يروح instance تاني فيلقى نفسه خرج. الحل مش sticky sessions (ده بيخلّي السيرفر مهم تاني ويخرب التوزيع)، الحل إن الـ service يبقى stateless والحالة في Redis أو في التوكن.
  • health endpoint تقيل ومش مكشوف — فحص بيعمل ٤ استعلامات، مضروب من ٣ LBs كل ثانية = حمل دائم على الداتابيز. خلّيه خفيف، وcache نتيجته لثانية-اتنين، ومتعرّضهوش للنت بره.
  • LB واحد — لسه عندك single point of failure، بس نقلته مكان. الـ LB السحابي redundant أصلاً؛ لو مستضيف nginx بنفسك، لازم زوج ورا IP عايم.
6

اختبر نفسك

1. ليه خطر إن الـ liveness probe يعتمد على الداتابيز؟
الـ liveness بيجاوب على «البروسيس ده بايظ؟» بس. فشل اعتمادية مشتركة مكانه الـ readiness، وبيتعامل معاه بإنك متبعتش traffic — مش بإنك تعيد تشغيل الأسطول كله.
2. الـ pool بياخد مزيج: lookups بـ ٢٠ ملي ثانية وتقارير Excel بـ ٣ ثواني. أنسب خوارزمية؟
الـ round robin بيفترض إن كل request زي التانية. لما الأطوال تختلف، الدور بيحط request سريعة ورا تقرير تقيل ويفجّر الـ p95. أقل عدد اتصالات بيقرا الحمل الحقيقي لحظياً.
7

الخلاصة في ٣ نقاط

  1. الخوارزمية بتجاوب «أبعت لمين»، والـ health check بيجاوب «مين يستحق يستلم» — والتاني هو اللي بيمنع العطل.
  2. لما أطوال الـ requests تختلف، least connections بيكسب الـ round robin في الـ p95 مش في المتوسط.
  3. الـ liveness يفحص البروسيس بس، والـ readiness هو اللي يشوف الاعتماديات — عكس كده بيحوّل عطل جزئي لعطل كامل.
