Caching I: Layers and Cache-Aside
1

ليه الدرس ده مهم؟

عندك endpoint في ASP.NET Core: GET /api/products/{id}. الاستعلام في EF Core بياخد ٤٥ ملي ثانية وهو مرتاح. جه الترافيك ١٢٠٠ طلب في الثانية — يعني ١٢٠٠ استعلام في الثانية على نفس الجدول، أغلبهم على نفس عشر منتجات. الـ CPU على SQL Server طلع ٩٠٪ والـ p95 بقى ٤٠٠ ملي ثانية.

حطيت cache-aside بـ TTL عشر دقايق. الـ hit ratio طلع ٩٤٪ → الداتابيز بقت شايفة ٧٢ طلب في الثانية بدل ١٢٠٠، والـ p50 نزل من ٤٦ ملي ثانية لأقل من ملي ثانية. مغيرتش سطر في الاستعلام ولا زوّدت سيرفر.

كل قرار caching هو نفس الصفقة: بتبيع شوية طزاجة وبتشتري سرعة. المهارة مش في إنك تعمل كاش — المهارة في إنك تحدد فين تخزّن وأد إيه تسمح للداتا تبقى قديمة.
لو مش فاهم الدرس ده: هتحط كاش من غير TTL فيتحول لـ memory leak بنوايا حسنة، أو هتحط مفتاح ناقص فتوّرِّي بيانات مستخدم لمستخدم تاني، أو هتعتمد على IMemoryCache على ٤ instances وتقعد تدوّر ليه الـ refresh بيرجّع نتيجتين مختلفتين.
2

الفكرة في صورة: رحلة الطلب عبر الطبقات

الطلب بيمشي من المستخدم لجوه لحد الداتابيز. أي طبقة تقدر ترد من عندها = الطبقات اللي بعدها مشافتش الطلب أصلاً. عشان كده القاعدة: خزّن أقرب ما تسمح الطزاجة — لو الداتا بتتغير كل شهر خليها في المتصفح والـ CDN، ولو بتتغير كل دقيقة نزّلها للـ application cache، ولو لازم تبقى دقيقة اللحظة ما تخزّنهاش خالص.

الطبقة الأخيرة اللي كتير بينساها: الـ buffer pool بتاع SQL Server نفسه كاش. يعني حتى «رحلة الداتابيز» ديه فيها hit وmiss جوّاها — بس دي حاجة مش تحت إيدك، والطبقات اللي فوق تحت إيدك بالكامل.

مثال واقعي من شغلك

أ. قبل: كل طلب بيضرب الداتابيز

app.MapGet("/api/products/{id:int}", async (int id, AppDbContext db) =>
    await db.Products.AsNoTracking()
        .FirstOrDefaultAsync(p => p.Id == id));

// p50 = 46 ms · 1200 req/s → 1200 استعلام في الثانية على نفس الصفوف

ب. بعد: cache-aside بـ IMemoryCache

app.MapGet("/api/products/{id:int}", async (int id, AppDbContext db, IMemoryCache cache) =>
{
    var key = $"product:{id}";
    if (cache.TryGetValue(key, out ProductDto? hit))
        return hit;                                  // 1) اسأل الكاش الأول

    var dto = await db.Products.AsNoTracking()      // 2) miss → المصدر الحقيقي
        .Where(p => p.Id == id)
        .Select(p => new ProductDto(p.Id, p.Name, p.Price))
        .FirstOrDefaultAsync();

    if (dto is not null)
        cache.Set(key, dto, new MemoryCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10),   // 3) TTL إجباري
            Size = 1
        });

    return dto;                                       // 4) رجّع
});

// hit ratio 94% · p50 نزل من 46 ms لـ 0.4 ms · الداتابيز شافت 6% من الحمل
لاحظ إننا بنخزّن ProductDto مش الكيان بتاع EF. الكيان المتتبَّع مربوط بـ DbContext عمره أقصر من الكاش، والكائن نفسه هيتشارك بين كل الـ requests — أي تعديل عليه بيبوّظ النسخة عند الكل. خزّن DTO ثابت (immutable) وخلاص. والـ Size ده بيلزمك بس لو ظابط SizeLimit على الكاش — وهي حاجة يستحسن تظبطها عشان تحط سقف للذاكرة.

ج. IMemoryCache ولا Redis؟

IMemoryCache — نانو ثواني، مفيش serialization ولا شبكة. بس: كل instance بكاشه لوحده، وبيضيع مع كل restart أو deploy. مناسب لـ reference data والمسارات السخنة جداً.
Redis (IDistributedCache) — ملي ثانية، فيها شبكة + serialization. بس: حقيقة واحدة مشتركة بين كل الـ instances وبتعيش بعد الـ deploy. مناسب للـ sessions والداتا اللي إبطالها مهم.

والنمط الاحترافي هو الاتنين مع بعض: L1 في الذاكرة بـ TTL قصير (٣٠ ثانية) فوق L2 في Redis (١٠ دقايق) فوق الداتابيز. الـ L1 بيمتص الضرب على المفاتيح السخنة، والـ TTL القصير بيحدّ أد إيه الـ instances ممكن تختلف عن بعض. .NET 9 عمل النمط ده رسمي باسم HybridCache: 

builder.Services.AddHybridCache(o =>
{
    o.DefaultEntryOptions = new HybridCacheEntryOptions
    {
        LocalCacheExpiration = TimeSpan.FromSeconds(30),   // L1 في الذاكرة
        Expiration = TimeSpan.FromMinutes(10)              // L2 في Redis
    };
});

// الاستخدام: مفيش TryGetValue ولا Set — نمط واحد بيلمّ الحالتين
var dto = await cache.GetOrCreateAsync(
    $"product:{id}",
    ct => LoadProductAsync(id, ct));

5

غلطات بتحصل كتير

  • كاش من غير TTL — «الداتا دي مبتتغيرش» مش سبب. المدخل هيفضل في الذاكرة لحد ما البروسيس يموت. أي مدخل كاش ليه تاريخ انتهاء، من غير استثناء.
  • مفتاح ناقص هوية — cache.Set("profile", dto) بدل $"profile:{userId}" (أو الـ tenant). دي مش مشكلة أداء، دي تسريب بيانات من مستخدم لمستخدم، وبتظهر في الإنتاج بس.
  • توقّع طزاجة موحّدة من IMemoryCache على أكتر من instance — عدّلت المنتج، instance واحد بس اللي عرف، والباقي هيفضلوا يرجّعوا القديم لحد ما الـ TTL يخلص. لو الطزاجة مهمة → Redis مشترك.
  • تخزين كيان EF متتبَّع أو object قابل للتعديل — كل الـ requests بتشوف نفس الكائن، وأي تعديل عليه بيتسرب للكل. خزّن DTO ثابت.
  • الشغل من غير قياس — من غير hit ratio إنت مش عارف لو الكاش شغال أصلاً. تحت ٨٠٪ على مسار قرائي معناه TTL قصير أوي أو مفاتيح غلط أو داتا مش مناسبة للتخزين.
6

اختبر نفسك

1. في الـ cache-aside، لو الكاش نفسه وقع، بيحصل إيه؟
الـ cache-aside بيعامل الكاش كتسريع اختياري والداتابيز هي مصدر الحقيقة — عشان كده استثناء من Redis لازم يبقى fallback مش 500. وبرضه خد بالك: داتابيز باردة تحت الحمل الكامل دي مخاطرة لوحدها.
2. عندك ٤ instances بـ IMemoryCache وTTL عشر دقايق. حد عدّل سعر منتج في الداتابيز من غير أي إبطال. إيه اللي بيحصل؟
كل instance بكاشه لوحده وبـ TTL بدأ في وقت مختلف، فالمستخدم ممكن يعمل refresh ويشوف سعرين. ده السبب الجوهري لاختيار Redis لما الطزاجة المشتركة مهمة — أو TTL قصير جداً لو الاختلاف مقبول.
7

الخلاصة في ٣ نقاط

  1. الكاش صفقة واضحة: بتدفع طزاجة وتقبض سرعة — فحدّد أد إيه الداتا مسموح تبقى قديمة قبل ما تختار الطبقة.
  2. Cache-aside = اسأل الكاش، لو مش موجود هات من المصدر وخزّن بـ TTL — وميزته إن سقوط الكاش بيبطّئ التطبيق مبيوقّفهوش.
  3. IMemoryCache أسرع بس لكل instance لوحده، وRedis أبطأ بس حقيقة واحدة مشتركة — والـ HybridCache بيديك الاتنين بـ TTL قصير فوق TTL طويل.
